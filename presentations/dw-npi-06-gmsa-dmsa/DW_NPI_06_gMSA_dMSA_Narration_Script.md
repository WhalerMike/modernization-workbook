# Building Non-Person Identity, Chapter 06 — gMSAs, dMSAs and the Kerberos Island — narration script (practice copy)

## Slide 1 — Chapter 06: gMSAs, dMSAs and the Kerberos Island

Welcome to the Federal Modernization Workbook's developer workbook, Building Non-Person Identity. This is Chapter 6: group and delegated managed service accounts, and the Kerberos island. These accounts are good credentials with a known expiry date, the day the last domain controller is demoted, so the chapter makes sure every one of them moves, retires, or sits on a dated list before then. We'll start from Learn's own procedures, see what they leave out, then walk the plan, the island list, the write path, two labs and the dangers. One note before we begin: the code is illustrative, tested against fixtures.

## Slide 2 — Why every gMSA and dMSA needs an end date

Why does this chapter have an end date built in? Because a group managed service account only works while A D is in charge, and anything still running under one of these accounts loses its credential when the last domain controller goes. So every account must end up moving to a workload identity, retiring, or on a dated island list. The program's rules, as design guidance: each account's disposition is the owner's decision from Chapter 3. New accounts follow the managed service account standard, and a group account's retrievers are one group of its hosts. Every write carries its SailPoint request and ServiceNow change. The pipeline's own account sends what it can; a person sends the delegated account steps. And never delete: the old account is disabled and moved to a holding O U, and a person deletes it later.

## Slide 3 — What gMSAs and dMSAs are, and where the code runs

A quick grounding in what these accounts are. A group managed service account is a domain account whose password the domain controllers manage and rotate, and which several servers can fetch. Learn adds rules the plan respects: its name must be unique in the forest, its password interval can be set only when it's created, and a forest should have only one key distribution service root key, because more than one makes these accounts fail after a rotation. The delegated kind is new in Windows Server 2025: it takes over from an old-style service account, and once the move completes, the old password stops working and the old account is disabled. The workbook's migration path matrix says which target each account gets. And because everything here is an Active Directory command against the domain, the cloud choice doesn't change anything in this chapter.

## Slide 4 — Learn's four procedures, pinned and run

Here's what Microsoft gives you: four procedures, covering the delegated account walk-through, its limits, the group account walk-through, and the one-time root key that every managed password is derived from. These procedures live only inside web pages, so the repository pins their source unmodified, with hashes a test checks and a weekly watch for changes. Then a harness runs each PowerShell block exactly as published, against stand-ins that accept only the parameters the real commands have. That last detail matters, as you'll see in a moment.

## Slide 5 — What the procedures leave to you: the key and the steps

This is where the stand-ins earn their keep. The creation steps are fine, and the code keeps them as its model. But the root key check uses a command that returns the key itself, the secret every managed password comes from, so the code reads only its start time. The backdated key is meant for a test lab, not production. And one step sets the migration state with a parameter the command simply doesn't have, so as published it fails. Placeholder names that change from step to step are replaced by names from reviewed data, held to the program's naming standard, and a group account's retrievers become one reviewed group of its hosts.

## Slide 6 — What they leave to you: limits, waits and deletes

The rest of the gaps are about timing and safety. The walk-through completes a migration with no wait, while the overview asks for weeks, so the code waits thirty days, the program's parallel run. It never checks the limits, like unconstrained delegation that silently stops working, so the code checks each one before planning. It restarts every service on the host. And the pages disagree on deleting the old account; the code takes the stricter side and has no delete at all. So the verdict: use Learn's commands and their order, but not the procedures as the program.

## Slide 7 — The code, Chapter 03's decisions and four inputs

So what does the code add? A module, two entry scripts kept strictly apart, one that only reads and one that writes, and its own list of allowed calls. It builds on Chapter 1's register and Chapter 3's decisions, and refuses either if its hash doesn't match. Then four reviewed files. The first gives each re-platformed account's new account, workload and hosts, and the SailPoint request and ServiceNow change that approved its writes; Chapter 12 writes these rows for approved requests. The second says who may fetch each managed password. The third is the forest's account standard: the service account O U, the holding O U, the creator group, the retriever group pattern and the thirty-day interval. The fourth is the one program dates file. The end state has no default: if the decision is missing, the run stops rather than guessing.

## Slide 8 — The check: ten rules, NPI-KRB-01 to NPI-KRB-10

The reader collects the root key's start time, every managed account with its password retrievers and migration state, and, for a delegated conversion, the domain controllers and each host's operating system. Then ten rules run. Some come from Learn: the root key must exist and be old enough, the migration's limits must hold, and managed accounts shouldn't sit in privileged groups. Others come from the project plan: every account needs a decision, an owner for its service principal names, an end date inside the program's deadline, and a reconciled destination. The account standard adds three checks: a new name must follow the naming standard, a group account's retrievers must be exactly one group of its hosts, and a write with no SailPoint request or ServiceNow change isn't planned at all; the plan records it as blocked. Every finding gets a stable ID.

## Slide 9 — The plan: one action per account

Each account becomes one action, or, for a superseded account, a disable and a move together. The group account path: create it in the service account O U with a thirty-day interval, outbound-only when the old account holds no service principal names; the server owner installs it and switches the service over; after a thirty-day parallel run, disable the old account and move it to the holding O U. The pipeline sends those writes. The delegated path: create it, start the migration, wait thirty days, then complete it. A person sends those, because they need Domain Admins. Each write carries who sends it, its request, its change and its controls. And because the same inputs always produce the same file, byte for byte, a reviewer approves one hash.

## Slide 10 — The island list and the reconciliation

Two outputs carry the chapter's end date. The island list holds every account that will stay on Kerberos, under the name it will end up with, along with its disposition from Chapter 3, its owner, its end date and the date that bounds it, and whether it's ready to hand to the program's retirement work. An account kept on Kerberos is ready only with the authorizing official's acceptance. The hand-off flag only turns true when every single row is ready. The reconciliation covers every managed account, existing or planned, and says where it ends up. When the program confirms its end-state decision, the program dates file changes in a reviewed pull request, and Chapter 3's run and this one are repeated well before A D retires.

## Slide 11 — The separate write path, and its refusals

Writing to the domain lives in its own script, which refuses to run unless several things are true. The plan must be the exact one a reviewer approved, by hash, for this domain and less than a week old. Every write must be a declared call with only its allowed parameters, in the right O U, carrying its SailPoint request and ServiceNow change, and nothing that deletes or undoes exists to call. Each call also says who sends it. Run as the pipeline's own account, it sends the creations, retriever changes, disables and moves, and refuses the delegated account steps. Run as a person, it sends those, and refuses the pipeline's, except in a test domain. So one approved plan is applied in two runs. Before each write it checks the target again; after it, it reads it back, recording sent only when the change shows.

## Slide 12 — Who builds, runs and reviews it, and with what rights

Who's involved? Developers build the code. Server and directory engineers own the pipeline that runs the write path, run its delegated account steps, and change the hosts. Application owners name each service principal name's owner and end date, and the security officer reviews the island list. The read task holds no domain administration, just a narrow delegated read of the root key's dates. The write task is split. The pipeline's own group managed service account holds only delegated rights on the service account O Us, to create group accounts, set their retrievers, and disable and move old ones. It's in no privileged group. The delegated account steps need Domain Admins under Learn's procedure, so they stay with a person, on a plan someone else approved.

## Slide 13 — Lab 1: Learn's procedures, then the check

Lab 1 needs only a laptop, PowerShell 7 and Pester, plus the runs of Chapters 1, 2 and 3: the register, the owners and the owners' decisions. First you run Learn's own procedures against the stand-ins, and you can read the test where the migration-state step fails, just as it would on a real server. Then you list what each task is allowed to run: the read task is only lookups. Then you run the check against a fictional estate. Nine accounts are in scope, with six findings and five planned writes: four for the pipeline to send and one for a person. And the hand-off isn't ready yet. Let's see why.

## Slide 14 — Lab 1: reading the findings and the plan

Reading the findings is where the rules become concrete. Every decision here is the owner's, from Chapter 3. One web server account is trusted for unconstrained delegation, which stops working after a delegated migration, so its owner kept it on Kerberos, with the authorizing official's acceptance, but it has no S P N owner. Two group accounts still name computer accounts as retrievers, while their reviewed lists name one group of hosts each, so the plan corrects both. An intranet account being re-platformed has no owner and an end date years out, so it can't be reconciled. Meanwhile the plan completes a migration that started forty days ago, and creates two group accounts with a thirty-day interval; the print account's is outbound-only. Each write shows its request, its change, and who sends it.

## Slide 15 — Lab 1: the island list, a dry run and a refusal

Next you read the island list and the reconciliation side by side. Two rows aren't ready for hand-off, so the flag stays false. The web front end carries the authorizing official's acceptance, so it becomes ready once it has an S P N owner. That's the point: an incomplete list never goes. Then the write path. A dry run as the pipeline reports four writes it would send, and refuses the migration's completion, a person's step. Applying it to the fake as the pipeline sends those four; applying it as a person sends the completion and refuses the rest. Each run reads every write back. Finally you pass a hash nobody approved, and it refuses outright. The full suite is five hundred forty-nine passing tests.

## Slide 16 — Lab 2: a test domain, a real migration

Lab 2 moves to a test domain, never production, with a Windows Server 2025 domain controller and member server. You make two test accounts, one for each path, record their decisions by running Chapters 2 and 3 over them, and create the group account's retriever group with the member server in it. The inputs name a test request, a test change and the test domain's O Us. You grant the reader only a narrow delegated read of the root key's dates. A second person reviews the plan and hands you its hash. You apply it as a person; the group account is the pipeline's step, so a person sends it only in a test domain, with the test domain switch. Then run the next plan to start the migration and watch the Kerberos events. After thirty days, complete it, or back it out by hand.

## Slide 17 — Dangers, and the guard for each

Each of these failures has a guard in the code. The biggest is the one the chapter is built around: an account left behind when A D retires, and the guard is the reconciliation, rerun whenever the end-state decision changes. Others are about the migration itself: completing too early, on a host that can't use the new account, or deleting the old one so there's no way back. Then the quieter ones: reading the root key as a secret, widening retrievers by hand, or a plan that changed after review. Two come from the account standard: a write identity with more rights than it needs, guarded by giving the pipeline's account only delegated rights and keeping Domain Admins with a person; and a write nobody approved, guarded by refusing any write without its SailPoint request and ServiceNow change. Each guard is a rule that runs every time.

## Slide 18 — Done when: the chapter's checklist

Here's what done looks like. Every Kerberos account has a reviewed decision, and the root key was checked without administrator rights. Retrievers match the reviewed list, one group per group account, and every new account follows the standard. Every write carried its SailPoint request and ServiceNow change, the pipeline's account held only its delegated rights, and a person sent the delegated account steps. No migration broke the limits or finished early, and someone other than the person who applied each plan approved it. Nothing was deleted by this code. Every island account has an owner and an end date inside the deadline, and every managed account has a reconciled destination.
