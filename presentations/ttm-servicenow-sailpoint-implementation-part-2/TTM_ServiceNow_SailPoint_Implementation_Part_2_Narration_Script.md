# Companion guide — Ticket-to-Machine on ServiceNow and SailPoint — Implementation, Part 2 — narration script (practice copy)

## Slide 1 — Part 2: Actuation, re-read, tempo and evidence

Welcome to Part 2 of the implementation series for Ticket-to-Machine on ServiceNow and SailPoint. Part 1 confirmed the boundary, decided the writers and approvers, connected the sources, and opened the front door. Part 2 covers the three gates that finish the loop. First, actuation, where the ticket authorizes a machine to do the work. Then the re-read, because a ticket status isn't proof. And then the tempo, with its measures, its identity fixes, and the evidence an ISSO files. After that, we'll look at the dangers across all seven gates, and what it would take to move the guide from draft to proved. It's still an example, not an endorsement. And because the kit's first pass doesn't actuate anything, the first gate here is about configuring the products themselves.

## Slide 2 — G5–G7 on one page: done when, proved by, rollback

Here are Part 2's three gates on one page. Actuation is done when each lane acts through a connector or a declared exception, under a service identity, with a change record where its class needs one. It closes the third gap, and there's no automated check for it yet. You'll run one task per lane by hand. The re-read gate is done when nothing closes without a re-read of the target, which closes the first gap. The kit's tests prove its logic. The tempo gate is done when the windows are measured, the identity fixes run through the loop, and the evidence is produced on a schedule. Two rules run through all three. A person's role stops at approval, except for declared exceptions. And a success response doesn't count as closure. The kit's first pass doesn't write to Entra ID, Active Directory or SailPoint, which is why the actuation gate relies on a manual lab for now.

## Slide 3 — G5: the ticket authorizes a machine, by authority

In the actuation gate, the ticket authorizes a machine. For owner-governed access, SailPoint's connectors do the work: accounts, groups, roles, licenses and access packages. When the Entra connector disables an account, it also signs the user out of any existing sessions. For low-authority tasks, ServiceNow's Entra spoke can act, as long as its actions cover the task. Check what it really covers. It has no M F A reset action, and its reset action works only for cloud-only users. When a person does have to act, they activate an eligible role through PIM, with the ticket number as the justification. PIM doesn't check that number, so a SIEM rule does. And resetting someone's authentication methods stays with the help desk's identity verification. A connector's M F A setting is not a substitute for verifying the person. The prerequisites are the front door from gate four, and the lanes decided in gate two, already written into the record.

## Slide 4 — G5: change records, and the declared-exception lane

Two more steps cover what the connectors can't. SailPoint's service desk integration can't raise change requests, which is the third gap. So a ServiceNow flow raises a standard, normal or emergency change from the request, based on its change class. The kit plans that flow for its second pass. Until then, the approver raises the change record by hand and links it. Either way, closure still waits for the re-read. Disconnected applications, the ones with only an admin console, run in the declared-exception lane. That means a service desk ticket, a named approver before the session, a time-limited PIM activation, a recorded session, an end date, and a plan-of-action item to automate or retire the application. The danger is the exception that never ends. End dates and reviews are what stop it. The ServiceNow flow chooses the change type from the class, so a pre-authorized standard change, a normal change with approvals, or an emergency change each leave the record the class needs.

## Slide 5 — G5: requirement, evidence, availability, rollback

On the federal side, access restrictions for change call for the connector and spoke identities, with their permissions. Access enforcement and least privilege call for SailPoint's provisioning events and PIM activation records. Change control calls for change records linked from each request. Session audit isn't in any baseline, but it's added here, so declared-exception sessions are recorded with counsel consulted. And each exception gets a plan-of-action item. Validation is manual. Run one task per lane from start to finish, and confirm each leaves its record. Then re-run the identity check, so no integration identity holds more than its lane needs. PIM is available in Azure Government. The spoke's documentation shows only the worldwide Graph endpoint, so it fits GCC, but confirm GCC High with ServiceNow. To roll back, run the paired action. A leaver's deprovisioning is never rolled back. They come back through a new request.

## Slide 6 — G6: Awaiting verification, and the business rule

The re-read gate closes the first gap. Out of the box, SailPoint treats a mapped ServiceNow status as done. So add an awaiting verification state, and a business rule that turns any close into that state. The only exception is an update that carries new evidence and comes from the verifier account. A named exception approver can still cancel with a note. Apply the same rule to the incident and request tables, so SailPoint's status mapping no longer decides completion. Then schedule the re-read client. It re-reads the account, the identity, or the Graph user. If the target matches, it closes the record with the query, the time and a hash of the response. If it doesn't match, it reopens the record with the differences. A SailPoint read reflects the last aggregation, so allow a grace period, tuned to the aggregation schedule. The verifier account comes from gate one, and its audit trail is what makes every closure attributable.

## Slide 7 — G6 in code: six waiting findings, re-read offline

The workbook's fifth chapter adds two things to the re-read client. The first is a guard. A record whose intended state names nothing checkable used to close on nothing, with evidence. Now it's skipped, and never verified. The second is an offline mode. It makes the same decisions using saved records and saved reads. It never writes anything, and it treats a missing read as an error, never as a match. Six fictional records are re-read at noon. Three verify. A terminated user who's still enabled is a mismatch, so that record would reopen. One read is older than the change, so it waits. And the empty one is skipped. A day later, the grace period has run out, so that stale read becomes a mismatch too. The business rule's own tests confirm that evidence alone isn't enough, and neither is the verifier alone. Before this chapter, the client could only run against a live instance and tenant, so its decisions were visible only in mocked unit tests.

## Slide 8 — G6: requirement, evidence, availability, rollback

On the federal side, change control calls for the evidence attachment and hash on every closed record. Control verification calls for the re-read result and its time. Continuous monitoring calls for counts of closed and reopened records each period. Audit record generation calls for the verifier account's audit trail. To validate, the kit's tests prove that a dry run writes nothing, that a match closes, that a mismatch reopens, and that a stale read waits. On a live system, a person's close should land in awaiting verification, and only the client should close it, once the account matches. The re-read uses SailPoint's account and search A P I's and Graph's users endpoint. GCC High uses its own Graph host. Until the client runs on a schedule, the verifier runs it by hand once a day. To roll back, disable the business rule, though closures lose their evidence while it's off.

## Slide 9 — G7: the tempo, the five measures, the schedules

Once the loop is running, it follows the Federal Modernization Workbook's Book 13's tempo. A P1 halts work. P2 has one hour, P3 has a day, and P4 has three days. These are the program's windows, not federal ones. Schedule the drift reconciliation and the re-read client, and keep their outputs with the date and the checker version. Report five measures to the governance board: detection coverage, how well windows are kept, the escalation rate, the share of findings closed by machine, and the number of declared exceptions. Together they show whether the loop is closing on machines, inside its windows, or leaning on exceptions. Export the evidence nightly. That's planned for the kit's second pass, and the workbook already builds the ServiceNow half. Review each declared exception at its end date, and each autonomous class every quarter. These measures come from Book 13's tenth chapter, and they're what leadership reads to see whether the loop is actually working.

## Slide 10 — G7: the identity fixes, routed through the loop

The tempo gate also routes the everyday identity fixes through the loop. Most of this mapping is the program's inference. A wrong fact in HR gets corrected in HR, and SailPoint picks it up on its next read, since it can't write HR's attributes back. A late personnel action shows up as a lifecycle-state change, and the leaver state disables the account and its sessions. An urgent leaver that HR hasn't entered yet runs the same leaver sequence through an emergency change. A write made outside the pipeline is caught by native change detection. SailPoint restores the value, and the writer's access gets reviewed. An account that matches nobody gets correlated to a person or disabled. A rule that grants the wrong access is changed through a normal change. And a credential that outlives the person is outside both products. It's handled by the card system and the certificate platform.

## Slide 11 — G7 in code: evidence records and the hash chain

The workbook's seventh chapter reads closed findings back out of ServiceNow, using a read-only role, and writes one Book 13 evidence record for each. Approval, executing identity and what ran are left empty, each with its reason, because the first pass doesn't actuate. Four checks run on every record. Does the evidence still match its hash? Is there evidence at all? Did the intended state match? And did it close inside its window? Five fictional records come out with two of three closed on time. Three have problems: one closed late, one had its evidence edited after closing, and one was closed with a note that just says done. Book 13 calls that prose, not evidence. Each line carries the hash of the line before it, so the ISSO's verifier catches a removed record. The package can show tampering, but it isn't signed. A later month continues the chain from the previous month's head, so the packages link from one period to the next.

## Slide 12 — G7: requirement, evidence, availability, rollback

On the federal side, continuous monitoring calls for the scheduled run outputs and the five measures. Risk response calls for window adherence and the overdue list. Plans of action call for the exception register. Audit review calls for the monthly evidence package and its review. To validate, the evidence export and the drift comparison are automated, but the five measures aren't yet. The manual part is a month of scheduled runs with their outputs kept, the measures reported once, and the first monthly package accepted by the ISSO. This gate uses nothing beyond the earlier gates. Until the export exists, build the monthly package by hand, from a ServiceNow report and a SailPoint event search. And forward Entra's audit logs to the SIEM, since Entra only keeps them for thirty days. To roll back, stop the schedules. The records stay.

## Slide 13 — The evidence record on ServiceNow and SailPoint

Every lane writes the same record, and this slide shows where each field comes from on these products. Origin is the SailPoint trigger, the reconciliation finding, or the catalog request. Owner and clock come from the ServiceNow assignment, the severity and the due date. Approval is ServiceNow's for low-authority tasks, SailPoint's for owner-governed access, and the authorizing official's acceptance for autonomous classes. The executing identity is the connector's or the spoke's service principal, or a person's PIM activation. What ran is the provisioning event, the workflow version, or the session recording. The result is the re-read evidence. And closure is the closed record, with its hash and attachment. The mapping is the program's. The authorizing official and the assessors decide whether a control is actually satisfied. Today the workbook's export fills origin, owner, result and closure from ServiceNow. The other three wait for a later pass that actuates.

## Slide 14 — Dangers across the seven gates

Before closing, here are the dangers the guide names, each with the gate that guards against it. Closing by ticket status completes SailPoint's task with nothing checked, so the re-read rule goes on every table SailPoint writes to. With two approval systems for one class, both approve or neither does, so there's one approval system per class. Two writers for one attribute overwrite each other, which the attribute map and the writer check catch. A vendor-cloud action nobody recorded leaves the reviewed boundary, so it goes in the data-flow record. A feature outside the authorization needs written confirmation before production. A connector's M F A setting isn't a reset procedure. An integration identity with broad write rights is a back door, so it gets certificates, two owners, and a review. And an exception that never ends needs an end date and a review. Most of these come down to a decision made early, in gates one and two, and enforced later by the re-read and the reviews.

## Slide 15 — From Draft to Proved, and where to go next

The guide is still a draft. To move it to proved, build gates three to six in a ServiceNow developer instance and a SailPoint sandbox, run the kit's lab items, and record the evidence. Some questions are still open. Is the full feature set available in SailPoint's FedRAMP environment, and what is its A P I domain? Are the apps in ServiceNow's government store? And does the Entra spoke work in GCC High? To build the code, use the developer workbook, Building Ticket-to-Machine. It has eight chapters, each with labs that run on a laptop. To learn the material in order, use the learning path for Ticket-to-Machine on ServiceNow and SailPoint. For the reasons behind it, see Book 13 and Book 15. The loop, closed, looks like this. The ticket authorizes a machine, the machine acts under a service identity, and only a re-read closes the ticket.
