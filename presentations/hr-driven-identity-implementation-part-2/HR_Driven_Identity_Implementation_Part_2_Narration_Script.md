# Companion guide — HR-Driven Identity — Implementation, Part 2 — narration script (practice copy)

## Slide 1 — Part 2: Access, credentials, separation and drift

Welcome to Part 2 of the implementation series for HR-driven identity. Part 1 named one writer for every account state, brought employees and contractors in from their sources, and got joiners ready on day one. Part 2 covers the last four gates. First, access assigned from HR attributes, with a review of what a move leaves behind. Then PIV and CAC credentials tied to HR events. Then separations, timed and proven from the logs. And finally drift, metrics and the evidence an ISSO files. The format is the same as Part 1. Each gate gets its steps, the workbook's lab commands, the federal requirement and evidence, availability in GCC and GCC High, an interim path, and a rollback. Design guidance is labeled, and the code is tested against fixtures, not a live tenant.

## Slide 2 — G4–G7 on one page: done when, proved by, rollback

Here are Part 2's four gates on one page. The access gate is done when department access is assigned automatically, the supervisor HR names approves requests, and anything left over after a move gets reviewed. The credentials gate is done when every card issuer is trusted with a revocation list, and cards are issued and revoked by HR and contractor events. The separation gate is done when a leaver's access is blocked first, credentials and devices are revoked in parallel, and the account is deleted last, with the timing measured. The drift gate is done when drift is found and fixed at its source, and the metrics are reported on the monitoring cadence. Each gate has its own rollback, except the last, which is a standing loop. Together they finish the track. Every entitlement traces back to a rule and a record, and every separation blocks in time and leaves evidence.

## Slide 3 — G4: department packages by automatic assignment

Dynamic groups carry access that a rule can decide on its own. Access packages carry what a rule can't, with approvals and reviews. Department packages are assigned automatically. A policy gives the package to everyone who matches a rule on user attributes, and takes it away when they stop matching. Each policy covers up to fifteen thousand users. Write the rules on the coded attributes HR owns. Keep one automatic policy per package. If a user matches two policies, or moves between them, they can lose access. Each policy also creates a hidden dynamic group, so leave it alone. One date matters. From November 3, 2026, any policy whose rule uses group membership is quarantined, and it stops adding or removing anyone. Microsoft publishes a read-only script that finds them, so run it now. Finally, a policy can keep access for a grace period after someone moves. Use that for standard access, and give privileged access no grace period.

## Slide 4 — G4: approvals, the mover's residual, and privilege

Next, decide who approves, what happens when someone moves, and where privilege goes. Requests go to the manager as approver, with a fallback for anyone without one. That makes the supervisor HR names the one who approves. When someone changes organization, the mover workflow removes the old department's packages and requests the new one. Then it starts a review of everything the person holds outside packages. That leftover access is the residual, and the time from transfer to review is the metric for personnel transfer. Privileged access stays out of rules altogether. HR attributes decide who may request eligibility, and the role itself is activated through PIM. And treat a reorganization as a mass move. Rehearse it, let the execution limit quarantine it, and release it only after you've checked it against HR.

## Slide 5 — G4 in code: lint the policies, list a mover's residual

The workbook's fourth chapter keeps the policies as reviewed files. Run against five broken ones, its lint catches a rule built on group membership, and two policies on one package that the same employees both match. It also catches a policy that adds but never removes, an approval with no fallback, and privileged access assigned by a rule. A separate scan reads the tenant's existing policies and finds the one still using group membership. Then the residual. A fictional employee moved departments in October. For each package they hold, the code checks the rule against their new attributes. The old baseline goes after the grace period, and the new one stays. Three items go to the manager of record: one requested package, and two groups held outside packages. One finding stands out: the review is still open thirteen days after the move, past the program's ten.

## Slide 6 — G4: requirement, evidence, availability, rollback

On the federal side, account management, least privilege and separation of duties call for the policy exports, with their rules and the separation-of-duties settings. Personnel transfer calls for the transfer-to-review times and the review decisions. Account review results must be exported before Entra's thirty-day history closes. CISA's baseline requires highly privileged roles to come only through a privileged access system, so the ISSO shows PIM eligibility through packages, and no standing role assigned by a rule. To validate, compare membership before and after a test move. No kit check reads the policies yet, so keep the export and a clean group-membership scan. Most features are available in Azure Government, with one gap. Administrative units with dynamic membership aren't available there, so GCC High uses assigned units, filled by a scheduled job. To roll back, remove the policy, but keep the old dynamic group until the package has run clean for a full cycle.

## Slide 7 — G5: trust the issuing CAs, each with a CRL

A PIV card without a binding to the account is just a badge. The binding names one specific certificate, so any reissue changes it. The first step is to trust each issuing authority, and give each one a revocation list. Without a list, Entra doesn't check revocation at all. The limits depend on the cloud. For interactive sign-in, a list can be twenty megabytes in GCC and forty-five in GCC High, and it must download within ten seconds. If Entra can't download a configured list, certificate sign-in fails for every certificate from that authority. So host the lists on highly available endpoints, ideally over HTTP. Next, raise PIV certificates to multifactor strength by issuer or policy, and require phishing-resistant strength in Conditional Access.

## Slide 8 — G5: issuance and revocation follow HR events

The rest of this gate ties the card's life to the person's. No card is requested without a joiner record and a sponsor. The card system writes the binding when the card is issued, and removes it when the card is revoked. Once the binding lands, the temporary pass from gate three isn't needed anymore, and the proofing level is recorded per person. The card system's events flow back in, keyed on the person key. Those events are termination, revocation, suspension and expiry, and the same event can mean two different things. For a contractor, a terminated or expired card ends the engagement. For an employee, it's credential drift, not a separation, because only HR decides when an employee leaves. And a legal name change rewrites the binding. The guide is open that the card system's interface, and the contractor PIV path, are still pending proof.

## Slide 9 — G5 in code: measure the CRLs, check the settings

The workbook's fifth chapter does two things. First, it measures each revocation list once, recording its size, its download time, and any error. A failed download is the finding, so it's recorded, not raised. Then it checks the tenant's settings against the limits for a named cloud. The fictional tenant tells a story. One certificate authority was renewed, so the card program's expected authority is gone from the trust store. The renewed list is eighteen and a half million bytes, takes over eleven seconds to download, and is served over HTTPS. The slow download fails in every cloud. The policy mapping points at the wrong PIV identifier. And the phishing-resistant policy is still in report-only mode. Run the same check for GCC High and one warning disappears. That size is close to the commercial limit, but well under Azure Government's.

## Slide 10 — G5: requirement, evidence, availability, rollback

On the federal side, accepting PIV credentials and public-key authentication call for the certificate sign-in configuration export: the trusted authorities, the revocation settings, the binding rules, and the required affinity. CISA's baseline requires phishing-resistant MFA for all users and for privileged roles, so keep the ScubaGear report. FIPS 201 allows issuance only once a proper authority authorizes it, so the card system's records are joined to the HR or contractor event. To validate, one kit check lists card holders with no binding, or only weak ones. No kit check reads the configuration, so the evidence includes a revoked test certificate being refused at sign-in. Everything here is available in both clouds, though the size limits differ. Until there's a clear way to write the binding after Active Directory retires, keep it in AD and sync it. To roll back, restore the bindings from the card system, never by editing the directory.

## Slide 11 — G6: block first, revoke in parallel, dispose last

The separation gate puts the leaver in the Federal Modernization Workbook's Book 03's order and then proves the timing. Disable the account and revoke its sessions first. Then one custom task starts the device retire and the card revocation together, and waits for both to report. That wait can run from thirty minutes to three hours, and if it times out, it goes to a high-priority exception, not a retry loop. Then come the removals, and a read-back to confirm the block took. A disabled account with live sessions is an incident. Deletion comes last, in a separate workflow, after the devices are retired. Set the leave time late in the day, and remember the schedule is part of the time allowed. An emergency means an immediate out-of-band block, then the same sequence on demand, behind approval. A separation entered more than three days late misses the trigger, so run it by hand. Privileged leavers need their own path.

## Slide 12 — G6 in code: separation timing from the logs

The workbook's sixth chapter measures each separation from the audit logs. A leaver counts as blocked once both the disable and the session revocation are recorded. They count as fully revoked when the card and the devices are done too. Nine fictional separations are measured. The typical block lands in about fifteen minutes. But the slowest ten percent take over five hours, against a sample limit of four, and full revocation takes far longer. Three stories stand out. One leaver was blocked late, and that person's card was revoked twenty-three hours after notice, past the eighteen FIPS allows. Another separation was entered almost a week late, and its only disable failed, so that person was never blocked at all. And the pipeline re-enabled a third leaver two days after the disable. These limits are only samples. The agency sets the real period, and sets it together with the schedule.

## Slide 13 — G6: requirement, evidence, availability, rollback

On the federal side, personnel termination and account disabling call for both measured times for each leaver, along with the workflow run, the device actions, and the card revocation with the list that published it. Contractors add the time from end date to block. FIPS 201 says a card that can't be collected must be revoked within eighteen hours of notice, so keep both timestamps. Emergency disables are logged as changes. To validate, run a full pay period with no missed leavers, blocks within the limit, and every exception closed. Security owns this gate. Lifecycle Workflows and PIM are available in Azure Government. The guide infers that a GCC tenant's Logic App sits in a commercial Azure subscription. Until the extensions exist, use a leaver checklist with a named owner for each row. To roll back a cancelled separation, re-enable from the corrected record. A deleted cloud user can be restored for thirty days.

## Slide 14 — G7: lifecycle drift, six metrics, the sole source

The last gate keeps the record true. Run the lifecycle drift checks: missing identity, stale access, orphan accounts, unauthorized writes, and credential drift for employees and contractors. Fix each finding at its source, and let the fix flow back through the pipeline, never as a direct directory edit. Report six metrics on the monitoring cadence. Prove HR is the only source, using seven days of logs, then close the ticket path. And keep the evidence outside the directory, because it has to outlive the accounts. The table shows the workbook's lab run. Blocking, revocation, joiner readiness, correlation coverage, and the share of access granted by rules are all out of bounds on this fixture. Transfer-to-review isn't measured, because a review is still open. A metric with no input is reported as not measured, never as zero. And the thresholds are for the agency to choose.

## Slide 15 — G7 in code: package, chain, period; the evidence

The workbook's seventh chapter makes this gate one run, plus a chain of evidence packages. The run reads the earlier labs' outputs, checking each one against its own manifest. It insists on knowing whether it's a fixture or a tenant run, so a lab can't pass for production. The evidence tool packages each run with checksums, chained to the one before. Then the period report verifies the whole chain. Here the chain is unbroken and nothing is missing, but twenty findings are still open, so the period isn't complete. On the federal side, continuous monitoring calls for the six metrics per period. Audit review and retention call for the log export, findings closed at the source, and retention set to the records schedule. CISA's continuous reporting calls for ScubaGear results. The kit checks run on the drift cadence, and the CISO owns it. There's no rollback here, because this is the loop that keeps running.

## Slide 16 — One evidence file per population, and what's next

Put together, the gates make one evidence file for each population. It holds the register, the sources and the reconciliations. It holds the workflows and their run history, and the access policies and reviews. It holds the certificate configuration and the card records. It holds the separation times and their exceptions. And it holds the drift findings, the metrics and the sole-source proof. File every kit run with its date, tenant and check version. To build the code for these four gates, use the developer workbook, Building HR-Driven Identity, chapters four to seven, each with its labs. For the design, see Book 03. For the attributes these gates read, see the attribute-driven migration implementation guide. To learn it all in order, use the learning path for HR-driven identity: seven modules, one per gate, each with a fixture lab and a knowledge check. The pipeline makes the account exist. These seven gates make the HR record decide what happens to it, and they leave the evidence that it did.
