# Module 5: The pipeline and the separate channel {.unnumbered}

*Part of the [Help Desk Automation learning path](index.md). Book 15, Chapter 12, tasks 1, 2, 4 and 5. Workbook [Chapter 05](../../project-plans/developer-workbooks/help-desk-automation/05-the-request-pipeline-and-the-one-time-secret.md). About 50 minutes.*

## Introduction (3 minutes)

Every five minutes, a scheduled task on the platform host, under its own gMSA, works the queue Module 4 fills. It believes SailPoint, not the ticket: it re-reads each approval by its access request id, the re-read rule the [Ticket-to-Machine learning path's Module 6](../ticket-to-machine/06-actuation-and-the-re-read.md) teaches, applied to the approval. It acts only through the kit's scripts, and when a task produces a secret (a temporary password or a Temporary Access Pass) it hands it to one place: a restricted field the verifying agent reads to the person on a channel the request didn't come in on.

**The federal requirement.**

| Requirement | KSI | Evidence |
|---|---|---|
| AC-2; AC-6; CM-3: a typed change only after approval, through Module 1's checks | KSI-CMT-LMC; KSI-IAM-JIT | `evidence.json` and the plan |
| IA-5; AC-2: a password reset that forces a change at next sign-in | KSI-IAM-JIT | `evidence.json` |
| IA-5; IA-2; IA-12; SI-4: an authenticator reset with a single-use, 60-minute pass | KSI-IAM-JIT; KSI-IAM-SUS | `evidence.json` |
| AC-2; AC-6; IA-5: a cloud account from an approved profile | KSI-IAM-AAM | `evidence.json` |

The pipeline's records support these controls; the assessor decides them *(design guidance for the KSI mapping)*.

## Learning objectives (1 minute)

After this module, you'll be able to:

- say why the pipeline ran, left waiting or refused each item, by rule;
- name the one place a one-time secret goes, and three it never goes;
- show that the pipeline won't run as the assessment gMSA;
- state the open question about the pipeline's SailPoint token.

## Knowledge check (5 minutes)

1. The ticket says "approved", but SailPoint shows the request `REJECTED`. What does the pipeline do?
    a. Runs it: the ticket says approved
    b. Refuses it (HT-RQ-02): it re-reads SailPoint, not the ticket
    c. Waits
    d. Asks the agent
2. A user who holds a directory role asks for an authenticator reset. What happens?
    a. The pipeline resets it with the worker app
    b. HT-RQ-04: it goes to a Privileged Authentication Administrator, by hand
    c. It waits for a second approval
    d. It is refused as invalid
3. Where does a one-time secret go?
    a. A work note
    b. The evidence file, encrypted
    c. Only the restricted field the verifying agent reads, cleared after two hours
    d. An email to the requester
4. Why does the pipeline never run as `gmsa-fmpassess$`?
    a. That gMSA has no password
    b. The pipeline writes; keeping it apart means a compromise of a read-only job can't change users
    c. Task Scheduler forbids it
    d. The assessment gMSA is for SQL Server only
5. What is still open about the pipeline's SailPoint sign-in?
    a. Nothing
    b. Whether a client-credentials token can read the access request status, which SailPoint's specification lists under user authentication
    c. The token endpoint's address
    d. Whether SailPoint is FedRAMP authorized
