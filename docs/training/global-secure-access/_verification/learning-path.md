# Verification — Learning path: Global Secure Access as the Identity-Aware Network

Files: `docs/training/global-secure-access/index.md` and its six modules, `01-decide-design-and-log-first.md` to `06-rings-rollback-and-the-evidence-package.md`.
Example code: none. The guide has no kit in `examples/` and no developer workbook yet.
Verified: 2026-11-13

Method:
- The path adds no new facts. Every fact a module states is carried by link from the Global Secure Access implementation guide (`docs/books/guides/global-secure-access-implementation.md`, draft of November 11, 2026, review pending) or the book chapters it links (Book 09, Chapters 03 and 05; Book 04, Chapter 07 and Appendix C; Book 11, Chapter 10; Book 12, Chapter 03), and relies on those pages' verification logs and footnotes (Microsoft Learn's Global Secure Access, Microsoft Graph and Microsoft Entra pages read on November 11, 2026; CISA's TIC 3.0 Remote User Use Case; fedramp.gov's KSI pages). New writing is limited to the path, the module framing, objectives, unit glue, lab framing, knowledge-check questions and time estimates.
- No Learn page was read again for the path beyond what the guide's verification log records for November 11, 2026.
- Each knowledge-check answer links the section that teaches it; the answer was checked against that section's text.
- **There is no Lab 1.** With no kit and no fixtures, nothing in the path runs without a tenant. Each module's lab is a Lab 2: the guide's own commands and Validate steps, in the guide's run order, in a test tenant. The labs weren't run by the authors, as each page says. Every expected result is the one the guide (or the Learn page it cites) states; none is captured output.
- Lab commands taken verbatim from the guide: Steps 1.1, 2.1, 3.1, 3 Validate, 4.1, 4.3, 4 Validate, 5.1 to 5.4, 5.6, 5 Validate, 6.1 to 6.5, 6 Validate, 7.1 to 7.3, 7 Validate, 8.1, 8.2, 8 Validate, 9 Validate, 10.2, 10 Validate (`klist`), 12.1 and 12 Validate.
- Lab commands the path adds, each built from the guide's own request pattern or a standard cmdlet, and each named here so a reviewer can check it:
  - Module 1: `New-Item`, `Set-Location`, `Import-Csv`, `Get-Content` and `Get-ChildItem` to make the lab folder and show the guide's output files; the bash `cat` of the diagnostic setting GET.
  - Module 2: writing the device usage summary and the signaling GET to files (`ConvertTo-Json`, `Out-File`), as the guide's Step 1.1 and 8.1 do for theirs; `Connect-MgGraph` with `NetworkAccessPolicy.Read.All`, the permission the guide's footnote for `getDeviceUsageSummary` lists.
  - Module 3: `PATCH` of the compliant network policy's `state` to `enabled` and back to `enabledForReportingButNotEnforced` (the guide's Step 7 How-section names both as the enforcement and the rollback); the lab shortens the 10 business days and says so.
  - Module 4: the GETs of connectors and connector groups (URIs from the guide's Step 2.1); Step 10.1 written out as Steps 6.1 to 6.4 with the administrative host's values, as the guide instructs; Step 10.2's policy scoped to the privileged test group rather than the pilot group, because 10.1 assigns the administrative app only to the privileged group; `Test-NetConnection` for the guide's reachable and unreachable port test (the guide gives no command); a `SigninLogs` query on the two `NET-PA-` policies, in the pattern of the guide's Step 7 report-only query.
  - Module 5: the GETs of filtering profiles and policies (URIs from Step 2.1); `Get-NetFirewallRule` to show Step 5.6's rule.
  - Module 6: the policy and profile listings; `PATCH` of each `NET-` policy to report-only and the security profile's policy to `disabled` (the guide's Rollback and Step 5 rollback); `{"networkPacketTaggingStatus":"disabled"}` (Step 8 rollback); `{"state":"disabled"}` on each profile (Step 4 rollback); `{"signalingStatus":"disabled"}` (the guide's Rollback, last line); `DELETE` of the test Conditional Access policies (v1.0), applications (v1.0), filtering profile and filtering policy (beta), which the guide doesn't give and which follow Graph's resource paths in the guide's own URIs; `Remove-NetFirewallRule` for Step 5.6's rule; `az rest --method DELETE` on the diagnostic setting's URI from Step 12.1 (the guide's Step 12 rollback says to delete it).
- Portal steps (Intune Win32 app values, DNS over HTTPS profile, profile assignments, the TLS inspection policy removal order, client diagnostics, the four-case test) use only the names and values the guide gives; where the guide gives no click path, the step names the setting, not a path.
- Command lists at the top of each lab are generated by `scripts/generate_labs.py`, which now registers this path and reads `cmd` and `kusto` blocks as well as `bash` and `powershell` (with `REM` and `//` step comments).
- Requirements and KSIs: each module's table is the guide's "Federal requirements and KSIs, by step" rows for its steps, with the evidence from each step's How-section. Claim wording: the evidence *supports* the controls; the assessor decides them. KSIs are written as indicators for cloud service providers that the agency lines its evidence up with.
- Government cloud: GCC first, as the guide's availability table states (product-wide sentence, as of November 11, 2026); GCC High and DoD only as the guide's "not yet supported" side note and Step 1.3's compensating path. Module 4 carries the guide's statement on applications in AWS, Google Cloud and Oracle Cloud Infrastructure.
- Time estimates are the program's planning figures *(design guidance)*, not measurements.
- The guide's narrated deck (`presentations/guide-global-secure-access`, built November 13, 2026) isn't on the Watch page yet; the path links its narration script and names the slides each module builds on. The module decks are planned as a separate change.
