# Module 3: Proving the move {.unnumbered}

*Part of the [Application Modernization learning path](index.md). Book 18, [Chapter 04](../../books/b18-application-modernization/04-moving-the-data.md). Workbook [Chapter 03](../../project-plans/developer-workbooks/application-modernization/03-proving-the-move.md). About 50 minutes.*

## Introduction (3 minutes)

A passing report is only worth what its checks can catch. In this module you read the reports the fixture runs wrote: a clean load, a changed amount, a deleted row, a truncated name, and a delta after the legacy system kept changing, and you see which check fires for each and which key it names.

**The federal requirement.** The output of this module's lab is evidence for these controls; your organization still sets their parameters, policy and procedures, and the assessor decides whether each is satisfied. The workbook chapter's [Federal requirements and evidence](../../project-plans/developer-workbooks/application-modernization/03-proving-the-move.md#federal-requirements-and-evidence) table has a row for each lab step, and the kit's `config/requirements.json` holds the mapping.

| Requirement | KSI | Evidence |
|---|---|---|
| CM-3(2), Testing, Validation, and Documentation of Changes | KSI-CMT-VTD | The validation reports, with the keys any failure names |
| CM-4(2), Verification of Controls | KSI-CMT-VTD | The damage reports: the checks shown to fire |

KSIs are FedRAMP 20x indicators for cloud service providers. The agency lines this evidence up with what its providers report against them; it doesn't report KSIs itself. Which file supports which indicator is the program's mapping *(design guidance)*.

## Learning objectives (1 minute)

After this module, you'll be able to:

- say what each of the three checks proves and what it can't;
- find the table, check and key behind a failure;
- run a delta from the previous report's watermark, and name the two things a delta can't see;
- explain why the report holds keys, counts and digests, never rows.

1. **Run the lab reports:** `-Dlab.dir` tells them where to go: this run's folder.

    ```powershell

    Import-Module ./powershell/AppModernization/AppModernization.psm1
    ```

    Once Maven has its dependencies, this prints nothing: Maven is quiet when the tests pass. The first run also downloads Maven, the PostgreSQL binaries and the test libraries, and prints their progress. The run takes a few minutes: the tests start a real PostgreSQL 18 server.

2. **Read the clean load's checks:**

    ```powershell
    Get-AmValidationSummary -Path "$Run\lab\load-full.json" | Format-Table Table, Check, Passed, Detail
    ```

    Expected output:

    ```text
    Table       Check           Passed Detail
    -----       -----           ------ ------
    applicant   row_count         True source 20, target 20
    applicant   checksum_sha256   True
    applicant   aggregate         True
    case_record row_count         True source 50, target 50
    case_record checksum_sha256   True
    case_record aggregate         True
    ```

    Six checks, all passed: three for each table.

3. **Change one amount by a cent, and see who notices:**

    ```powershell
    Get-AmValidationSummary -Path "$Run\lab\damage-amount.json" | Where-Object { -not $_.Passed } | Format-Table Table, Check, Detail
    ```

    Expected output:

    ```text
    Table       Check           Detail
    -----       -----           ------
    case_record checksum_sha256 differ 1 [C-000010]; missing from target 0; extra in target 0
    case_record aggregate
    ```

    The checksum names `C-000010`; the aggregate's totals disagree; the row count doesn't notice.

4. **Delete one row:**

    ```powershell
    Get-AmValidationSummary -Path "$Run\lab\damage-delete.json" | Where-Object { -not $_.Passed } | Format-Table Table, Check, Detail
    ```

    Expected output:

    ```text
    Table       Check           Detail
    -----       -----           ------
    case_record row_count       source 50, target 49
    case_record checksum_sha256 differ 0; missing from target 1 [C-000020]; extra in target 0
    case_record aggregate
    ```

    All three fail, and the checksum says `C-000020` is missing from the target.

5. **Truncate one name:**

    ```powershell
    Get-AmValidationSummary -Path "$Run\lab\damage-truncate.json" | Where-Object { -not $_.Passed } | Format-Table Table, Check, Detail
    ```

    Expected output:

    ```text
    Table     Check           Detail
    -----     -----           ------
    applicant checksum_sha256 differ 1 [7]; missing from target 0; extra in target 0
    ```

    Only the checksum fails, on applicant `7`: counts and sums can't see text. This is why the checksum exists.

6. **Follow the coexistence period:**

    ```powershell
    foreach ($f in 'delta-0-full', 'delta-1-drift', 'delta-2-after') { $r = Read-AmJson -Path "$Run\lab\$f.json"; [pscustomobject]@{ Report = $f; Mode = $r.mode; Since = $r.since; Cases = $r.loaded.case_record; Passed = $r.passed; Failures = $r.failures -join ' '; NextWatermark = $r.nextWatermark } }
    ```

    Expected output:

    ```text
    Report        : delta-0-full
    Mode          : full
    Since         :
    Cases         : 50
    Passed        : True
    Failures      :
    NextWatermark : 2026-09-27T02:02:38.032084Z

    Report        : delta-1-drift
    Mode          : validate-only
    Since         :
    Cases         :
    Passed        : False
    Failures      : applicant/row_count applicant/checksum_sha256 applicant/aggregate case_record/row_count

    NextWatermark : 2026-10-16T08:00:00Z

    Mode          : delta

    Cases         : 4
    Passed        : True
    Failures      :
    NextWatermark : 2026-10-16T08:00:00Z
    ```

    The drift shows before the delta runs. The delta loads four cases: the two changed, the new one, and the boundary row at the watermark itself, because the bound is inclusive and every write is an upsert.

## Knowledge check (5 minutes)

1. One applicant's name is truncated in the target. Which check fails?
    a. Row count
    b. Checksum only
    c. Aggregate only
    d. All three
2. Why does the kit add aggregates when the checksum already compares every field?
    a. The checksum shares the transform with the load, so a wrong rule passes it; aggregates are computed without the transform
    b. Aggregates are faster
    c. The checksum can't read amounts
    d. Aggregates name the key
3. A delta runs from the last watermark. Which change can it miss?
    a. A changed amount
    b. A new case
    c. A row deleted in the source
    d. A changed status
4. The delta loaded four cases, but only three changed. Why?
    a. A bug
    b. The bound is inclusive, so the row at the watermark is loaded again, harmlessly, as an upsert
    c. An applicant changed
