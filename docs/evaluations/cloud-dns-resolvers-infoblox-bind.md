# Cloud DNS on AWS, Azure and Oracle Cloud: Native Resolvers, Infoblox and BIND {.unnumbered}

[Book 08 — DNS, DHCP & IPAM](../books/b08-ddi/index.md) asks for one authoritative policy and state plane that every other DNS system consumes. Zones, forwarding rules, IPAM data and security policy live in one place, and cloud DNS services are "synchronized targets or forwarding destinations rather than independently authored sources" ([Chapter 08](../books/b08-ddi/08-reference-architecture.md#moving-from-per-cloud-local-syncs-to-a-unified-control-plane)). The warning is about authoring copies in every silo, which produces split-brain answers, names that work in one cloud but not another, and uneven Protective DNS and logging.

This page fills gaps in how the workbook covers that design in the clouds:

- **Infoblox with Azure and AWS is covered.** Book 08 [Chapter 07](../books/b08-ddi/07-cloud-private-endpoints-and-ipam.md) covers Azure private endpoints, the Azure DNS Private Resolver in a hub-and-spoke network, the hybrid resolution patterns and AWS VPC IPAM. [Chapter 08](../books/b08-ddi/08-reference-architecture.md) sets the per-cloud conditional forwarding (Decision 3) and the order of the forwarding chain (Decision 2). The research explainer [Trinzic Alone, or Trinzic Plus Cloud DDI?](trinzic-multicloud-ddi.md) sets out the three Infoblox options: vNIOS in each cloud (A), Universal DDI writing to the cloud DNS services (B), and the Grid alongside native cloud DNS with two-way forwarding (C).
- **The Route 53 Resolver is covered more thinly than Azure's.** Book 08 names its endpoints, rules and rule sharing, but doesn't lay out how they work or what differs in AWS GovCloud (US), service by service. Part 1 does.
- **Oracle Cloud is covered at the comparison level.** Book 08 Chapter 07 compares Oracle Cloud Infrastructure's private DNS with the other platforms, and notes that the HR platform runs on Oracle Cloud. Part 1 adds its resolver in the same depth as the other two, with the US Government Cloud and FedRAMP scope.
- **BIND in AWS or Azure isn't covered.** The only mention in the books is [Book 12, Chapter 05](../books/b12-security-operations/05-from-log-warehouse-to-detection.md), where Microsoft's ASIM DNS parser for Infoblox NIOS also handles BIND logs. Parts 2 to 4 cover it.

## The answer in brief

**Use the native resolver as the forwarding bridge in each cloud, and keep the policy in the DDI plane.** The Route 53 VPC Resolver and the Azure DNS Private Resolver are managed, zone-redundant forwarding services that both providers recommend over DNS servers on virtual machines.[^cdns-az-hybrid][^cdns-r53-what] Oracle Cloud gives every VCN a dedicated resolver with listening and forwarding endpoints that does the same job.[^cdns-oci-pdns] None of the three is an authority for the agency's own namespaces, and neither AWS nor Azure signs private zones.[^cdns-r53-sign][^cdns-az-dnssec] Oracle Cloud is the one with no native DNS-layer filter for private DNS, so in a VCN the agency's policy applies only if queries are forwarded to agency resolvers.[^cdns-oci-tm] Book 08's Decision 3 already treats their inbound endpoints as forwarding destinations.

**Run your own DNS servers in a cloud only for a stated reason** *(design guidance)*: the native resolver can't do something the agency needs, such as answering an NS delegation, holding the agency's response policy zones, logging at the agency resolver as M-22-09 expects, or serving as a bridge during AD DNS retirement. Infoblox vNIOS is the choice when the Grid already runs the agency's DNS, because it joins the same Grid and gets its policy from the Grid Master. BIND is the choice when there is no Grid member to place there, or a tool needs BIND itself. Either way it consumes the policy plane; it doesn't become a second one.

**Additional BIND servers in AWS align with Book 08 when they are forwarders or resolvers under central configuration, logged to the SOC, owned and with a reason. Separately authored zones, or servers edited by hand, are the pattern Book 08 tells agencies to move away from.**

| BIND in AWS **aligns** when it is… | BIND in AWS **creates a silo** when it… |
|---|---|
| A resolver or forwarder whose configuration comes from the policy plane: cloud names to Route 53 Resolver inbound endpoints, on-premises names back through outbound rules, its addresses in IPAM, its queries logged to the SOC (Decision 3 expects the same forwarding rules on every resolver) | Hosts zones authored separately from the DDI platform: a new source of truth and a new split-brain |
| A deliberate bridge with an owner and an end date, for example during AD DNS retirement, or for a need the Route 53 Resolver can't meet | Is edited by hand: no baseline, no change record, drift |
| Configured from Git and applied by automation, so the repository is the CM-2 baseline and the pull request is the CM-3 change record ([Ansible guide](../books/guides/ansible-configuration-automation.md#evidence-to-the-program)) | Skips the shared policy (Protective DNS, DNSSEC validation, query logging), so resolution in AWS is less protected than on premises |
| Hardened, patched, inventoried and owned like any other DNS server | Duplicates the Route 53 Resolver with no stated reason: more servers to harden and patch (CM-6, SI-2) for nothing |

## Part 1 — The native resolvers

### AWS: the Route 53 VPC Resolver

**The name.** AWS renamed the Route 53 Resolver the **Route 53 VPC Resolver** when it introduced Route 53 Global Resolver.[^cdns-r53-what] The VPC User Guide, the API, the GovCloud User Guide and AWS's FedRAMP page still use the older name, so both appear in runbooks. This page says "VPC Resolver" except where it quotes.

**What it is.** Every VPC reaches the VPC Resolver at the VPC's base address plus two (VPC+2), and at `169.254.169.253`. It answers the VPC's own EC2 names and records in private hosted zones associated with the VPC, and recurses for public names.[^cdns-r53-what][^cdns-vpc-dns] It only answers recursive queries, and network ACLs and security groups can't filter traffic to it.[^cdns-vpc-dns] Each network interface may send 1,024 packets per second to link-local services, a total that covers DNS, instance metadata, time and Windows licensing; the quota can't be raised, and traffic over it is rejected.[^cdns-vpc-dns] That quota matters to any DNS server on EC2 that forwards to VPC+2 (Part 3).

| Component | What it does | Limits and points to know |
|---|---|---|
| **Inbound endpoint** | Lets resolvers on the agency network, or in other clouds, forward queries into a VPC; they get the answers that VPC sees, private hosted zones included. A second type, the delegation inbound endpoint, answers NS delegations[^cdns-r53-hybrid] | At least two IP addresses in different Availability Zones (six by default); each address handles up to 10,000 UDP queries per second, but as few as 1,500 for inbound queries under connection tracking or behind a Network Load Balancer; Do53, DoH and **DoH-FIPS** (FIPS 140-2), the last for inbound forward endpoints only[^cdns-r53-endpoints][^cdns-r53-quotas] |
| **Outbound endpoint** | Sends queries that match a forwarding rule from the VPC to the agency's resolvers[^cdns-r53-hybrid] | Do53 and DoH only, so no FIPS option outbound; needs Direct Connect, VPN or a NAT gateway; sharing a rule shares its outbound endpoint too[^cdns-r53-endpoints] |
| **Forwarding rules** (conditional forwarding) | One rule per domain, with target IP addresses; the most specific matching rule wins, and a rule overrides a private hosted zone of the same name[^cdns-r53-rules][^cdns-r53-phz] | 1,000 rules per Region; 6 target addresses per rule; a "." rule forwards almost everything[^cdns-r53-quotas][^cdns-r53-rules] |
| **System rules** | Carve a subdomain back out of a forwarding rule, so it resolves locally (forward `example.com`, keep `acme.example.com` in the VPC); AWS also creates autodefined system rules, including reverse DNS[^cdns-r53-rules] | The recursive "Internet Resolver" rule handles everything else and can't be deleted[^cdns-r53-rules-manage] |
| **Delegation rules** | Forward queries whose answers carry NS records for a delegated subdomain to the agency's resolvers[^cdns-r53-rules] | In GovCloud, see the availability table below |
| **Rule sharing** | AWS Resource Access Manager (RAM) shares rules with accounts, organizational units or the whole organization; the receiving account associates them with its VPCs but can't change or delete them[^cdns-r53-rules-manage] | Moving an account between OUs removes its associations unless the rule is also shared with the new OU[^cdns-r53-rules-manage] |
| **DNS Firewall** | Rule groups of allow, alert and block rules (block answers NODATA, NXDOMAIN or a custom override), against custom or AWS managed domain lists; the Advanced tier detects domain generation algorithms (DGA) and DNS tunneling[^cdns-r53-fw][^cdns-r53-fw-actions][^cdns-r53-fw-adv] | Filters only queries that pass through the VPC Resolver, including those arriving through inbound endpoints; fails **closed** (SERVFAIL) by default; AWS managed lists can't be downloaded or browsed[^cdns-r53-fw-how][^cdns-r53-fw-config][^cdns-r53-fw-managed] |
| **Query logging** | Logs queries from the VPC, queries through inbound and outbound endpoints, and DNS Firewall actions, to CloudWatch Logs, S3 or Firehose; fields include query name and type, response code, answer, source address and the source instance or endpoint[^cdns-r53-qlog][^cdns-r53-qlog-fields] | Logs only queries that reach the VPC Resolver, and not answers from its cache; configurations can be shared through RAM[^cdns-r53-qlog][^cdns-r53-qlog-share] |
| **Private hosted zones** | Zones answered only inside associated VPCs; same-name public and private zones give split-view DNS[^cdns-r53-phz] | Need `enableDnsHostnames` and `enableDnsSupport`; 300 VPCs per zone; cross-account association is by API only (authorize, then associate); an empty match returns NXDOMAIN, with no fallback to public DNS[^cdns-r53-phz][^cdns-r53-phz-xacct][^cdns-r53-quotas] |
| **Profiles** | Bundle private hosted zones, rules, DNS Firewall rule groups, interface endpoints and query log configurations, and share them with many VPCs and accounts through RAM[^cdns-r53-profiles] | One Profile per VPC; local VPC settings win on an exact-name tie[^cdns-r53-profiles] |
| **DNSSEC** | Validation of public signed names, enabled per VPC; signing of **public** hosted zones only, with the key-signing key in AWS KMS[^cdns-r53-validate][^cdns-r53-sign] | No signing for private hosted zones; the VPC Resolver ignores the DO and CD bits and returns no DNSSEC records and no AD bit, so a resolver behind it can't validate for itself; AWS warns enabling validation "could result in an outage"[^cdns-r53-validate][^cdns-r53-sign] |

Route 53 Global Resolver, generally available since March 2026, is a different thing: an internet-reachable anycast resolver (Do53, DoT and DoH) for authorized clients in branches and on-premises sites, which resolves private hosted zones and filters malicious domains.[^cdns-r53-global] It is listed in 30 commercial Regions and not in GovCloud.[^cdns-r53-global]

There are no separate rows for the VPC Resolver, DNS Firewall or Profiles; AWS's general rule is that "generally available features of each of the services are considered in scope" unless specifically excluded.[^cdns-aws-fedramp] The FedRAMP Marketplace lists AWS US East/West at Moderate and AWS GovCloud at High.[^cdns-fedramp-mkt] For a Moderate civilian workload, both locations therefore cover the DNS service. The Resolver features are covered by AWS's general statement, not by a row of their own, which is worth noting in the system security plan *(inference)*.

### Azure: the DNS Private Resolver and DNS resolver policy

Book 08 [Chapter 07](../books/b08-ddi/07-cloud-private-endpoints-and-ipam.md#the-azure-dns-private-resolver-in-a-hub-and-spoke-network) covers the Private Resolver's hub-and-spoke design, its subnets, limits, loop rules and an illustrative deployment. In summary, with today's limits:

| Component | What it does | Limits and points to know |
|---|---|---|
| **Inbound endpoint** | Receives queries from on-premises or other clouds and answers from private DNS zones linked to its virtual network | Its own delegated subnet; static address recommended; 5 per resolver; 10,000 queries per second each[^cdns-az-pr][^cdns-az-rulesets] |
| **Outbound endpoint and forwarding ruleset** | Sends queries for named domains to target servers; rulesets are linked to virtual networks | 1,000 rules per ruleset, 500 virtual network links, 6 targets per rule; one ruleset linked per virtual network; same region only[^cdns-az-pr][^cdns-az-limits] |
| **Platform constraints** | — | No virtual networks with encryption enabled, no IPv6-enabled subnets; one region per resolver, zone-redundant inside it[^cdns-az-pr][^cdns-az-rel] |
| **DNS resolver policy** (formerly "DNS security policy") | Filters and logs every query in a linked virtual network, public and private, with allow, block and alert rules; includes a Microsoft-managed threat intelligence list from MSRC | One policy per virtual network, same region only; logs to Log Analytics (`DNSQueryLogs`), storage or Event Hubs through diagnostic settings[^cdns-az-policy][^cdns-az-traffic] |
| **Monitoring** | Resolver and ruleset metrics (endpoint counts, queries per second) | Microsoft lists resource logs only for resolver policies, so per-query logs come from a resolver policy (or Azure Firewall's DNS proxy), not from the resolver itself *(inference from the complete list)*[^cdns-az-monitor][^cdns-az-hybrid] |
| **DNSSEC** | Public zones can be signed | The Azure-provided resolver doesn't validate DNSSEC; no Microsoft page describes signing private zones or whether the Private Resolver validates; *confirm*[^cdns-az-dnssec] |
| **Zone transfers** | — | "Azure DNS doesn't currently support zone transfers (AXFR/IXFR)," so a BIND server can't be a secondary of an Azure private zone, or the reverse[^cdns-az-faq] |

Microsoft renamed DNS security policy to **DNS resolver policy**; the URL, the price meters and the Architecture Center still use the old name.[^cdns-az-policy]

**Azure Government and FedRAMP scope.** Microsoft's audit-scope page (updated February 2026) has one **DNS** row, in scope for FedRAMP High in Azure commercial and for FedRAMP High and DoD levels in Azure Government; there is no separate row for the Private Resolver or resolver policy.[^cdns-az-fedramp] The products-by-region page doesn't show Azure Government regions in its public table, and no Learn page states the Private Resolver's or resolver policy's Azure Government availability.[^cdns-az-regions] Azure's retail price list does carry Private Resolver meters in the US Gov billing zones (effective October 1, 2024) and DNS resolver policy meters there (effective June 1, 2026).[^cdns-az-prices] A meter is a strong signal that the service is offered, but not an availability statement; confirm in the target region before design *(inference)*. The Trinzic explainer left the same point open.

### Oracle Cloud: the VCN resolver

Oracle Cloud Infrastructure (OCI) matters here because the HR platform runs on Oracle Cloud. Book 08 [Chapter 07](../books/b08-ddi/07-cloud-private-endpoints-and-ipam.md#how-each-platform-implements-private-dns) compares OCI's private DNS with the other platforms; in summary, with what this page adds:

| Component | What it does | Limits and points to know |
|---|---|---|
| **VCN resolver** | Created with each VCN and listening on `169.254.169.254`; answers from the private views attached to it, in order, then its default view, then resolver rules, then the internet; it "performs recursion to the internet and DNSSEC validation for DNSSEC-signed zones"[^cdns-oci-pdns] | A match in the sequence ends resolution, even an NXDOMAIN, so a private zone for `example.com` hides a forwarding rule for `onprem.example.com`[^cdns-oci-trouble] |
| **Private zones and views** | Private zones are grouped into views; a view can be attached to any number of resolvers, sharing private DNS data across VCNs in the same region; same-name private and public zones give split-horizon DNS[^cdns-oci-pdns] | Resolution between VCNs, in the same or another region, uses resolver endpoints over a local or remote peering gateway[^cdns-oci-pdns] |
| **Listening endpoint** | Receives queries from on-premises or other VCNs | One IP address in the subnet; security rules for UDP and TCP port 53[^cdns-oci-pdns] |
| **Forwarding endpoint and resolver rules** | Sends queries that no view answers to target servers | Two IP addresses; up to 50 rules per resolver; a rule matches a client address block, a domain (up to 10 each) or **None, which matches any query**; forward is the only action; first match wins, and an unreachable target ends processing[^cdns-oci-rules][^cdns-oci-trouble] |
| **Custom resolver** (DHCP option) | Sends a subnet's instances to up to three DNS servers of the agency's choosing, in the VCN, on premises or on the internet, instead of the VCN resolver[^cdns-oci-vcndns] | Instances on a custom resolver reach private views and rules through `169.254.169.254` only if it is in the DHCP nameserver list; otherwise it answers internet names only[^cdns-oci-trouble] |
| **DNS-layer policy** | None native: Oracle's traffic management steering policies apply only to public DNS, and no Oracle page describes a DNS firewall or response policy for the VCN resolver[^cdns-oci-tm] | — |
| **Logging** | Private resolver query and response logs through OCI Logging, with the resolution path of each query[^cdns-oci-log] | Oracle documents them for the commercial realms only[^cdns-oci-log] |
| **Resilience** | May answer from stale cache (RFC 8767) with a 30-second TTL, for up to 24 hours, when it can't resolve a name it resolved before[^cdns-oci-trouble] | No published query rate for `169.254.169.254` |

**Oracle US Government Cloud and FedRAMP scope.** Oracle's US Government Cloud (realm OC2: US Gov East in Ashburn and US Gov West in Phoenix) has a FedRAMP High authorization and DISA Impact Level 4. Its tenancies "can't subscribe to the commercial regions." Its DNS API is "for private DNS only"; public DNS isn't available in the government realms.[^cdns-oci-gov] The FedRAMP Marketplace lists **Oracle Cloud Infrastructure-Government Cloud** as FedRAMP Certified at High (JAB, October 2020); it lists no commercial OCI infrastructure offering. Oracle's SaaS has its own listings, such as **Fusion Cloud** at Moderate.[^cdns-oci-mkt] So *(inference)*:

- A Moderate system on OCI infrastructure inherits from the Government Cloud's High authorization. Commercial OCI regions have no FedRAMP listing of their own, so a federal system placed there needs its own authorization basis, which the agency must settle before design.
- Whether private resolver logging is available in the government realm isn't documented; *confirm* with Oracle.
- An agency that holds only the HR platform's SaaS service has no VCN: the HR platform is a public name, as Book 08 Chapter 07 explains, and the work is keeping agency resolvers' path to it consistent.

### How each meets on-premises DNS and the policy plane

The three resolvers meet on-premises DNS the same way, and Book 08's Decision 3 already holds the rules *(design guidance)*:

- **Into the cloud.** On-premises and other clouds' resolvers conditionally forward each cloud namespace (and, for Azure, each private endpoint service's public zone) to the inbound endpoints, using static addresses written once. On OCI the entry point is a listening endpoint. Neither the AWS nor the Azure inbound endpoint accepts an ordinary NS delegation of a private zone; AWS's delegation inbound endpoint is the exception and is new.[^cdns-r53-hybrid][^cdns-az-arch]
- **Out of the cloud.** Each cloud forwards the agency's on-premises namespaces to the agency resolvers through outbound endpoints and rules (AWS), rulesets (Azure) or a forwarding endpoint and resolver rules (OCI). On AWS, the rules are created once in a network account and shared through RAM or a Profile, so spokes associate them and can't edit them, which is the cloud form of "one policy object" *(design guidance)*.[^cdns-r53-rules-manage][^cdns-r53-profiles]
- **Internet-bound queries.** CISA requires Protective DNS for all egress DNS resolution, and says agency cloud deployments should use it upstream "either directly or via a SASE/SSE solution," or use agency internal DNS infrastructure as their upstream.[^cdns-cisa-edns] None of the native resolvers forwards the default path to Protective DNS on its own; that takes a "." rule (AWS, Azure) or a rule whose condition is None (OCI) pointing at the agency resolvers or a resolver that forwards there.[^cdns-oci-rules] Whether a given estate's cloud egress already reaches Protective DNS some other way is for the agency to establish with CISA *(confirm)*.
- **Policy.** DNS Firewall and DNS resolver policy are each cloud's own DNS-layer filter; OCI has none for private DNS, so its catch-all rule to the agency resolvers is the only way agency policy reaches a VCN *(inference)*. They're useful, but they're a second policy surface beside the agency's response policy zones. Feed them from the same indicator decisions, or use them as a backstop, so a block on premises is also a block in each cloud *(design guidance)*.
- **Logs.** Route 53 query logs, Azure resolver policy logs and OCI private resolver logs go to the SIEM beside the agency resolvers' logs, parsed through ASIM's DNS schema as [Book 12](../books/b12-security-operations/05-from-log-warehouse-to-detection.md) does for every DNS source.

## Part 2 — When to run your own DNS servers in the cloud

Microsoft's guidance is direct: "Use DNS Private Resolver instead of custom DNS server software like BIND when possible." It names one case where VM-hosted DNS is needed: on-premises needs an authoritative answer for an NS-delegated subdomain, "because neither DNS Private Resolver nor Azure private DNS zones expose authoritative name servers for name server (NS) delegation."[^cdns-az-hybrid] AWS's current guidance steers hybrid DNS to Resolver endpoints and rules; its older whitepaper, now marked for historical reference only, described running custom resolvers on EC2 for control, or when the 1,024-packet quota limits scale.[^cdns-r53-hybrid][^cdns-aws-whitepaper]

The criteria *(design guidance)*:

| Run your own (vNIOS or BIND) when… | Stay with the native resolver when… |
|---|---|
| A zone must be authoritative in the cloud and reached by NS delegation, and AWS's delegation features don't fit or aren't available in the Region | The need is forwarding in and out of the cloud; the inbound and outbound endpoints do that, managed and zone-redundant |
| The agency's response policy zones, or its encrypted-DNS logging at the agency resolver (M-22-09), must apply in the cloud exactly as on premises, and the native filter can't carry them, or, as on OCI, there is no native filter | The cloud's own filter (DNS Firewall, resolver policy) plus forwarding "." to the agency resolvers gives the same policy; on OCI, a catch-all rule to agency resolvers reachable over FastConnect or VPN does |
| Workloads need a resolver they can reach over DoT or DoH from inside the cloud, and the native endpoints' protocols don't fit (AWS outbound endpoints: Do53 or DoH, no DoH-FIPS; Azure ruleset targets: plain DNS over UDP or TCP) | Clients use Do53 to the VPC or VNet resolver, and encryption starts at the agency resolver |
| A bridge is needed during a migration, such as AD DNS retirement or a datacenter exit, with an end date | The bridge has no end date, or no one owns its removal |
| Load would exceed the per-instance quotas of forwarding everything to the native resolver (1,024 packets per second per ENI on AWS; 1,000 queries per second per VM on Azure), and a caching tier helps[^cdns-vpc-dns][^cdns-az-limits] | Volume fits within the endpoint quotas (10,000 queries per second per endpoint address) |

**vNIOS or BIND.** Where the agency's DNS runs on an Infoblox Grid, vNIOS is the natural choice: it joins the same Grid, takes its zones, response policy zones and DNSSEC from the Grid Master, and is managed in the same console (option A in the [Trinzic explainer](trinzic-multicloud-ddi.md)). The [NIOS implementation guide](../books/guides/infoblox-nios-implementation.md) notes that Infoblox's cloud HA documentation lists only commercial endpoints, so vNIOS failover in GovCloud and Azure Government is a point to confirm. BIND is the choice when there is no Grid, when a vNIOS license or member isn't justified for a small footprint, or when a tool or application expects BIND itself. BIND has no policy plane of its own: its policy has to come from somewhere, and for Book 08 that is the DDI platform and Git (Part 3).

## Part 3 — BIND on AWS, Azure and Oracle Cloud

### Version and support

ISC supports each even-numbered BIND 9 branch for four years. As of October 29, 2026, **9.20** (9.20.30, October 2026) is the supported production branch, shown as current stable and Extended Support, with end of life in the second quarter of 2028; **9.18 reached end of life in June 2026**, and odd-numbered branches (9.21) are development.[^cdns-isc-support][^cdns-isc-download] ISC's vulnerability policy covers only "the most recent monthly releases" of supported branches.[^cdns-isc-vuln] Operating-system packages follow their vendor's support instead: Ubuntu 24.04's archive, for example, carries 9.18.39 as of this check, so support for that package comes from Ubuntu, not ISC. An agency must decide which it relies on and record it *(design guidance)*.

### Roles, placement and high availability

BIND does three jobs; NIST and ISC both say to keep them apart. NIST SP 800-81r3 says DNS hosts "should be dedicated to that task and hardened," that recursion should be off on authoritative servers, and that an internet-facing instance "should not be configured to serve in both roles"; combining roles is acceptable on internal-only servers.[^cdns-nist81-231] ISC says "Do not combine authoritative and recursive nameserver functions."[^cdns-isc-auth]

| Role | When it fits in a cloud | Book 08 condition *(design guidance)* |
|---|---|---|
| **Forwarder** (no zones; forwards by domain) | The common case: a cloud-side hop that applies agency policy and logging, then forwards cloud names to the native resolver and everything else to the agency resolvers or Protective DNS | Its forward zones are the Decision 3 rules, generated from the policy plane |
| **Recursive resolver** (caches, validates, applies response policy zones) | Where agency policy and logging must apply at the first hop in the cloud | Same response policy zones, validation and logging as on premises |
| **Authoritative** (hosts zones) | Only for an NS-delegated zone the native services can't answer, or a secondary of a zone mastered on the DDI platform | A secondary, never a separately authored primary; the zone's one writable owner stays on the DDI platform |

**Placement.** Put cloud DNS servers in the shared-services or network hub VPC or VNet that already holds the native resolver's endpoints, never in workload accounts *(design guidance)*. On AWS, a BIND server can forward only to its own VPC's +2 address: AWS says forwarding to "any VPC CIDR + 2 address from on-premises or other VPC DNS servers is not supported."[^cdns-r53-hybrid] Private hosted zones it needs must therefore be associated with its VPC, or reached through an inbound endpoint. On Azure, a custom DNS server must sit in the same virtual network as the VMs whose hostnames it resolves, and forward those to `168.63.129.16`.[^cdns-az-vnetdns] On OCI, a BIND server in a VCN forwards the VCN's names (`oraclevcn.com`) and private views to `169.254.169.254`, and the subnets that use it get it through the custom resolver DHCP option, which takes at most three servers.[^cdns-oci-vcndns][^cdns-oci-trouble]

**High availability.** NIST asks for at least two servers on different network segments, dispersed geographically, and a hidden primary for authoritative service.[^cdns-nist81-232] Microsoft asks for at least two DNS VMs across availability zones.[^cdns-az-hybrid] In practice: two or more servers per Region in different Availability Zones, a second Region for a Region-wide failure, and every client and forwarder configured with all of them *(design guidance)*. The 2022 AWS whitepaper describes EC2 auto-recovery and movable secondary addresses for failover.[^cdns-aws-whitepaper]

### Forwarding to and from the native resolver

The native resolver stays the only path to the cloud's own names; BIND forwards those to it, and forwards everything else up the governed chain (Book 08 Decision 2). AWS says a custom DNS server must "route your private DNS queries to the IP address of the Amazon-provided DNS servers for your VPC."[^cdns-r53-phz-cons] BIND's `forward` default is `first`, which falls back to its own recursion when forwarders fail;[^cdns-bind-ref] for private names, that fallback can return the public answer or NXDOMAIN, so the AWS whitepaper says "it is critical to specify the forward only option."[^cdns-aws-whitepaper]

Four quotas and behaviors shape the design:

- **Per-instance limits.** On AWS, the 1,024-packet-per-second link-local quota covers all DNS queries a BIND server sends to VPC+2.[^cdns-vpc-dns] On Azure, a VM may send 1,000 queries per second to `168.63.129.16` with 200 pending; queries over the limit "are dropped," per VM.[^cdns-az-limits] BIND's cache absorbs repeats; size the fleet so no one server forwards near the limit *(design guidance)*.
- **Timeouts.** Microsoft says a forwarder's timeout should be more than four seconds, or Private DNS records may resolve to public addresses.[^cdns-az-vnetdns]
- **Visibility.** The VPC Resolver logs and filters only queries it receives, so it sees BIND as the source, not the client, and never sees BIND's cache hits *(inference)*.[^cdns-r53-qlog][^cdns-r53-fw-how] BIND's own logs carry the client.
- **Loops.** Don't forward a domain to an inbound endpoint from inside the VPC or VNet that holds that endpoint, and don't associate a VPC with both a rule and that rule's inbound endpoint.[^cdns-r53-bp][^cdns-az-rulesets]

The configuration below is the forwarder role on AWS. It is **illustrative**: names and addresses are examples, it passed `named-checkconf` from BIND 9.18.39 (the Ubuntu 24.04 package) but hasn't run against a VPC or been checked on 9.20, and in practice it is rendered from the policy plane and Git, not typed.

```text
// Illustrative only: forwarder in a shared-services VPC (10.20.0.0/16).
// Generated from the DDI policy plane and Git; never edited on the host.
acl "clients" { 10.0.0.0/8; };

options {
    directory "/var/cache/bind";
    version none;                       // don't disclose the version
    recursion yes;
    allow-query { clients; };
    allow-recursion { clients; };
    allow-transfer { none; };
    dnssec-validation auto;
    // Private namespaces have no DNSSEC chain, and the VPC Resolver strips DNSSEC data
    validate-except { "aws.corp.agency.gov"; "corp.agency.gov"; "internal"; };
    // Internet-bound: the governed upstream (agency resolvers, then Protective DNS)
    forward only;
    forwarders { 10.1.0.10; 10.1.0.11; };
};

// Cloud names to the VPC Resolver of this VPC (VPC+2); private hosted zones are associated here
zone "aws.corp.agency.gov" { type forward; forward only; forwarders { 10.20.0.2; }; };
zone "compute.internal"    { type forward; forward only; forwarders { 10.20.0.2; }; };

// On-premises names to the agency resolvers
zone "corp.agency.gov"     { type forward; forward only; forwarders { 10.1.0.10; 10.1.0.11; }; };
```

On OCI, the same file forwards `oraclevcn.com`, the agency's OCI private zones and Oracle private endpoint names, such as `<prefix>.adb.<region>.oraclecloud.com` for an Autonomous Database, to `169.254.169.254`, or to a listening endpoint from another VCN.[^cdns-oci-vcndns][^cdns-b08-c07] On Azure, the same file forwards the agency's Azure namespaces and each private endpoint service's public zone (for example `blob.core.usgovcloudapi.net` in Azure Government) to `168.63.129.16`, or to the Private Resolver's inbound endpoint when the BIND server is in a different virtual network.[^cdns-az-vnetdns][^cdns-b08-c07]

### DNSSEC signing and validation

**Validation.** BIND validates by default: `dnssec-validation` defaults to `auto`, with the root trust anchor built in.[^cdns-bind-ref][^cdns-bind-dnssec] SP 800-81r3 asks for validation, the root key as trust anchor and automated trust anchor rollover.[^cdns-nist81-validate] Two cloud specifics:

- **Behind the VPC Resolver, BIND can't validate.** The VPC Resolver "ignores the DO (DNSSEC OK) EDNS header bit," returns no DNSSEC records and sets no AD bit, so "performing your own DNSSEC validation is not currently supported by the VPC Resolver."[^cdns-r53-validate] Validation of public names happens either in the VPC Resolver (enabled per VPC) or in BIND when it forwards to an upstream that returns DNSSEC data.
- **The OCI resolver validates.** Oracle says the VCN resolver performs DNSSEC validation for signed zones.[^cdns-oci-pdns] Whether it passes DNSSEC records and the AD bit back to a resolver behind it, so that BIND could validate for itself, isn't documented; *confirm*.
- **Private namespaces need exceptions.** A private zone under a signed public parent, such as a private hosted zone for a name under the agency's signed `.gov` domain, has no secure delegation, so a validator treats its answers as bogus. BIND's `validate-except` lists the names "at and beneath which DNSSEC validation should not be performed."[^cdns-bind-ref] Hold that list in the policy plane with the forwarding rules, because it is part of the same split-horizon decision (Book 08 [Chapter 06](../books/b08-ddi/06-dns-identity-and-dnssec.md)) *(design guidance)*.

Whether CISA's Protective DNS returns DNSSEC records to forwarders, so that BIND can validate behind it, isn't stated on CISA's public pages; *confirm* with CISA.

**Signing.** SC-20 asks for signed authoritative data, and M-08-23 required DNSSEC on federal systems.[^cdns-sp80053][^cdns-m0823] Neither AWS nor Azure signs private zones, and no Oracle page describes signing private zones.[^cdns-r53-sign][^cdns-az-dnssec][^cdns-oci-pdns] SP 800-81r3 §3.8.6 says signing internal zones "is not recommended" except where it is required, and notes that government agencies may require it.[^cdns-nist81-sign] Where an agency signs, BIND's `dnssec-policy default` is ISC's "recommended, fully automated way to sign and maintain DNS zones" (inline signing, automatic ZSK rollover; KSK rollover needs the parent's DS updated).[^cdns-bind-dnssec] The program's position is that the zone's one writable owner signs it, and Book 08 keeps DNSSEC keys on the Grid Master or an HSM, so a cloud BIND secondary serves signed data and holds no keys *(design guidance)*.

### Response policy zones as Protective DNS

**BIND's mechanism.** Response policy zones (RPZ) are "ordinary DNS zones containing RRsets that can be queried normally if allowed." A `response-policy` statement takes up to 64 of them. Five triggers (client IP, query name, response IP, name server name, name server IP) map to actions: NXDOMAIN, NODATA, PASSTHRU, DROP, TCP-only or local data. Because a policy zone is an ordinary zone, it is kept in sync with zone transfers and NOTIFY.[^cdns-bind-rpz] SP 800-81r3 describes protective DNS as "generally implemented by using DNS firewalls or RPZs," with name servers acting as secondaries for RPZ feeds.[^cdns-nist81-pdns]

**How CISA's Protective DNS fits.** For civilian agencies, CISA's Protective DNS Resolver is mandatory, sits "upstream from agency networks," and "does not interfere with internal DNS architecture"; traffic from "mobile, roaming and cloud assets" can flow to it directly.[^cdns-cisa-pdns] CISA's implementation guidance says agency DNS infrastructure "should use only Protective DNS as its upstream provider" except when it's unavailable, that the service supports DoH and DoT over IPv4 and IPv6 and plain DNS "for authorized FCEB DNS infrastructure," and that IaaS deployments should use "Protective DNS or agency internal DNS infrastructure as their upstream DNS provider."[^cdns-cisa-edns] NIST notes that its own "protective DNS" is the general class, "not the CISA program of the same name."[^cdns-nist81-pdns] So *(design guidance)*:

- Agency RPZs on a cloud BIND server are the agency's own protective DNS, in front of CISA's: the same RPZs, from the same feed, as the agency's on-premises resolvers, transferred from the DDI platform.
- Internet-bound queries leave the BIND server only toward Protective DNS, directly or through the agency resolvers.
- RPZ hits and blocks are logged and sent to the SOC, with the same alerting as on premises.

CISA's public pages don't mention RPZ, so the layering is NIST's and the program's, not CISA's.

**Encrypted upstream.** BIND 9.20 can serve DoT and DoH, and its `forwarders` statement takes a `tls` configuration, so it can forward to Protective DNS over DoT.[^cdns-bind-ref] CISA's guidance (April 2024) says BIND "does not currently support communicating with upstream DNS servers using encrypted DNS protocols" and recommends a co-located proxy. That was true of 9.18 and is no longer true of 9.20.[^cdns-cisa-edns] The same appendix suggests setting `recursion no` to keep BIND from using root hints. In BIND that turns off recursive service to clients; the usual way is `forward only;` with `forwarders`, as above.[^cdns-bind-ref] Follow the current ARM where the two differ *(inference)*.

### Query and response logging into the SOC

SP 800-81r3 asks government agencies for "robust DNS traffic logging," names dnstap as an efficient method, says blocked or malicious queries "should always be logged," and asks for integration with the SIEM.[^cdns-nist81-log] M-22-09 expects agencies to keep visibility by logging at their designated resolvers, and M-26-14 sets the retention: searchable for six months and retrievable for a year.[^cdns-m2209][^cdns-m2614]

BIND offers two mechanisms.[^cdns-bind-ref]

- **The `logging` statement** writes the `queries`, `responses`, `query-errors`, `security`, `dnssec`, `rpz`, `rpz-passthru` and `xfer-out` categories to files or syslog. The `querylog` option, or `rndc querylog`, turns query logging on.
- **dnstap** records client, resolver, auth, forwarder and update messages, queries and responses, to a file or a Unix socket. It needs a BIND build configured with `--enable-dnstap`, and `dnstap-output` can't be changed by a reload.

ISC warns that query logging adds heavy overhead and needs planning.[^cdns-isc-rec] Send the logs to the SIEM through the Azure Monitor Agent's syslog path or the agency's collector, and write detections against ASIM's `_Im_Dns`, which already parses BIND ([Book 12, Chapter 05](../books/b12-security-operations/05-from-log-warehouse-to-detection.md)). Because the native resolver sees BIND rather than the client (Part 3, forwarding), BIND's log is the record of who asked; without it, cloud DNS is a blind spot *(inference)*.

### Patching and configuration settings (SI-2, CM-6)

SP 800-81r3 has no section on patching DNS software; it asks for hardened, dedicated hosts and a secured platform and stack.[^cdns-nist81-231] The patching sources are ISC's, and the clock is CISA's:

- **Subscribe** to `bind-announce`, which ISC's best-practice pages tell operators to do, and check ISC's BIND 9 Software Vulnerability Matrix for each version in use.[^cdns-isc-auth][^cdns-isc-matrix]
- **Stay on a supported branch.** 9.18 is end of life at ISC (above). ISC gives support customers advance notice of serious vulnerabilities, three to five business days before disclosure.[^cdns-isc-vuln]
- **Patch to CISA's clock.** BOD 26-04 (June 10, 2026) replaced BOD 22-01 and BOD 19-02 with risk-based remediation timelines. Its shortest window, three days, applies to the highest-risk vulnerabilities in publicly exposed assets (SI-2).[^cdns-bod2604] BOD 23-01 requires asset discovery every 7 days and vulnerability enumeration every 14, including cloud deployments, so cloud BIND servers are in its scope.[^cdns-bod2301]

**Settings (CM-6, CM-7).** Every setting below is in the BIND ARM:[^cdns-bind-ref][^cdns-bind-sec]

- **Disclose and accept less.** `version none` stops BIND answering version queries. `allow-query` defaults to all hosts, so set it, and set `allow-recursion` to the agency's clients.
- **Protect transfers.** `allow-transfer` restricts zone transfers, and TSIG keys authenticate them. SP 800-81r3 adds TLS for their confidentiality.[^cdns-nist81-xfr]
- **Run unprivileged.** Run `named` as an unprivileged user, chrooted where practical (ARM chapter 7).
- **Keep the host to DNS.** No other services on it, as NIST and ISC both say.

### Hardening baselines: what exists

- **NIST SP 800-81r3** (March 2026) is the deployment guide, and the source for this page's hardening points.[^cdns-nist81]
- **ISC's documentation:** the ARM's Security Configurations chapter, and the *BIND Best Practices* pages for authoritative and recursive servers. ISC marks the recursive page as stale.[^cdns-bind-sec][^cdns-isc-auth][^cdns-isc-rec]
- **CIS** lists two BIND benchmarks: *ISC BIND DNS Server 9.11* v1.0.0 and *ISC BIND DNS Server 9.9* v3.0.1.[^cdns-cis] **There is no CIS benchmark for the supported branch (9.20) or for 9.18.** The 9.11 benchmark can be read for its intent, but its settings must be checked against the 9.20 ARM before use. The National Checklist Program's dates for the two benchmarks (about 2020 and 2016) couldn't be loaded from NIST and aren't relied on here.
- **DISA** publishes a BIND 9.x STIG *(High only)*. Its current release couldn't be read from DISA's site on October 29, 2026. It isn't this page's configuration authority.

The baseline an agency states is therefore its own profile: the 9.20 ARM settings, SP 800-81r3, and the CIS 9.11 benchmark's intent, recorded as the CM-6 configuration settings and approved by the CISO *(design guidance)*.

### Configuration from Git, applied by Ansible

The [Ansible guide](../books/guides/ansible-configuration-automation.md#linux-and-unix) treats Linux hosts outside Intune and Arc as tier 2, managed by a playbook from a reviewed repository. A BIND server is exactly that case *(design guidance)*:

- **Rendered, not typed.** `named.conf` and its forward zones are templates rendered from data exported by the DDI policy plane: the forwarding rules, the `validate-except` list, the RPZ primaries and the TSIG key references. Book 08's single source therefore drives BIND too.
- **Checked before it lands.** Every change reaches the main branch only by pull request with a required reviewer. CI runs `named-checkconf` and `named-checkzone`, and the playbook validates again before it reloads.
- **Git is the evidence.** The commit and tag are the CM-2 baseline, the pull request is the CM-3 change record, and check-mode runs report drift ([Ansible guide, evidence](../books/guides/ansible-configuration-automation.md#evidence-to-the-program)).
- **One owning tool.** Ansible owns `named.conf` on these hosts, and nothing else writes it ([one owning tool per setting](../books/guides/ansible-configuration-automation.md#one-owning-tool-per-setting)). A hand edit is drift, to be reverted.
- **Secrets stay out of Git.** TSIG keys and DoT certificates come from the agency's secrets store at run time.

## Part 4 — Alignment checklist for self-managed BIND in AWS

These are the questions that decide whether an agency deploying additional BIND servers in AWS fits Book 08's single policy plane or creates a silo. The usual form is BIND on virtual machines, which in AWS means EC2 instances in a VPC: everything in Part 3 applies to them directly, including the per-interface quota to VPC+2 and the VPC Resolver's view of BIND as the client. If the VMs are instead guests in a VMware environment that runs on AWS, they sit on NSX segments, and their resolution path follows the NSX row of Book 08 [Chapter 07](../books/b08-ddi/07-cloud-private-endpoints-and-ipam.md#how-each-platform-implements-private-dns) until it reaches a VPC; establish which case applies before reading the answers. Ask the questions of each server, or each class of server, and record the answers in the CMDB entry; the same questions apply to BIND in Azure or Oracle Cloud, with that cloud's resolver in place of the VPC Resolver *(design guidance)*.

| # | Question | Aligns when the answer is… | Silo signal |
|---|---|---|---|
| 1 | **Role.** Is it authoritative for any zones, a recursive resolver, or a forwarder? | A forwarder or resolver, or an authoritative *secondary* of a zone mastered on the DDI platform; roles separated as SP 800-81r3 §2.3.1 asks | A primary for zones, or authoritative and recursive combined on an internet-facing server |
| 2 | **Source of truth.** Which zones and records does it hold, and who creates them? | None, or zones transferred from the DDI platform, its one writable owner | Records created on the BIND server, or zones that also exist, separately edited, in Route 53 or on premises |
| 3 | **Why BIND.** Why not the Route 53 VPC Resolver, or Infoblox vNIOS? Permanent, or a bridge? | A stated need from Part 2 that the native resolver can't meet; for a bridge, an end date and the change that retires it | "We've always run BIND," or no end date for a bridge |
| 4 | **Configuration.** Is it in Git, applied by Ansible or another tool, with changes reviewed? | Rendered from policy-plane data, merged by reviewed pull request, applied by automation, checked for drift | Edited on the host; no repository; no change records |
| 5 | **Placement.** EC2 instances or VMware guests? GovCloud or commercial Regions? Which VPCs? Shared Resolver rules? | In the network or shared-services VPC of each Region it serves, at least two per Region across Availability Zones; the VPC Resolver rules that point at it created once and shared through RAM or a Profile; both GovCloud and commercial placements recorded, each checked against the Part 1 table | Servers in workload accounts; rules created per account; one Region's design copied to the other without checking what differs |
| 6 | **Shared policy.** Are its queries logged to the SOC, with the same Protective DNS and DNSSEC validation as on premises? | Query and response logs (or dnstap) in the SIEM with M-26-14 retention; the agency's RPZs from the same feed; internet-bound queries only to Protective DNS; validation on, with `validate-except` from the policy plane | No logs, or logs only in CloudWatch from the VPC Resolver (which shows BIND, not the client); no RPZs; its own upstream |
| 7 | **Hardening, inventory, owner.** Hardened to SP 800-81r3, in the CMDB, with a named owner? | A supported BIND branch on ISC's or the OS vendor's security feed; the agency's stated baseline (CM-6); a CMDB record (CM-8) and IPAM entry for each server; a named owner and backup | An end-of-life branch, an unstated baseline, missing from the CMDB, or "the cloud team" as owner |

**How to read the answers.** Yes to every row means the servers are one more surface the policy plane governs, which is what Book 08 asks for. A silo signal on rows 2 or 4 is the serious one: the servers have become an independently authored source, and the fix is to move their zones to the DDI platform and their configuration into Git before adding more. A silo signal on row 3 alone means the servers may not be needed; compare them with the VPC Resolver's endpoints and rules, and retire them if nothing is lost.
