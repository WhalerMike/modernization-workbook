# Attribute-Driven Migration from Active Directory to Microsoft Entra ID

*In Active Directory an object's place in the tree decided what applied to it; in Entra ID what the object says about itself decides, so the migration is really the work of making those statements true and keeping them true.*

::: {.callout-note}
## In this guide
What the migration accomplishes and how you know you're there, and the four tracks it runs in, because one OU tree holds four populations with different sources of truth: people (the HR track), end-user devices (the Intune track), servers (the Azure Arc track), and service accounts, service principals, managed identities, workload identities and AI agents (the non-person identity track). Then one path for the migration, run on attributes rather than OU placement, in nine stages, each tagged with the tracks it applies to: read what the OU tree encodes, source the attributes (with Federal HR 2.0 as the coming authoritative source), prove them, map them through sync, rebuild OU subtrees as dynamic groups, delegate with administrative units, retarget Group Policy to Conditional Access and Intune, cut over in phases, and correct drift. For each stage: what it is, the decision and who owns it, the gate that says it's done, how it fails, and links to the chapter sections that carry the detail. Then a worked example that follows one user through a mover event, an attribute-to-mechanism crosswalk, the Intune, Arc and non-person identity tracks with what Microsoft documents for each, PIV and CAC certificate binding as an attribute, the limits, the dangers of dynamic groups and how to avoid them, the federal requirements each track supports, and a checklist. This guide is a map. The books hold the depth, and it links to them rather than repeating them.

## What this migration accomplishes {#what-this-migration-accomplishes}

**The goal.** Every person, device, server and workload is governed by attributes that are true, owned by exactly one source, and read by policy. That means:

- Joining, moving and leaving change access automatically and correctly, with no ticket and no hand-edited group. A new device or workload gets its access the same way, from its owning record.
- Delegation and policy follow facts about the object, not its position in a folder tree.
- Every non-person identity has a named owner, the least privilege it needs, and a credential that expires or is managed, so none is left orphaned.
- Every access decision and change leaves evidence.
- Active Directory can be reduced and eventually retired without losing any of the four jobs the OU tree did: delegation, policy scope, accountability and security scope ([Book 01, Chapter 04](../b01-transformation-arc/04-identity-transformation.md#the-identity-claim)).

**How you know you're there.** The criteria below are *(design guidance)*. Where a book states its own gate, that gate governs, and the last column links it.

## Four tracks, each with its own source of truth {#four-tracks}

One Active Directory OU tree holds four different populations of identity: the people who work for the agency, their workstations and mobile devices, the member servers, and the service accounts that workloads run as. They move to Microsoft Entra ID (and Azure) by different paths and take their attributes from different sources, so this guide treats them as four tracks. Mixing them is the commonest source of confusion in this material: an HR attribute and a Group Policy computer setting can sit side by side in the same OU, but they belong to different tracks and change for different reasons.

| Track | What it covers | Source of truth for its attributes | Where the attributes are written | What reads them in the target |
|---|---|---|---|---|
| **HR track: people** | User accounts for employees and contractors | HR (Core HCM, Federal HR 2.0 for employees) and the contractor source of authority, through provisioning | The user object: in AD while users are synced (AD-mastered), in Entra ID once cloud-mastered | Dynamic user groups, administrative units, Conditional Access personas, Lifecycle Workflows (joiner, mover, leaver), license and access-package assignment |
| **Intune track: end-user devices** | Workstations, laptops and mobile devices | Device provisioning: Autopilot registration and group tag, Intune enrollment, and Graph writes by the device provisioning service | The Entra device object: extension attributes 1–15, enrollment profile, physical IDs | Dynamic device groups, Intune assignment filters, Conditional Access device filters, compliance |
| **Azure Arc track: servers** | Member servers on premises and in other clouds, brought under Azure Resource Manager | Arc onboarding (`azcmagent connect --tags` and the resource group), then Azure Policy | Azure resource tags and the resource group or subscription | Azure Policy and machine configuration, Update Manager scoping, Defender for Servers, Azure RBAC |
| **Non-person identity track: workloads and services** | AD service accounts, MSAs and gMSAs, application registrations and service principals, managed identities, workload identities, and AI agents | The application or workload's **owner/sponsor record**: the system inventory or CMDB entry, the application registration and the AI inventory. These are not HR records | Service principal and application properties, custom security attributes, owners and sponsors, and credentials (certificates, federated credentials) | Conditional Access for workload identities, app role assignment, Azure RBAC (with ABAC conditions where supported), access reviews of owners, and credential-expiry and orphan checks |

: The four tracks {.striped .hover}

**What this means for Group Policy.** Group Policy splits the same way:

- **User-configuration settings move with people,** to user-targeted Intune policy and Conditional Access ([Stage 6](#stage-6-replace-gpo-inheritance-with-conditional-access-and-intune-targeting)).
- **Computer-configuration settings move with devices** (Intune device policy and filters, [Book 05, Chapter 08](../b05-devices/08-gpo-to-intune-policy-migration.md)) **and with servers** (Azure Policy and machine configuration, [Book 05, Chapter 09](../b05-devices/09-servers-under-azure-arc.md#azure-policy-and-machine-configuration)).

**What each attribute can reach.**

- HR never describes a device, a server or a service.
- A device rule can never read its owner's attributes.[^adm-dyn-rules]
- A non-person identity has no HR record. Its owner and sponsor are its accountability, and its lifecycle is driven by the owning system's record and by credential expiry, not by a hire or leave date.

**How this guide is organized by track.** The nine stages are written mostly for the HR track, because that's where the attribute model starts. Each stage opens with a **Tracks** line that says which tracks it applies to and what differs for the others. [Beyond users](#beyond-users) is the home of the Intune, Arc and non-person identity tracks.

## Attributes: what you know from AD, and what Entra ID gives you {#attributes}

In Active Directory, *where* an object sits does half the work; in Entra ID, *what the object says about itself* has to do all of it. This section is the reference the later stages point back to: the attribute stores Entra ID offers, in the order to reach for them, which mechanisms read each one, and how the AD attributes an administrator already knows map across. The slot numbers (10 for the organization code, 11 for worker type, 12 for position category, 6 for division, 4 for region) are the program's, from the [program attribute map](../b03-hr-identity/06-canonical-attribute-schema.md#program-attribute-map), not Microsoft's.

### The attribute stores, in the order to reach for them

1. **Native properties.** `department`, `jobTitle`, `companyName`, `officeLocation`, `employeeId` (at most 16 characters), `employeeType`, `employeeHireDate`, `employeeOrgData` (division and cost center), `manager`, `usageLocation` (required for users who are assigned licenses), `userType` (`Member` or `Guest`) and `accountEnabled`.[^adm-user-res] HR provisioning, sync from AD or an administrator writes them. Dynamic rules read many of them, but not `employeeType`, `employeeOrgData` or `manager`.[^adm-dyn-rules] Use a native property first.
2. **`extensionAttribute1`–`15`.** Fifteen predefined string slots on users (`onPremisesExtensionAttributes`) and on devices (`extensionAttributes`), which began as AD and Exchange custom attributes; each holds up to 1,024 characters.[^adm-ext-ref][^adm-user-res] On a synced user they're mastered in AD and read-only in Entra ID; on a cloud-only user they're writable; on a cloud-only user who was once synced, they're read-only in Microsoft Graph and managed through Exchange.[^adm-user-res] Test that last case before a population's source of authority moves to the cloud *(design guidance)*. Device slots are written through Graph ([Intune track](#intune-track)).[^adm-device-update] Dynamic user and device rules read them.[^adm-dyn-rules] Conditional Access device filters read a device's own slots, but only when the device is Intune-managed, compliant or hybrid joined.[^adm-ca-device-filter] Lifecycle Workflows can scope on them ([Book 02, Chapter 10](../b02-identity/10-migrating-and-governing.md#lifecycle-workflows)). The catch: anyone who can read the object can read its extension data, so these slots aren't for sensitive values.[^adm-csa]
3. **Directory extensions** (`extension_<appId-without-hyphens>_<name>`). Registered on an application and targeted at users, groups, devices and other directory objects; synced from custom AD schema attributes by Entra Connect, or created through Graph; up to 100 values per object.[^adm-ext-ref][^adm-dirext-connect] Cloud Sync supports them only through its own `CloudSyncCustomExtensionsApp` application or the one Entra Connect created.[^adm-cloudsync-dirext] Dynamic rules read single-valued ones;[^adm-dyn-rules] Microsoft doesn't document Conditional Access reading them. Use them when 15 slots aren't enough, or for custom AD schema attributes.
4. **Custom security attributes.** Typed values in attribute sets, on users and service principals. Attribute Definition Administrator defines them and Attribute Assignment Administrator assigns them; Global Administrator can't read, define or assign them by default. A tenant holds up to 500 active definitions and an object up to 50 values.[^adm-csa] HR provisioning, including API-driven provisioning, can set them, and Lifecycle Workflows can scope on them.[^adm-whatsnew] Conditional Access application filters read them on service principals (string type only),[^adm-ca-app-filter] and Azure ABAC conditions read them on principals.[^adm-abac] Dynamic membership rules **can't** read them.[^adm-csa-users] Use them for sensitive values no rule reads, and for tagging service principals.
5. **Schema extensions and open extensions.** Application data in Microsoft Graph. They can't be used in dynamic membership rules and don't sync from AD,[^adm-ext-ref] so no targeting in this guide relies on them.
6. **Device properties.** On the Entra device object: `deviceOSType`, `deviceOwnership` (`Personal`, `Company` or `Unknown`), `deviceTrustType` (`AzureAD`, `ServerAD` or `Workplace`), `enrollmentProfileName`, `accountEnabled` and `devicePhysicalIds` (`[ZTDId]`, and the Autopilot group tag as `[OrderID]`). Dynamic device rules read these, and a device rule can't read its owner's attributes.[^adm-dyn-rules][^adm-autopilot] In Intune's inventory: model, manufacturer, OS SKU and version, category and ownership (which Intune calls `Corporate`, not `Company`). Assignment filters read these at check-in, and not extension attributes.[^adm-filter-props]
7. **Azure resource tags** (Arc track). Set at onboarding with `azcmagent connect --tags`, through the portal, CLI or ARM templates, or by Azure Policy inheritance.[^adm-arc-organize][^adm-azcmagent][^adm-tag-policies] Azure Policy, Resource Graph and Update Manager's dynamic scoping read them ([Book 05, Chapter 09](../b05-devices/09-servers-under-azure-arc.md#resource-groups-and-tags)). Tags aren't a role-assignment scope: Azure RBAC attaches to the management group, subscription, resource group or resource.[^adm-arc-cloud-native] Tags are plain text, so they're no security boundary.
8. **Credential binding: `certificateUserIds`** (in `authorizationInfo`). Up to 10 values of up to 1,024 characters, each unique in the tenant. For synced users only Entra Connect writes it, from an AD value such as `altSecurityIdentities` through sync rules the administrator adds, because `altSecurityIdentities` isn't in the default attribute set. For cloud-only users a Privileged Authentication Administrator writes it, or Graph does. Certificate-based authentication matches against it.[^adm-cuid] The [PIV section](#pki-binding) carries the detail.

| Store | Objects | Dynamic membership rules | Conditional Access | Other readers |
|---|---|---|---|---|
| Native properties | Users, devices | Yes, except `employeeType`, `employeeOrgData` and `manager` | Through groups | Lifecycle Workflows triggers and scope; licensing (`usageLocation`) |
| `extensionAttribute1`–`15` | Users (read-only in Entra ID for synced users); devices (Graph) | Yes, for users and devices | Device filters read the device's slots, if it's managed, compliant or hybrid joined ([B04 Ch03](../b04-access/03-the-conditional-access-model.md#conditions)) | Lifecycle Workflows scope ([B02 Ch10](../b02-identity/10-migrating-and-governing.md#lifecycle-workflows)) |
| Directory extensions (`extension_<appId>_<name>`) | Users, groups, devices and other directory objects; synced from AD or created through Graph | Yes, single-value only | Not documented | Token claims |
| Custom security attributes | Users; service principals | **No**[^adm-csa-users] | Application filters (service principals, string type) | Azure ABAC principal attributes; Lifecycle Workflows scope; provisioning from HR sources, including API-driven provisioning[^adm-whatsnew] |
| Schema and open extensions | Many Graph resources | No | No | Application data only |
| Intune inventory | Managed devices | No | No | Assignment filters |
| Azure resource tags | Arc servers and other Azure resources | No | No | Azure Policy; Resource Graph; Update Manager dynamic scoping ([B05 Ch09](../b05-devices/09-servers-under-azure-arc.md#resource-groups-and-tags)) |
| `certificateUserIds` | Users | No | Authentication strength, through CBA | Certificate-based authentication username binding |

: Which store each consumer reads {.striped .hover}

Custom security attributes suit sensitive values that no rule reads, because reading them is restricted to the attribute roles, while anyone who can read an object can read its extension data.[^adm-csa] Access codes stay in `extensionAttribute10` to `12`, as [Book 03, Chapter 06](../b03-hr-identity/06-canonical-attribute-schema.md#design-rules) decides.

### Compared with Active Directory

| Topic | Active Directory | Entra ID |
|---|---|---|
| Structure | A hierarchy: distinguished names and OUs | Flat |
| Schema | An extensible LDAP schema; additions are forest-wide and can't be removed, only made defunct[^adm-ad-schema] | Fixed properties plus the extension mechanisms above |
| Access | LDAP or AD PowerShell | Microsoft Graph; some filters, such as those on extension attributes, need advanced queries[^adm-adv-query] |
| Write control | Per-attribute ACLs and OU delegation | Roles, scoped by administrative units; custom security attributes have their own roles |
| Groups from attributes | None natively; scripts | Dynamic rules, over the attributes they can read |
| Identity anchor | `objectGUID` and `objectSid` | The Entra object ID, plus `onPremisesImmutableId`, the source anchor: Entra Connect uses `ms-DS-ConsistencyGuid` (from version 1.1.524.0), and Cloud Sync uses `ms-DS-ConsistencyGuid` with a fallback to `objectGUID`, which can't be changed[^adm-sourceanchor][^adm-cloudsync-faq] |
| Mastering | AD | For synced users, AD still masters most attributes, read-only in Entra ID, until the source of authority moves |

**What follows from the comparison.**

1. Placement has to become coded data before cutover.
2. While users are synced, edit attributes in AD or HR, never in Entra ID.
3. Not every familiar attribute can be read by a rule, which is why the coded mirrors exist.
4. Write access to an attribute is the new security boundary ([dynamic group dangers](#dynamic-group-dangers)).
5. Some AD concepts, such as Kerberos SPNs and `adminCount`, carry over as a different mechanism, not as an attribute.

## Stage 0: read what the OU tree encodes

**Tracks: all four.** The same tree holds user accounts, computer objects for workstations and servers, and service accounts, so the inventory reads all of them: the user OUs and their delegations for the HR track, the computer OUs and their GPO links for the Intune and Arc tracks, and the service-account inventory, classified by type and risk, for the non-person identity track ([Book 02, Chapter 09](../b02-identity/09-building-the-entra-target.md#discovering-service-accounts)). Record which track each OU and each GPO belongs to; a GPO's user-configuration and computer-configuration halves can belong to different tracks.

**What it is.** The OU tree did four jobs at once: delegation, policy scope, accountability and security scope ([Book 01, Chapter 04](../b01-transformation-arc/04-identity-transformation.md#the-identity-claim)). The assessment captures what each OU actually encodes so the target reproduces intent, not structure: placement and size, GPO links and inheritance, and the non-inherited access-control entries that someone delegated by hand ([Book 02, Chapter 08](../b02-identity/08-assessing-the-forest.md#ou-hierarchy-and-delegation)). Record what read-only discovery couldn't see ([Chapter 07](../b02-identity/07-read-only-discovery.md#recording-what-read-only-discovery-couldnt-see)).

**Decision.** For every OU function, where it goes: GPO scoping to Conditional Access and Intune, delegation to administrative units, logical organization to attributes and dynamic groups ([Book 02, Chapter 09](../b02-identity/09-building-the-entra-target.md#organizational-units)). For every security group: keep synced, convert to cloud-only, convert to dynamic, or retire ([the per-group decision](../b02-identity/09-building-the-entra-target.md#the-per-group-decision)).

**Gate.** Book 02's Phase 0: a complete inventory in Git, a UPN remediation plan, a recorded decision for every group, the OU structure mapped to proposed units, and the service-account risk classification complete ([Book 02, Chapter 10](../b02-identity/10-migrating-and-governing.md#phase-0-assessment)).

**Failure modes.** A site-linked GPO looks unlinked to an OU-only search ([Book 02, Chapter 08](../b02-identity/08-assessing-the-forest.md#what-to-collect)). `adminCount` overstates current privilege, because it stays set after an account leaves a protected group ([Chapter 09](../b02-identity/09-building-the-entra-target.md#adminsdholder-and-protected-groups)).

## Stage 1: source the attributes

**Tracks: mostly HR.** This stage is about people. The other three tracks source their attributes elsewhere, never from HR, and their authorities are decided here too:

- **Intune:** device provisioning, from the procurement or asset record through the Autopilot registration and group tag, Intune enrollment and Graph writes by the device provisioning service. The primary user's department isn't a source ([Book 05, Chapter 03](../b05-devices/03-where-device-and-server-data-lives.md#which-system-owns-which-fact); [Chapter 04](../b05-devices/04-intune-first-onboarding.md#where-the-organizational-assignment-comes-from)).
- **Arc:** the tags applied at onboarding and the resource group, carrying the same procurement or asset record, then Azure Policy ([Book 05, Chapter 09](../b05-devices/09-servers-under-azure-arc.md#resource-groups-and-tags)).
- **Non-person:** the owning application or workload's record: the system inventory or CMDB entry, the application registration and, for AI, the AI use-case inventory ([Book 17, Chapter 03](../b17-ai-identity/03-the-inventory-as-an-identity-source.md#reading-the-fields-as-identity-data)). Book 03 keeps these identities out of the human-worker pattern on purpose ([Chapter 01](../b03-hr-identity/01-overview-and-applicability.md#where-it-doesnt-apply-as-written)).

**What it is.** One governed set of HR-sourced attributes drives five outcomes: dynamic group membership, administrative-unit scope, Conditional Access targeting, license assignment and drift visibility ([Book 01, Chapter 04](../b01-transformation-arc/04-identity-transformation.md#what-the-attributes-drive)). This stage decides where each attribute comes from, what it's called, what it holds and who may write it.

**Decisions and owners.**

- *Which system owns each fact.* HR is authoritative for who a worker is and where they sit; the identity platform for how identity is proven and whether a request is permitted now ([Book 03, Chapter 04](../b03-hr-identity/04-attribute-authority.md#system-of-record-versus-identity-provider)). Every attribute is authoritative in one system and derived everywhere else, and corrections flow upstream ([authoritative versus derived](../b03-hr-identity/04-attribute-authority.md#authoritative-versus-derived-attributes)).
- *The enterprise person key.* A key the agency controls, carried in `employeeId` (at most 16 characters), with the source person number mapped to it, so a change of HR source changes only the source key ([Book 03, Chapter 04](../b03-hr-identity/04-attribute-authority.md#one-person-layered-identifiers)). The governance body decides it.
- *The canonical schema.* Native Entra attributes first; three coded extension attributes for access (organization code, worker type code and position category in `extensionAttribute10` to `12`); codes, never display strings, in anything a rule reads ([Book 03, Chapter 06](../b03-hr-identity/06-canonical-attribute-schema.md#design-rules); the stores are compared in [Attributes](#attributes)). The data architect owns the schema and HR owns the code lists ([Chapter 07](../b03-hr-identity/07-who-owns-workforce-identity.md#the-data-architect-one-model-one-key-one-owner-per-attribute)).
- *Writers.* The provisioning service is the only writer of every schema field; help-desk, self-service and Exchange-admin write paths to the access slots are removed, and any other write is drift ([Book 03, Chapter 06](../b03-hr-identity/06-canonical-attribute-schema.md#writers)). Security decides write permissions on HR-mastered attributes.

**Gate.** Book 03's Phase 1 gate: the identifier decision, authority map and schema signed ([Chapter 12](../b03-hr-identity/12-execution-plan.md#phase-1-attribute-authority-and-schema)).

**Failure modes.** A key owned by the source breaks at the Core HCM cutover; an owner without the means leaves duty station stale; the help desk becomes a shadow source ([Book 03, Chapter 07](../b03-hr-identity/07-who-owns-workforce-identity.md#where-ownership-fails-and-how-the-program-prevents-it)).

### Building the attributes from Federal HR 2.0

Federal HR 2.0 is what will supply most of these attributes for federal employees, so it belongs in this stage, not after it.

**The coming source.** The joint OMB/OPM memorandum of December 10, 2025 consolidates the government's Core HCM systems onto one government-wide platform, and OPM awarded the Core HCM contract to Oracle (Oracle Fusion Cloud HCM) on June 10, 2026. Wave 1 is the agencies that volunteered; Wave 2 is everyone else, transitioning in FY 2027; the government-wide adoption goal is FY 2028; and the memo expects the platform eventually to make eOPF and EHRI redundant. The memo's sample onboarding runs about eight months, with interconnections live around month 5, which the chapter treats as a planning assumption to confirm with the HR 2.0 program office ([Book 03, Chapter 03](../b03-hr-identity/03-federal-hr-2-0.md#the-program-facts)).

**What OPM does and doesn't require.** No OPM document mandates or specifies how the platform integrates with the agency's own directory. The solicitation's identity requirements point into the platform: its users sign in through OPM's identity provider and are provisioned into it by SCIM 2.0. The reverse direction appears only as a sample interconnection, an "Identity Management Solution" fed by Core HCM as the authoritative source for user identity data, with no protocol, product or directory named, and the Core HCM Steering Committee approves agency-specific integrations ([Book 03, Chapter 03](../b03-hr-identity/03-federal-hr-2-0.md#what-opm-requires-and-what-it-leaves-to-the-agency)). So the Entra design is the agency's own decision. The book's recommendation, as design guidance, is to take the HR-to-identity feed to the Steering Committee in Phase 0, before the interconnection goes live, and to name it in the memo's integration-point inventory ([Chapter 12, Phase 0](../b03-hr-identity/12-execution-plan.md#phase-0-program-alignment)). The window closes at interconnection go-live ([Chapter 03](../b03-hr-identity/03-federal-hr-2-0.md#why-this-is-the-opportunity-not-the-project)).

**The path from HR to Entra ID.** Oracle Fusion Cloud HCM has no native Entra connector, so the Microsoft realization is API-driven inbound provisioning: HCM Extracts for the full load and Atom feeds for changes, read by middleware in the agency's boundary that validates, sequences, normalizes to SCIM, writes provenance and reconciles each event, then posts to Microsoft Graph `/bulkUpload` ([Book 03, Chapter 05](../b03-hr-identity/05-the-provisioning-pipeline.md#why-api-driven-inbound-provisioning)). Read the hire, termination and cancellation feeds by published date, or pre-hire workflows never run ([what the feeds do](../b03-hr-identity/05-the-provisioning-pipeline.md#what-the-feeds-do-that-the-middleware-has-to-handle)). The [HCM-to-Entra research guide](hcm-entra-implementation.md) carries the build detail. Each provisioning app has its own endpoint and lands users in one of two places:[^adm-api-concepts]

| Population | Where HR writes the attributes | How they reach Entra ID | What that means |
|---|---|---|---|
| AD-mastered (synced) users, most of the estate today | Active Directory, through the Microsoft Entra provisioning agent; the OU is computed from HR attributes and `manager` becomes a DN reference | Entra Connect Sync or Cloud Sync projects them; for synced users the Entra extension-attribute values are read-only | AD is still where the attributes are written. Hire and leave dates land in `extensionAttribute2` and `3` and a sync rule maps them to `employeeHireDate` and `employeeLeaveDateTime` |
| Cloud-mastered users | Entra ID directly; structure lands as attributes, not as an OU | Already there | Any AD account an application still needs is provisioned from Entra ID |

**What the HR-sourced attributes then drive.** Organization, division and position codes feed the dynamic groups of Stage 4 and the unit rules of Stage 5. The worker type code defines the Internals persona that Conditional Access targets in Stage 6, and `manager` becomes the approver for access packages and the reviewer for access reviews ([Book 03, Chapter 10](../b03-hr-identity/10-from-attributes-to-access.md#access-packages-and-access-reviews)).

**Before the agency's wave lands.** The pipeline doesn't wait for Core HCM. Four choices make the switch a source swap rather than a redesign:

1. Key on an enterprise person key the agency controls, not on the source's person number ([Book 03, Chapter 04](../b03-hr-identity/04-attribute-authority.md#one-person-layered-identifiers)).
2. Map to OPM's standard elements and codes, not to the current system's or Oracle's field names ([Chapter 06](../b03-hr-identity/06-canonical-attribute-schema.md#the-standard-attribute-layer)).
3. Keep one door into the directory, so validation, provenance and reconciliation live in middleware that outlasts the source ([Chapter 05](../b03-hr-identity/05-the-provisioning-pipeline.md#logical-architecture-and-microsoft-realization)).
4. Don't build against EHRI or eOPF feed shapes, which the memo expects to retire ([Chapter 03](../b03-hr-identity/03-federal-hr-2-0.md#why-this-is-the-opportunity-not-the-project)).

**Licensing and GCC, as of October 29, 2026.** API-driven inbound provisioning is included with Entra ID P1, P2 and ID Governance;[^adm-api-concepts] it became generally available in the US Government cloud in June 2025, and Microsoft's feature-availability table lists it, with provisioning-agent registration for US Government tenants.[^adm-whatsnew][^adm-feature-avail] Lifecycle Workflows need Entra ID Governance or Entra Suite,[^adm-lcw] and ID Governance is available in GCC, GCC High and DoD.[^adm-feature-avail] The `/bulkUpload` daily cap is 2,000 calls with P1 or P2 and 6,000 with ID Governance, at up to 50 operations a call.[^adm-api-concepts]

## Stage 2: prove the attributes are true before anything depends on them

**Tracks: HR, with the non-person equivalent.** Correlation here means accounts to worker records. The non-person equivalent is correlating every service account and service principal to an owner and a reason, which Book 02's Phase 0 classifies and Phase 4 acts on ([Book 02, Chapter 10](../b02-identity/10-migrating-and-governing.md#phase-4-service-account-modernization)). The device equivalent is the read-only correlation pass across the device records ([Book 05, Chapter 03](../b05-devices/03-where-device-and-server-data-lives.md#a-read-only-correlation-pass)).

**What it is.** Every later control reads these attributes, so a drifted HR feed produces drifted access faster than any ticket queue ([Book 03, Chapter 12](../b03-hr-identity/12-execution-plan.md#sequencing-principle)). A token has to assert an authorization that is true, not just well-formed ([Book 01, Chapter 04](../b01-transformation-arc/04-identity-transformation.md#from-sessions-to-tokens)).

**Decision.** The correlation threshold, set by the agency's risk governance; 99% on the pilot cohort is a proposed starting point, not a requirement, and a risk-tiered threshold is usually better ([Book 03, Chapter 12](../b03-hr-identity/12-execution-plan.md#sequencing-principle)). HR owns the fix for every wrong value.

**Work.** Baseline HR against reality for worker type, organization, supervisor and status, and fix errors at the source; populate `employeeId`; flag every unmatched enabled account as an orphan candidate with an owner; confirm the extension-attribute carriers are free ([Phase 1](../b03-hr-identity/12-execution-plan.md#phase-1-attribute-authority-and-schema)). In AD, remove write paths on the target OUs and Exchange's custom-attribute cmdlets ([Chapter 06](../b03-hr-identity/06-canonical-attribute-schema.md#writers)).

**Gate.** Correlation threshold met on the pilot; every enabled account correlated or on a dated exception list ([Phase 1](../b03-hr-identity/12-execution-plan.md#phase-1-attribute-authority-and-schema)). Privacy basis, PIA and the minimized attribute set are Phase 1 gate items too ([Book 03, Chapter 07](../b03-hr-identity/07-who-owns-workforce-identity.md#the-privacy-office)).

**Validate.** The read-only [validation kit](../../../downloads/validation-kit.zip) measures this gate: VK-HR-01 (uncorrelated accounts), VK-HR-02 (coded attribute coverage), VK-HR-03 (reconciliation with an HR export) and VK-HR-04 (duplicate `employeeId`).

**Failure modes.** Automating against unverified data in month one ([Book 03, Chapter 12](../b03-hr-identity/12-execution-plan.md#the-program-at-a-glance)). Expect a burst of high-severity findings in the first month of a new pipeline; that is the measurement working ([Chapter 11](../b03-hr-identity/11-drift-metrics-and-evidence.md#drift-between-hr-and-the-directory)).

## Stage 3: map the attributes through sync

**Tracks: HR.** Hybrid-joined Windows devices also synchronize from AD,[^adm-stale-devices] but the program's device attributes are written to the Entra device object by provisioning, not carried from AD ([Book 05, Chapter 08](../b05-devices/08-gpo-to-intune-policy-migration.md#the-device-attribute-schema)).

**What it is.** The plumbing between HR, AD and Entra ID during coexistence.

**Decisions.** The sync engine (Cloud Sync unless a Connect-only requirement applies) and the sign-in method (password hash sync everywhere), both decided by identity engineering ([Book 02, Chapter 09](../b02-identity/09-building-the-entra-target.md#choosing-and-configuring-the-sync-engine)). Filtering, including the `DoNotSync` scoping filter on `extensionAttribute15` ([filtering](../b02-identity/09-building-the-entra-target.md#filtering)), and attribute flow, including the date mappings for AD-landed users ([Book 03, Chapter 06](../b03-hr-identity/06-canonical-attribute-schema.md#the-schema)) and the transitional account-type rule that derives slot 7 from OU placement, which is dropped once the value is on the source object ([Book 02, Chapter 09](../b02-identity/09-building-the-entra-target.md#attribute-flow-and-transformations)). Use the same carrier in both landing zones ([Attributes](#attributes)), so a rule on `extensionAttribute10` works for a hybrid user and a cloud-mastered one ([Book 03, Chapter 06](../b03-hr-identity/06-canonical-attribute-schema.md#design-rules)).

**Gate.** Book 02's Phase 1: object counts within ±1%, no sync errors, an attribute spot check ([Chapter 10](../b02-identity/10-migrating-and-governing.md#phase-1-sync-deployment-and-initial-sync)). Book 03's Phase 3: initial full sync reconciled before deltas, then shadow mode with every pipeline-versus-directory difference explained, and zero unmatched-record creations ([Chapter 12](../b03-hr-identity/12-execution-plan.md#phase-3-hybrid-go-live-pilot)).

**Failure modes.** A soft or hard match overwrites cloud attributes with on-premises values, so clean AD first and keep both match types blocked outside a planned window ([Book 02, Chapter 09](../b02-identity/09-building-the-entra-target.md#soft-match-and-hard-match)). A Connect Sync server not on 2.6.84.0 with application-based authentication stops synchronizing on April 7, 2027 ([Connect Sync deadline](../b02-identity/09-building-the-entra-target.md#cloud-sync-or-connect-sync)). An omitted attribute in a `/bulkUpload` record can clear the target value if clearing is enabled, so send the complete record every time ([Book 03, Chapter 05](../b03-hr-identity/05-the-provisioning-pipeline.md#the-middleware-five-duties-per-event)).

## Stage 4: materialize OU subtrees as dynamic groups

**Tracks: HR and Intune.** Dynamic user groups are the HR track; dynamic device groups, on the device's own attributes, are the Intune track. Arc servers are scoped by resource group and tag, not by group, and Microsoft documents no dynamic rule type for service principals ([non-person identity track](#non-person-identity-track)). Read [Dynamic group dangers and how to avoid them](#dynamic-group-dangers) before the first rule grants access.

**What it is.** AD answered "who is in the Finance branch?" by walking the tree; Entra ID answers it by evaluating a rule. Every governed group uses one of two patterns: a node query on an organization code (with `-in` for a roll-up) or a functional query that combines an organizational attribute with another ([Book 01, Chapter 04](../b01-transformation-arc/04-identity-transformation.md#the-two-query-patterns)). Every access rule excludes disabled accounts and guests, and agents' user accounts, explicitly ([Book 03, Chapter 10](../b03-hr-identity/10-from-attributes-to-access.md#rule-patterns)).

**Decision.** For each group whose membership really follows department, location or role, convert; otherwise keep it assigned ([Book 02, Chapter 09](../b02-identity/09-building-the-entra-target.md#converting-static-groups-to-dynamic-groups)). The application owner decides the access rule; HR owns the attribute values it reads ([Book 03, Chapter 07](../b03-hr-identity/07-who-owns-workforce-identity.md#who-uses-it)). Flatten nested chains rather than rebuilding them ([Book 02, Chapter 09](../b02-identity/09-building-the-entra-target.md#nested-groups); [Book 06, Chapter 16](../b06-data-platform/16-groups-roles-and-membership.md#flat-by-design)).

**Gate.** No dynamic group grants production access until its attributes are populated and verified for a pilot cohort and its rule has been validated, shadowed against the group it replaces and reconciled ([Book 06, Chapter 17](../b06-data-platform/17-dynamic-membership-delegation-and-privilege.md#writing-naming-and-testing-rules)).

**Failure modes.** A rule written on a display string breaks the next time someone retypes it ([Book 06, Chapter 17](../b06-data-platform/17-dynamic-membership-delegation-and-privilege.md#choosing-the-attributes)). A rule change removes existing members who no longer match ([same chapter](../b06-data-platform/17-dynamic-membership-delegation-and-privilege.md#writing-naming-and-testing-rules)).

## Stage 5: delegate with administrative units

**Tracks: HR and Intune.** Units hold users, groups or devices. Delegation over Arc servers is Azure RBAC at management group, subscription or resource group scope ([Arc track](#arc-track)), and a non-person identity's accountability is its owner and sponsor, not a unit ([non-person identity track](#non-person-identity-track)).

**What it is.** OU-level delegation becomes administrative units: containers of users, groups or devices against which a role is assigned so that it applies only to the unit's members ([Book 02, Chapter 05](../b02-identity/05-delegation-without-ous.md#what-administrative-units-are)). The three-tier model puts tenant-scoped readers above department and division units, and each unit's dynamic rule mirrors the corresponding group's rule ([Book 01, Chapter 04](../b01-transformation-arc/04-identity-transformation.md#the-three-tier-model)). Division units read the division code in `extensionAttribute6` ([Book 02, Chapter 05](../b02-identity/05-delegation-without-ous.md#division-aus-tier-3-created-on-demand)).

**Decisions.** The delegation model is identity engineering's decision ([Book 02, Chapter 06](../b02-identity/06-who-owns-the-migration.md#the-responsibility-matrix)). Restricted management is a per-unit decision with a default of no, made before the unit exists because it can't be changed afterward ([Book 02, Chapter 05](../b02-identity/05-delegation-without-ous.md#restricted-management-a-per-au-decision)). Role principals are assigned, role-assignable groups whose members are PIM-eligible ([role assignment matrix](../b02-identity/05-delegation-without-ous.md#role-assignment-matrix)). Create the unit and its scoped assignment before the groups it will hold, so no window exists where only a tenant-wide administrator can manage them ([Book 06, Runbook R07](../b06-data-platform/r07-groups-aus-and-the-conditional-access-perimeter.md#sequencing-the-administrative-unit-comes-first)).

**Gate.** Every unit's rule matches the registry and its processing is on; every role assignment is in the matrix; the scoped role is denied outside its unit ([Book 02, Chapter 05](../b02-identity/05-delegation-without-ous.md#drift-detection); [R07 verification](../b06-data-platform/r07-groups-aus-and-the-conditional-access-perimeter.md#verification-and-rollback)).

**Failure modes.** Treating a unit as a confidentiality boundary when it only scopes writes. Restricting a broad HR-driven population, which removes it from PIM, entitlement management, Lifecycle Workflows and access reviews. Expecting a Global Administrator to be locked out, when restriction only makes the bypass deliberate and audited ([Book 01, Chapter 04](../b01-transformation-arc/04-identity-transformation.md#restricted-management)).

## Stage 6: replace GPO inheritance with Conditional Access and Intune targeting

**Tracks: all four.** The user-configuration half of Group Policy goes to user-targeted Intune policy and Conditional Access (HR track). The computer-configuration half goes to Intune device policy and filters for end-user devices (Intune track) and to Azure Policy and machine configuration for servers (Arc track, [Book 05, Chapter 09](../b05-devices/09-servers-under-azure-arc.md#azure-policy-and-machine-configuration)). Service principals get Conditional Access for workload identities, assigned directly ([non-person identity track](#non-person-identity-track)).

**What it is.** GPOs inherited down the tree; Conditional Access policies and Intune assignments target groups. Conditional Access targets personas built from authoritative attributes, such as Internals from the worker type code in `extensionAttribute11` ([Book 04, Chapter 03](../b04-access/03-the-conditional-access-model.md#personas)). Intune assigns policies to dynamic device groups built from device extension attributes, with assignment filters as a second layer for hardware, ownership, join type and OS, and for time-sensitive assignment uses a filter on a user group or on All devices instead, keeping dynamic device groups where a rule must read extension attributes ([Book 05, Chapter 08](../b05-devices/08-gpo-to-intune-policy-migration.md#assignment-strategy)). Intune can also assign to user groups, and Microsoft's guidance is that settings belonging to the user, such as email and user certificates, go to user groups and settings that must stay on a device go to device groups.[^adm-intune-assign] Device rules can read only device attributes, not the attributes of the device's owner,[^adm-dyn-rules] so a user's organization code never reaches a device group by itself; device attributes come from device provisioning.

**Decisions.** Control requirements belong to the CISO ([Book 02, Chapter 06](../b02-identity/06-who-owns-the-migration.md#the-responsibility-matrix)). Each GPO setting is classified before it moves, and every setting has exactly one owning policy ([Book 05, Chapter 08](../b05-devices/08-gpo-to-intune-policy-migration.md#policy-types)). Settings such as account lockout aren't Conditional Access controls; they go to Entra smart lockout or Intune ([Book 01, Chapter 04](../b01-transformation-arc/04-identity-transformation.md#conditional-access-the-policy-inheritance-replacement)).

**Gate.** Every Conditional Access policy in report-only for two to four weeks, then enforced in waves behind a monitoring gate, with the emergency-access group excluded ([Book 02, Chapter 09](../b02-identity/09-building-the-entra-target.md#testing-and-rollout)). Every policy targets only governed groups ([Book 01, Chapter 04](../b01-transformation-arc/04-identity-transformation.md#verification)). On the device side, each workload wave reports success on its ring and its GPO links are disabled, not deleted ([Book 05, Chapter 08](../b05-devices/08-gpo-to-intune-policy-migration.md#testing-at-each-gate)).

**Failure modes.** A grant policy restricts nothing on its own; it needs a paired block ([Book 04, Chapter 03](../b04-access/03-the-conditional-access-model.md#policies-come-in-pairs)). A policy that includes a dynamic group silently misses every user whose attribute is empty ([exclusions](../b04-access/03-the-conditional-access-model.md#exclusions)). Role targeting doesn't reach roles scoped to an administrative unit, so target the administrators' group ([users, groups and roles](../b04-access/03-the-conditional-access-model.md#users-groups-roles-and-workload-identities)). Conditional Access doesn't inherit through units, so the branch group has to include everyone the ancestor GPO targeted ([Book 01, Chapter 04](../b01-transformation-arc/04-identity-transformation.md#conditional-access-the-policy-inheritance-replacement)).

## Stage 7: cut over in phases

**Tracks: all four.** Waves select users and devices by attribute value, servers by resource group and tag, and non-person identities by the application that owns them; a service account moves with its application, running old and new credentials in parallel before the legacy account is disabled ([Book 02, Chapter 10](../b02-identity/10-migrating-and-governing.md#phase-4-service-account-modernization)).

**What it is.** A phased runbook, not a flag day: a pilot division, then division by division, two or three at a time, each drift-clean before the next ([Book 01, Chapter 04](../b01-transformation-arc/04-identity-transformation.md#migration-phases)). Waves are defined by attribute values, so each wave's scope is a query and its dynamic groups already exist ([Book 00, Chapter 09](../b00-orientation/09-design-pilot-and-rollout.md#waves-defined-by-attribute-values)). Book 05's workload waves run inside those division waves ([Book 05, Chapter 08](../b05-devices/08-gpo-to-intune-policy-migration.md#phase-5-workload-cutover-in-waves)).

**Decisions.** Wave go/no-go: identity engineering ([Book 02, Chapter 06](../b02-identity/06-who-owns-the-migration.md#the-responsibility-matrix)). Leaver automation goes first, because revocation is where the risk and the evidence are ([Book 03, Chapter 12](../b03-hr-identity/12-execution-plan.md#phase-4-lifecycle-automation-and-attribute-derived-access)). Align each population's HR cutover with its move to Entra ID and with the agency's Core HCM interconnection ([Phase 5](../b03-hr-identity/12-execution-plan.md#phase-5-cutover-population-by-population)). As a population becomes cloud-mastered, retarget its provisioning from the AD app to the Entra app, with the AD leg dormant but intact. Microsoft's source-of-authority guidance says the same: once the users' sync cycle completes, remove them from the HR-to-AD provisioning scope and add them to the HR-to-Entra configuration.[^adm-soa-guidance]

**Gate.** A signed validation report; a dry run on production data with writes disabled; seven days after cutover in which every change for the population traces to an HR event; then the ticket path for account creation closes ([Book 03, Appendix C](../b03-hr-identity/appendix-c-acceptance-and-cutover.md#proving-hr-is-the-sole-source)). Cloud-mastered populations run the full lifecycle with evidence and no AD writes, and rollback has been tested once ([Book 03, Chapter 12](../b03-hr-identity/12-execution-plan.md#phase-5-cutover-population-by-population)). Legacy retirement is the only destructive phase and needs approval per item ([Book 01, Chapter 04](../b01-transformation-arc/04-identity-transformation.md#phase-4-legacy-retirement)).

**Failure modes.** A division reaching full availability before its own pilot is drift-clean. Deleting GPOs instead of disabling links, which removes the one-command rollback ([Book 05, Chapter 08](../b05-devices/08-gpo-to-intune-policy-migration.md#rollback)). Deleting a synced user only in Entra ID, which the next sync restores ([Book 03, Chapter 08](../b03-hr-identity/08-joiner-mover-leaver.md#deletion)).

## Stage 8: detect and correct drift

**Tracks: all four.** Each track has its own comparison: HR against the directory (below); device inventories reconciled on the Entra device ID ([Book 05, Chapter 10](../b05-devices/10-operating-and-evidencing-the-fleet.md#device-inventory-reconciliation)); Arc connection state and policy compliance ([Book 05, Chapter 09](../b05-devices/09-servers-under-azure-arc.md#what-arc-changes-and-what-it-doesnt)); and declared against observed AI and workload identities, including orphans and expiring credentials ([Book 17, Chapter 07](../b17-ai-identity/07-monitoring-drift-and-shadow-ai.md#drift-comparing-what-was-declared-with-what-is-observed)).

**What it is.** A scheduled comparison of what HR says with what the directory holds, and of the unit and role registry with the tenant. HR-side drift classes are missing identity, stale access, orphan account, attribute drift, unauthorized write, credential drift and schema drift ([Book 03, Chapter 11](../b03-hr-identity/11-drift-metrics-and-evidence.md#drift-between-hr-and-the-directory)). Directory-side checks catch unit rule drift, paused rule processing, unmatched role assignments and restriction mismatches ([Book 02, Chapter 05](../b02-identity/05-delegation-without-ous.md#drift-detection)).

**Decision.** Continuous monitoring evidence and drift findings: the CISO ([Book 02, Chapter 06](../b02-identity/06-who-owns-the-migration.md#the-responsibility-matrix)). Each finding is closed at the source, by fixing the record or the rule, never the copy ([Book 02, Chapter 10](../b02-identity/10-migrating-and-governing.md#the-assessment-pipeline)).

**Gate.** Book 01's verification list: valid attributes for every HR-listed worker, every group on one of the two patterns, every unit rule mirroring its group with processing on, every policy targeting only governed groups, zero drift findings, and a zero-action nightly plan ([Chapter 04](../b01-transformation-arc/04-identity-transformation.md#verification)). Book 03's recurring gate: the six lifecycle metrics within thresholds on the ConMon cadence ([Chapter 12](../b03-hr-identity/12-execution-plan.md#phase-6-sustained-posture)).

**Failure modes.** Entra ID's log retention is far shorter than federal records schedules and isn't retroactive, so route logs out from the pilot's first day ([Book 03, Chapter 11](../b03-hr-identity/11-drift-metrics-and-evidence.md#the-evidence-each-event-leaves)). Access-review decisions don't change dynamic-group membership, so review the rule and its inputs instead ([Book 06, Chapter 17](../b06-data-platform/17-dynamic-membership-delegation-and-privilege.md#access-reviews)).

## Worked example: one user and one mover event

A budget analyst in a finance division, a federal employee, AD-mastered because her division hasn't cut over. The codes are placeholders. The example is the HR track; step 5 is where the Intune track starts, and it shows why the two don't mix.

**Stage 1, the record.** Core HCM holds her worker record and assignment. The crosswalk projects it as `employeeId` (the enterprise person key), `department` "Finance", organization code `FIN-LED` in `extensionAttribute10`, division code in `extensionAttribute6`, worker type `EMP` in `extensionAttribute11`, position category `ANALYST` in `extensionAttribute12`, a region code in `extensionAttribute4`, and her supervisor as `manager` ([Book 03, Chapter 06](../b03-hr-identity/06-canonical-attribute-schema.md#program-attribute-map)).

**Stage 3, the landing.** Because she's AD-mastered, the provisioning agent writes these values to her AD account and Cloud Sync projects them to Entra ID, where her extension attributes are read-only ([Book 03, Chapter 05](../b03-hr-identity/05-the-provisioning-pipeline.md#landing-in-active-directory)).

**Stages 4 to 6, the effects.** She's in the node group for `FIN-LED` and the functional group for analysts across organizations ([Book 03, Chapter 10](../b03-hr-identity/10-from-attributes-to-access.md#rule-patterns)); in the department and division units, so the division's scoped help desk can reset her password ([Book 02, Chapter 05](../b02-identity/05-delegation-without-ous.md#role-assignment-matrix)); in the Internals persona, so the baseline Conditional Access policies apply ([Book 04, Chapter 03](../b04-access/03-the-conditional-access-model.md#personas)); and in a SQL Server reader group whose rule reads her organization and position codes ([Book 06, Chapter 17](../b06-data-platform/17-dynamic-membership-delegation-and-privilege.md#choosing-the-attributes)). Her laptop's policies come from device groups on its own tier and role attributes ([Book 05, Chapter 08](../b05-devices/08-gpo-to-intune-policy-migration.md#tier-groups)).

**The mover event.** HR processes her reassignment to the accounts-payable division as a personnel action, nature-of-action code 721, which is a mover ([Book 03, Chapter 08](../b03-hr-identity/08-joiner-mover-leaver.md#personnel-actions-are-the-triggers)). Nobody opens a ticket. The chain:

1. Core HCM publishes the change on its assignment feed; the middleware validates it, writes a provenance record and sends her complete record to `/bulkUpload` with organization code `FIN-AP` and the new division code ([Book 03, Chapter 05](../b03-hr-identity/05-the-provisioning-pipeline.md#the-middleware-five-duties-per-event); [research guide sequences](hcm-entra-implementation.md#the-sequences)).
2. The provisioning agent updates her AD account; the next sync cycle carries the values to Entra ID. Attribute-change triggers fire only after the sync delivers the change ([Book 02, Chapter 10](../b02-identity/10-migrating-and-governing.md#lifecycle-workflows)).
3. Dynamic groups and units recompute. She leaves the `FIN-LED` groups and the old division unit and joins the `FIN-AP` ones, usually within a few hours but possibly more than 24 ([Book 01, Chapter 04](../b01-transformation-arc/04-identity-transformation.md#mover)). The analyst group and the Internals persona don't change, because position category and worker type didn't. Access the SQL Server group gave her ends at the engine only after rule processing, token expiry and session turnover ([Book 06, Chapter 16](../b06-data-platform/16-groups-roles-and-membership.md#when-a-change-takes-effect)).
4. The mover workflow, triggered by the change in division code, removes the old department's access package, requests the new one, notifies the managers and starts a review of what's left ([Book 02, Chapter 10](../b02-identity/10-migrating-and-governing.md#mover-workflow)). The review matters because access from a package or a direct assignment doesn't leave on its own ([Book 03, Chapter 08](../b03-hr-identity/08-joiner-mover-leaver.md#mover)). Approvals now route to her new supervisor of record.
5. Her laptop's device groups don't move, because device rules can't read her attributes.[^adm-dyn-rules] If the device's department attribute should change, that's device reconciliation, not HR ([Book 05, Chapter 08](../b05-devices/08-gpo-to-intune-policy-migration.md#the-device-attribute-schema)).
6. The drift scan compares her HR record with her directory values field by field. Any difference is attribute drift, fixed in HR or in the mapping. The evidence is the provenance record, the provisioning log entry, the workflow run history, and the transfer-to-review interval that PS-5 asks for ([Book 03, Chapter 11](../b03-hr-identity/11-drift-metrics-and-evidence.md#the-measured-lifecycle)).

When her division cuts over (Stage 7), the same record is retargeted to the Entra app and lands in Entra ID directly. Her groups, units and policies don't change, because they read the same carriers in both landing zones.

## Beyond users: the Intune, Arc and non-person identity tracks {#beyond-users}

The stages above move people. This section is the home of the other three [tracks](#four-tracks): end-user devices, servers and non-person identities. For each it says where the attributes come from, what the computer half of Group Policy becomes, how you know the track is done, and then whether Microsoft documents targeting those objects by attribute. The Microsoft answers come from Microsoft Learn as of October 29, 2026. Where Microsoft doesn't document something, this section says so.

### Intune track: end-user devices {#intune-track}

**Source of truth.** Device provisioning, not HR. The procurement or asset record owns ownership, purpose, location and organizational assignment; the Autopilot registration carries the group tag; Intune enrollment and the device provisioning service's Graph writes put the values on the Entra device object ([Book 05, Chapter 03](../b05-devices/03-where-device-and-server-data-lives.md#which-system-owns-which-fact); [Chapter 04](../b05-devices/04-intune-first-onboarding.md#registration-and-group-tags)). A device with no source value carries an explicit "unpositioned" marker rather than an empty attribute ([Chapter 03](../b05-devices/03-where-device-and-server-data-lives.md#the-rule)).

**Group Policy.** The computer-configuration settings that reached workstations through OU links become Intune device policy, assigned to dynamic device groups and narrowed by filters, with one owning policy per setting ([Book 05, Chapter 08](../b05-devices/08-gpo-to-intune-policy-migration.md#policy-architecture)). Settings that belong to the user go to user groups instead.[^adm-intune-assign]

**Done when** *(design guidance)*: every managed device carries attributes written by provisioning, its policy is targeted by them, and computer-side GPO links are disabled population by population, with rollback tested ([Book 05's gates](../b05-devices/08-gpo-to-intune-policy-migration.md#testing-at-each-gate)). **Federal requirement:** CM-2, CM-6, CM-8 and IA-3, and M-22-09's device inventory and signal ([mapping](#federal-requirements)).

**Step by step:** the [Intune Track Implementation guide](intune-track-implementation.md) runs this track as seven gates, each with the validation kit checks that prove it. The device targeting conventions it builds on are set in [Gate 5 of the Attribute-Driven Migration implementation guide](attribute-driven-migration-implementation.md#gate-5-personas-and-targeting-conventions).

**What Microsoft documents for targeting by attribute: yes.**

- **Dynamic device groups.** Device rules can read device properties such as `deviceOSType`, `deviceOwnership`, `deviceTrustType`, `enrollmentProfileName`, `devicePhysicalIds` and `extensionAttribute1` to `15`, and only device properties: a device rule can't read the attributes of the device's owner.[^adm-dyn-rules] Windows Autopilot devices carry their own markers: `(device.devicePhysicalIDs -any (_ -startsWith "[ZTDid]"))` selects every Autopilot device, and the Autopilot group tag maps to the device's `OrderID`, so `(device.devicePhysicalIds -any (_ -eq "[OrderID]:<tag>"))` selects one tag.[^adm-autopilot]
- **Writing device extension attributes.** They're set through Microsoft Graph with `PATCH /devices/{id}` and an `extensionAttributes` body. The least-privileged application permission is `Device.ReadWrite.All`; for delegated calls it's `Directory.AccessAsUser.All`, with Intune Administrator as the least-privileged supported role; and in app-only calls, or for non-Windows devices, only `extensionAttributes` can be updated.[^adm-device-update] [Book 05, Chapter 08](../b05-devices/08-gpo-to-intune-policy-migration.md#writing-a-device-attribute) carries the program's device slots and a delegated sample that connects with `Directory.AccessAsUser.All`.
- **Assignment filters.** Filters evaluate Intune device properties at check-in, not Entra attributes: among them `deviceName`, `deviceOwnership` (`Personal` or `Corporate`), `deviceTrustType` (Intune's own values), `enrollmentProfileName`, `manufacturer`, `model`, `operatingSystemSKU`, `deviceCategory`, `cpuArchitecture` and `operatingSystemVersion`, which became generally available in August 2026.[^adm-filter-props][^adm-intune-whatsnew] Extension attributes aren't on the list.
- **Scope tags.** Intune delegates with its own role-based access control: a role assignment combines permissions, scope groups (the users and devices an administrator manages) and scope tags (the Intune objects the administrator can see). Tags can be assigned to devices through groups, an object or role takes at most 100, and Intune RBAC doesn't apply to Entra roles.[^adm-scope-tags]

### Azure Arc track: servers {#arc-track}

**Source of truth.** Arc onboarding: the resource group a server lands in and the tags applied at connection (`Environment`, `Workload`, `Criticality`, `Owner`, `CostCenter`, `PatchGroup` and `ArcOnboardedDate`), carrying the organizational attributes from the procurement or asset record, then Azure Policy to keep them ([Book 05, Chapter 09](../b05-devices/09-servers-under-azure-arc.md#resource-groups-and-tags)). Intune doesn't manage Windows Server, so servers never enter the Intune track ([same chapter](../b05-devices/09-servers-under-azure-arc.md)).

**Group Policy.** The computer-configuration settings that reached servers through OU links become Azure Policy and machine configuration, scoped by subscription, resource group or machine rather than by OU ([Book 05, Chapter 09](../b05-devices/09-servers-under-azure-arc.md#azure-policy-and-machine-configuration)). Arc attaches the management plane; it doesn't remove the domain join, which is a separate decision per workload ([same chapter](../b05-devices/09-servers-under-azure-arc.md#what-arc-changes-and-what-it-doesnt)).

**Done when** *(design guidance)*: every in-scope server is Arc-enabled with its tag taxonomy applied, and its baseline is assigned and evaluated by Azure Policy ([the day-one baseline](../b05-devices/09-servers-under-azure-arc.md#the-day-one-baseline)). **Federal requirement:** CM-2, CM-6 and CM-8; IA-9 for the server's workload identity ([mapping](#federal-requirements)).

**Step by step:** the [Azure Arc Track: Implementation Guide](arc-track-implementation.md) runs this track as eight gated steps, and the [Endpoint & Device plan's Phase 4](../../project-plans/endpoint-device.md#phase-4-servers-under-azure-arc) schedules it. The server targeting conventions it builds on are set in [Gate 5 of the Attribute-Driven Migration implementation guide](attribute-driven-migration-implementation.md#gate-5-personas-and-targeting-conventions).

**What Microsoft documents for targeting by attribute: yes, through Azure Resource Manager.**

- **The server is an Azure resource.** Connecting a server with the Connected Machine agent gives it an Azure resource ID. It's organized by management group, subscription and resource group like an Azure VM, and policies, role assignments and tags apply to it the same way.[^adm-arc-cloud-native]
- **Tags are its attributes.** Tags are key-value pairs set when the server is onboarded or afterward through the portal, CLI, PowerShell, ARM templates or Azure Policy.[^adm-arc-organize] At onboarding, `azcmagent connect --tags` takes a comma-delimited list such as `Datacenter=NY3,Application=SharePoint`.[^adm-azcmagent] Book 05 sets the program's tag taxonomy and warns that tags are plain text ([Chapter 09](../b05-devices/09-servers-under-azure-arc.md#resource-groups-and-tags)).
- **Azure Policy.** Assignments are scoped by management group, subscription or resource group, and policy rules can test tag values. The built-in *Inherit a tag from the resource group if missing* uses the modify effect to add a resource group's tag to new or updated resources, and a remediation task fixes existing ones.[^adm-tag-policies] Machine configuration carries Policy into the operating system ([Book 05, Chapter 09](../b05-devices/09-servers-under-azure-arc.md#azure-policy-and-machine-configuration)).
- **Azure Resource Graph** queries server metadata and tags at scale across subscriptions.[^adm-arc-organize]
- **Azure RBAC with ABAC conditions: not for Arc.** Role assignments at those scopes govern who manages the server. Role-assignment conditions (Azure ABAC) can currently be added only to role assignments that have blob storage or queue storage data actions.[^adm-abac] Microsoft doesn't document ABAC conditions for managing Arc-enabled servers.

### Non-person identity track {#non-person-identity-track}

**Source of truth.** The owning application or workload's record: the system inventory or CMDB entry, the application registration, and for AI the AI use-case inventory. None of these is an HR record, and Book 03 deliberately leaves non-person identities out of the human-worker pattern ([Book 03, Chapter 01](../b03-hr-identity/01-overview-and-applicability.md#where-it-doesnt-apply-as-written)). Accountability is a named owner and sponsor; the lifecycle runs on the owning system's record and on credential expiry, not on hire and leave dates. What a person contributes is the sponsor's own HR-driven lifecycle: when the sponsor moves or leaves, that is an event for every identity they sponsor ([Book 17, Chapter 05](../b17-ai-identity/05-owners-sponsors-and-lifecycle.md#when-the-sponsor-moves-or-leaves)).

**Done when** *(design guidance)*: every service account and service principal has an owner and sponsor, a reason and a target; each one is retired, re-platformed to a managed identity or gMSA, or made a certificate or federated-credential workload identity; none holds a password that never expires, and none is orphaned. Book 02's Phase 4 is the gate for service accounts ([Chapter 10](../b02-identity/10-migrating-and-governing.md#phase-4-service-account-modernization)). **Federal requirement:** AC-2, AC-6(5), IA-4, IA-5 and IA-9, and M-25-21 for AI ([mapping](#federal-requirements)).

**Step by step:** [Non-Person Identity: An Implementation Guide](non-person-identity-implementation.md) runs this track as six gated steps, and the [Non-Person Identity Modernization plan](../../project-plans/non-person-identity.md) schedules it. Owners and sponsors are recorded by the enterprise person key, a convention set in [Gate 5 of the Attribute-Driven Migration implementation guide](attribute-driven-migration-implementation.md#gate-5-personas-and-targeting-conventions).

#### Service accounts, MSAs, gMSAs and dMSAs

- **What they are and where they go.** Traditional user-object service accounts, managed service accounts, group managed service accounts and, on Windows Server 2025 domains, delegated managed service accounts. Each has its own target: a traditional account becomes an application registration with a certificate or federated credential, or a managed identity where the workload runs in Azure; an MSA is upgraded to a gMSA; gMSAs and dMSAs stay for on-premises Kerberos workloads and move to workload identity federation or a managed identity when the workload moves ([Book 02, Chapter 09](../b02-identity/09-building-the-entra-target.md#service-accounts); [the migration path matrix](../b02-identity/09-building-the-entra-target.md#the-migration-path-matrix)). SQL Server's engine accounts follow the same logic: a gMSA or domain service account works only while AD is authoritative ([Book 06, Chapter 09](../b06-data-platform/09-what-arc-provides-to-sql-server.md#the-managed-identity-and-the-service-account); [Chapter 02](../b06-data-platform/02-why-the-inheritance-must-end.md#driver-three-the-service-account-credential-problem)).
- **Owner and sponsor.** The application owner is identified before the account is touched, and every replacement application gets two human owners ([Book 02, Chapter 10, Phase 4](../b02-identity/10-migrating-and-governing.md#phase-4-service-account-modernization)). An account nobody will own is a retirement candidate.
- **Credential rules.** High-risk accounts (password never expires, over-privileged) convert first. The targets remove the stored secret: AD manages gMSA and dMSA passwords, Azure manages managed identities, and federation replaces the secret with a token from a trusted issuer ([Book 02, Chapter 09](../b02-identity/09-building-the-entra-target.md#the-migration-path-matrix)).
- **Lifecycle.** Driven by the owning application: discovered and classified in Phase 0, converted with old and new credentials in parallel for 30 days, then the legacy account disabled, and retired when the application is ([Book 02, Chapter 10](../b02-identity/10-migrating-and-governing.md#phase-4-service-account-modernization)).

#### Service principals, managed identities and workload identities

- **Owner and sponsor.** At least two human owners per application registration and service principal, never service accounts, with recurring reviews of delegated and application permissions by those owners ([Book 02, Chapter 09](../b02-identity/09-building-the-entra-target.md#governing-service-principals)). Microsoft's access reviews cover service principals assigned to privileged roles, including managed identities; the reviewers need Entra ID P2 and the reviewed service principals need Workload ID Premium.[^adm-wid-faq]
- **Credential rules.** Managed identities first, then federated credentials, then certificates on a rotation schedule; no client secrets for production workloads ([Book 02, Chapter 09](../b02-identity/09-building-the-entra-target.md#governing-service-principals)). Microsoft's application management policies can enforce that: a tenant-wide default policy, with per-application exceptions, can block new password secrets on applications and service principals and cap the lifetime of secrets and certificates. Configuring them needs Security Administrator plus Cloud Application Administrator or Application Administrator,[^adm-app-mgmt-policy] and Microsoft's Workload ID FAQ lists them among the free capabilities.[^adm-wid-faq]
- **Lifecycle.** Driven by the application registration and the system it serves, with credential expiry as a scheduled review point. Workload ID Premium adds recommendations that identify unused or inactive workload identities.[^adm-wid-faq] Conditional Access for workload identities can block a single-tenant service principal by location or risk, but not a managed identity, which access reviews cover instead.[^adm-ca-workload]

#### AI agents

- **Where they fit.** An AI agent is a non-person identity: most AI runs today as a service principal or managed identity, and Microsoft Entra Agent ID adds agent identities, which are special service principals ([Book 17, Chapter 04](../b17-ai-identity/04-kinds-of-ai-identity.md#agent-identities-microsoft-entra-agent-id)). Agent identities can't be members of dynamic membership groups; an agent's user account is a kind of user, and user rules include it unless they exclude it.[^adm-dyn-rules]
- **Owner and sponsor.** A sponsor is required when an agent identity or blueprint is created ([Book 17, Chapter 04](../b17-ai-identity/04-kinds-of-ai-identity.md#the-object-model)). The program's rule is two named humans and a record: an HR-mastered federal sponsor, a small sponsoring group, a technical owner who isn't the sponsor, and an inventory record that names the same sponsor ([Book 17, Chapter 05](../b17-ai-identity/05-owners-sponsors-and-lifecycle.md#three-accountable-relationships)).
- **Credential rules.** No stored secrets, least-privilege access chosen by access mode, and no standing privileged roles ([Book 17, Chapter 06](../b17-ai-identity/06-credentials-and-least-privilege.md#no-stored-secrets)).
- **Lifecycle.** Hangs from the sponsor and the inventory record: creation, sponsor change, reorganization, change of purpose, recertification by expiry, retirement and the orphaned agent ([Book 17, Chapter 05](../b17-ai-identity/05-owners-sponsors-and-lifecycle.md#the-lifecycle-event-by-event)).

#### What Microsoft documents for targeting service principals by attribute: partly

- **Custom security attributes** can be assigned to users and to enterprise applications (service principals). Attribute Definition Administrator defines them and Attribute Assignment Administrator assigns them; Global Administrator and other administrator roles can't read, define or assign them by default. A tenant holds up to 500 active attribute definitions, and an object up to 50 assigned values.[^adm-csa]
- **Conditional Access filter for applications.** A policy can select target applications by a custom security attribute on their service principals, evaluated at token issuance; only attributes of type string work.[^adm-ca-app-filter] Book 04 uses this to target applications by environment ([Chapter 03](../b04-access/03-the-conditional-access-model.md#target-resources)).
- **ABAC principal attributes.** A role-assignment condition can read a custom security attribute on the principal, a user or a service principal, through `@Principal`, within the storage data actions above.[^adm-abac]
- **App role assignment.** Users and security groups are assigned to an enterprise application, optionally to an app role that reaches the application in the token's `roles` claim. Group-based assignment needs Entra ID P1 or P2 and doesn't cascade to nested groups.[^adm-app-assign]
- **Conditional Access for workload identities.** Policies apply to single-tenant service principals registered in the tenant, assigned to the policy directly; a policy assigned to a group that contains a service principal isn't enforced for it. Block is the only grant, managed identities aren't covered, and Workload ID Premium is required.[^adm-ca-workload]
- **Dynamic groups of service principals: not documented.** Microsoft documents user rules and device rules only, and says agent identities, which are service principals, aren't supported as members of dynamic membership groups.[^adm-dyn-rules] It documents no rule type for service principals.

## PIV and CAC certificates as attributes {#pki-binding}

Certificate-based authentication (CBA) is attribute-driven too: Entra ID finds the user by matching a field of the presented certificate to a user attribute. [Book 03, Chapter 09](../b03-hr-identity/09-credentials-and-certificates.md#binding-the-piv-certificate-to-the-entra-user) and [Book 07, Chapter 06](../b07-pki/06-device-and-user-certificates.md#entra-certificate-based-authentication) carry the design; this section ties it to attribute sourcing.

**Username binding.** By default the SAN Principal Name maps to `userPrincipalName`.[^adm-cba-concepts] The bindable fields and the attributes they can match:

| Certificate field | User attributes it can bind to | Affinity |
|---|---|---|
| `PrincipalName` (SAN), `RFC822Name` | `userPrincipalName`, `onPremisesUserPrincipalName`, `certificateUserIds` | Low |
| `Subject`, `IssuerAndSubject` | `certificateUserIds` | Low |
| `SKI`, `SHA1PublicKey`, `IssuerAndSerialNumber` | `certificateUserIds` | High |

: CBA username bindings[^adm-cba-concepts] {.striped .hover}

**Affinity.** High-affinity bindings use identifiers that can't be reused. The tenant's **Required affinity binding** defaults to low; it can be set to high or overridden by custom rules on issuer, policy OID or both, and when high affinity applies the low-affinity bindings are dropped. With several bindings, CBA is only as secure as the lowest-affinity one.[^adm-cba-concepts] Setting the tenant to high before every user's `certificateUserIds` is correct can lock users out.[^adm-cba-howto] The program's position is high affinity in production ([Book 07, Chapter 06](../b07-pki/06-device-and-user-certificates.md#username-bindings-and-affinity)).

**`certificateUserIds`** (the credential-binding store in [Attributes](#attributes)). It holds up to 10 values of up to 1,024 characters, each unique in the tenant, with case-sensitive `X509:<…>` prefixes. For cloud-only users, at least a Privileged Authentication Administrator writes it in the admin center (up to four values of 120 characters there) or through Microsoft Graph (`PATCH /users/{id}` with `authorizationInfo.certificateUserIds`). For synced users, at least the Hybrid Identity Administrator role is needed and only Microsoft Entra Connect can update it, by syncing a value from AD such as `altSecurityIdentities`, or an expression over `userPrincipalName`. Microsoft notes that AD administrators can change the value for any synced account, and asks that only values for current valid certificates be populated and that values be removed when a certificate expires or is revoked.[^adm-cuid] The page names Entra Connect only; it doesn't document Cloud Sync for this attribute.

**Authentication strength.** The built-in Phishing-resistant MFA strength accepts Windows Hello for Business or a platform credential, a FIDO2 security key and multifactor CBA; single-factor CBA isn't in any built-in strength.[^adm-auth-strengths] The CBA authentication binding policy treats every certificate as single-factor by default, and rules by issuer or policy OID raise a card's certificates to multifactor.[^adm-cba-howto] Microsoft's M-22-09 guidance lists Entra CBA, including PIV, CAC and derived PIV credentials, among the phishing-resistant options.[^adm-m2209] The Conditional Access side is [Book 04, Chapter 03](../b04-access/03-the-conditional-access-model.md#authentication-strengths) and Book 02's [phishing-resistant roadmap](../b02-identity/10-migrating-and-governing.md#the-phishing-resistant-authentication-roadmap); trust in both directions during coexistence is [Book 07, Chapter 07](../b07-pki/07-coexistence-and-migration.md#ad-cs-chain-into-entra-id).

**Where the binding comes from.** HR supplies the person: the record, the key and the joiner event that starts sponsorship and proofing. The card management system supplies the binding, because a high-affinity value identifies one certificate and a reissue or renewal changes it ([Book 03, Chapter 09](../b03-hr-identity/09-credentials-and-certificates.md#binding-the-piv-certificate-to-the-entra-user)). During hybrid the value is written to `altSecurityIdentities` in AD, the attribute strong certificate mapping also uses on domain controllers ([Book 07, Chapter 06](../b07-pki/06-device-and-user-certificates.md#strong-certificate-mapping-kb5014754)), and synced. After AD, *(design guidance, unverified)* the card management system writes `certificateUserIds` through Microsoft Graph at issuance. That is an open pilot in the workbook repository, [issue #130](https://github.com/WhalerMike/modernization-workbook/issues/130), which asks which permission a workload needs and how the write behaves for users whose source of authority moved to the cloud; Microsoft documents neither. The leaver removes the value as well as revoking the card ([Book 03, Chapter 09](../b03-hr-identity/09-credentials-and-certificates.md#the-canonical-leaver-sequence)).

**Contractors.** A contractor has no HR record, so the contractor source chosen in Stage 1 supplies the three links HR supplies for employees *(design guidance)*: its joiner sends the sponsorship request, so no card is requested for someone it doesn't hold; the card management system publishes termination, revocation and expiry events back to the pipeline, where a contractor's termination or expiry ends the engagement and a reissue only rewrites the binding; and the contractor's end date, capped by the contract's completion date, is the notification that starts FIPS 201-3's 18-hour termination clock for a card that can't be collected.[^adm-fips201] Until the card arrives, a Temporary Access Pass registers a FIDO2 key that meets the phishing-resistant strength ([Book 04, Chapter 03](../b04-access/03-the-conditional-access-model.md#authentication-strengths)). The path is set out in [Book 03, Chapter 09](../b03-hr-identity/09-credentials-and-certificates.md#the-contractor-piv-path) and [Book 07, Chapter 04](../b07-pki/04-the-target-pki.md#the-contractor-piv-path), with the evidence in the evaluation [Contractors as Oracle Contingent Workers](../../evaluations/oracle-contingent-worker-contractor-source.md#part-5-the-contractor-piv-path).

**Pending proof.** The contractor PIV path is the program's design and hasn't yet been validated in practice; the criteria for Proved are in the evaluation's [Status and review](../../evaluations/oracle-contingent-worker-contractor-source.md#status-and-review).

## Limits

These are the limits as the chapters state them, with the Learn pages re-checked on October 29, 2026 where noted.

**Where dynamic membership stops.** Groups that hold Entra roles must have assigned membership, can't nest, and are capped at 500 per tenant. PIM for Groups doesn't take dynamic groups or groups synced from AD, so privileged access is assigned, cloud-only and time-bound, and HR attributes decide only eligibility ([Book 03, Chapter 10](../b03-hr-identity/10-from-attributes-to-access.md#where-dynamic-membership-stops)). Break-glass accounts depend on none of this machinery ([same section](../b03-hr-identity/10-from-attributes-to-access.md#where-dynamic-membership-stops)). Explicit role-assignment groups stay assigned ([Book 06, Chapter 16](../b06-data-platform/16-groups-roles-and-membership.md#migrating-the-four-ad-group-patterns)).

**Rule limits.** A rule body is at most 3,072 characters, a tenant can have at most 15,000 dynamic groups, and dynamic units count against the same total ([Book 03, Chapter 10](../b03-hr-identity/10-from-attributes-to-access.md#limits-and-efficiency)). Rules can't read `employeeType`, `employeeOrgData` or `manager`, which is why the coded mirrors exist, and multi-value extension properties aren't supported ([Book 03, Chapter 06](../b03-hr-identity/06-canonical-attribute-schema.md#design-rules)); both still held on October 29.[^adm-dyn-rules] Dynamic groups hold users or devices, never groups. The `memberOf` preview ends on November 3, 2026, after which groups, units and auto-assignment policies that use it freeze in their last state ([Book 02, Chapter 09](../b02-identity/09-building-the-entra-target.md#dynamic-group-rule-syntax)); Microsoft's page still says so, and that date is five days after this guide's check.[^adm-memberof] Prefer `-eq`, `-startsWith` and `-in` to `-match` and `-contains` ([Book 03, Chapter 10](../b03-hr-identity/10-from-attributes-to-access.md#limits-and-efficiency)).

**Latency.** Dynamic membership is usually processed within a few hours but can take more than 24, depending on the number of groups, the volume of changes and rule complexity; for bulk changes (more than 500 groups or 20,000 membership changes) Microsoft recommends pausing nonessential groups for at least 24 hours.[^adm-dyn-processing] Book 06 adds the token lifetime (60 to 90 minutes by default) and open sessions, so urgent removal disables the account and revokes sessions instead of waiting for a rule ([Chapter 16](../b06-data-platform/16-groups-roles-and-membership.md#when-a-change-takes-effect)). Conditional Access evaluates group targeting at token issuance ([Book 04, Chapter 03](../b04-access/03-the-conditional-access-model.md#users-groups-roles-and-workload-identities)). Lifecycle Workflows run on a tenant schedule, every 3 hours by default and settable from 1 to 24, with a three-day catch-up window ([Book 03, Chapter 08](../b03-hr-identity/08-joiner-mover-leaver.md#triggers-and-schedule)). For AD-mastered users, every change also waits for the sync cycle. Dynamic Intune device groups add the same processing delay; Microsoft's guidance for time-sensitive assignment is an assignment filter on a user group or on All devices.[^adm-intune-assign]

Dynamic group behaviour, which these limits feed, has its own section: [Dynamic group dangers and how to avoid them](#dynamic-group-dangers).

### Lifecycle Workflows

A **workflow** automates one scenario, such as pre-hire, joiner, mover or leaver. Its execution conditions are a trigger (a time-based attribute such as `employeeHireDate` or `employeeLeaveDateTime` with an offset, or an attribute change) and a scope (a rule over user properties), followed by an ordered list of **tasks**. A **custom task extension** is a task that calls an Azure Logic App, so the workflow can reach systems Microsoft doesn't, such as a card management system, an Intune retire or a ticketing system, either fire-and-forget or waiting for a callback.[^adm-lcw-ext] Scheduled workflows run on one tenant-wide interval, and scheduling is switched on per workflow; an **on-demand** run is a manual run for testing or exceptions.[^adm-lcw-understand] The real-time leaver and mover workflows can't be scheduled.[^adm-lcw-deploy] Lifecycle Workflows need Entra ID Governance or Entra Suite.[^adm-lcw]

| Limit or behaviour | Value | Implication | Response *(design guidance)* |
|---|---|---|---|
| Workflows per tenant | 100[^adm-gov-limits][^adm-lcw] | One workflow per tree, component or worker type runs out fast | A small set of general workflows that branch through scope rules, and a workflow budget in change control ([at scale](#lifecycle-workflows-at-scale)) |
| Tasks per workflow | 25[^adm-gov-limits] | A four-track leaver can be long | Group steps in one Logic App, or chain a leaver and a post-leaver workflow |
| Custom task extensions per tenant | 100[^adm-gov-limits] | Each integration and each variant uses one | One parameterized Logic App per integration |
| Trigger offset (`offsetInDays`) | −180 to +180 days[^adm-gov-limits] | Pre-hire and post-leaver steps fit within six months of the date | Keep longer horizons, such as records retention, outside Lifecycle Workflows |
| Administrative scopes per workflow | 5[^adm-gov-limits] | A workflow can be delegated to at most five units | Delegate by scope, not by copying workflows |
| Schedule interval | Every 3 hours by default, settable from 1 to 24[^adm-gov-limits][^adm-lcw-deploy] | A scheduled leaver isn't immediate, and the sync cycle and group processing add to it ([latency](#limits)) | Urgent terminations use the real-time leaver plus an out-of-band disable and session revocation ([Book 03, Chapter 08](../b03-hr-identity/08-joiner-mover-leaver.md#emergency-termination)) |
| On-demand run | At most 10 users;[^adm-gov-limits] it ignores the workflow's execution conditions, so its tasks apply to whoever is selected[^adm-lcw-understand] | There's no manual bulk run, and a wrong selection is applied anyway | Fix data at the source and let the scheduled run process it; treat each on-demand run as a change with a second-person check |
| Execution limits and quarantine | A tenant-wide or per-workflow threshold, as a percentage of users, a count or both (either trips it). A scheduled run that would exceed it is quarantined until an administrator approves; on-demand runs aren't subject to it[^adm-lcw-exec] | A mass event, such as a reorganization, either quarantines or runs for everyone | Size thresholds to normal weekly volume; plan reorganizations as change events with a pre-agreed release |
| Three-day catch-up | A user whose trigger or scope attributes are set late is still processed if setup completes within three days of the intended time; this doesn't apply to the *Time based attribute V2* preview trigger[^adm-lcw-understand] | HR data entered more than three days late can miss a time-based joiner or leaver | Monitor HR timeliness and report triggers in the past that never ran ([Book 03, Chapter 08](../b03-hr-identity/08-joiner-mover-leaver.md#triggers-and-schedule)) |
| Versions, not edits | Changing an existing workflow's tasks or execution conditions creates a new version[^adm-lcw-versioning] | A change reaches everyone in scope at the next run | Change control, a test tenant, a scoped pilot, and the version history kept as evidence |
| Custom task extension timeout | Microsoft's pages disagree: the service-limits page says 30 minutes to 3 hours,[^adm-gov-limits] the deployment page 3 minutes to 5 hours[^adm-lcw-deploy] | A long callback may time out | Design callbacks to finish well inside 30 minutes until Microsoft reconciles the pages |
| Built-in tasks | None revokes a certificate or PIV credential or retires a device ([Book 03, Chapter 08](../b03-hr-identity/08-joiner-mover-leaver.md#built-in-tasks-by-stage)) | One HR leaver event has to reach all [four tracks](#four-tracks) | Custom task extensions for the card management system and Intune; until they exist, a leaver checklist with owners ([one leaver, four tracks](../b03-hr-identity/08-joiner-mover-leaver.md#one-leaver-reaches-four-tracks)) |

### Lifecycle Workflows at scale {#lifecycle-workflows-at-scale}

*(Design guidance.)* The target estate is one forest of twelve trees synchronized to a live GCC (Moderate) tenant, with every user synced, so attributes are AD-mastered ([Book 03, Chapter 05](../b03-hr-identity/05-the-provisioning-pipeline.md#two-landing-zones)). At that size the limits above bite in predictable ways.

| Risk | Why it bites at this size | Mitigation |
|---|---|---|
| Running out of the 100 workflows | A workflow per tree, per component, per worker type or per scenario multiplies fast: 12 trees × joiner, mover and leaver × 3 worker types is 108, before pre-hire, rehire, conversion and reminders | A small set of general workflows (pre-hire, joiner, mover, leaver, rehire, conversion) that branch on coded attributes through scope rules, with up to 5 administrative scopes each. Never one workflow per organization. Keep a workflow budget in change control, and ask Microsoft Support before planning beyond the default |
| Running out of the 100 custom task extensions | Each integration becomes an extension: card management (revoke, rebind), Intune retire and wipe, server access removal, ticketing, mainframe security, mailbox delegation, HR write-back; variants per component or environment multiply them | One parameterized Logic App per integration, taking the component or code as input. Count extensions per tenant, test and production |
| 25 tasks per workflow | A four-track leaver (account, groups and licenses, PIV revoke, devices, server access, mailbox, tickets) can be long | Group steps inside one Logic App, or chain a leaver and a post-leaver offset workflow |
| The on-demand cap of 10 users | A reorganization, a failed HR batch or a correction can affect hundreds or thousands of people at once, and there's no manual bulk run | Fix the data at the source and let the scheduled run process it. Keep a documented bulk-remediation procedure, such as a provisioning re-run, for incidents |
| On-demand ignores execution conditions and bypasses quarantine | An administrator who runs the leaver workflow on the wrong 10 people disables them, and no execution limit stops it | Make the Lifecycle Workflows Administrator role PIM-eligible with approval; treat each on-demand run as a change with a second-person check, and log it |
| Mass events and quarantine | A reorganization that recodes many people's organization codes fires the mover workflow for all of them; a good threshold quarantines it, and without one it runs | Tenant-wide and per-workflow execution limits sized to normal weekly volume; reorganizations planned as change events with a pre-agreed approval to release the quarantine, and rehearsed in test |
| Latency for urgent terminations | The scheduled interval plus sync plus dynamic-group processing means a scheduled leaver isn't immediate | The real-time leaver plus an out-of-band disable and session revocation through the help desk's emergency path |
| Late HR data outside the three-day catch-up | A hire or separation entered more than three days late can be missed | Monitor HR timeliness, report "trigger date in the past and never processed" as a validation check, and run catch-up deliberately |
| No built-in PIV revoke or device retire | One HR leaver event must reach all four tracks, and natively only the account side is done | Custom extensions for card management (revoke the certificate, remove `certificateUserIds`) and Intune retire; until then, a leaver checklist with owners |
| Workflow changes are new versions | Editing a live workflow changes behaviour for everyone in scope at the next run | Change control, a test tenant, a scoped pilot, and version history kept as evidence |

## Dynamic group dangers and how to avoid them {#dynamic-group-dangers}

**Tracks: HR and Intune.** Dynamic user groups are the HR track's mechanism and dynamic device groups the Intune track's. They fail in the same pattern, so each has its own table below. Arc servers aren't grouped this way, and service principals can't be dynamic members ([non-person identity track](#non-person-identity-track)). [Stage 4](#stage-4-materialize-ou-subtrees-as-dynamic-groups) builds the groups; this section is what to guard against while it does. Facts come from the chapters first and were checked on Microsoft Learn on October 29, 2026; the responses are *(design guidance)* unless a chapter states them as its rule.

### Dynamic user groups (HR track)

| Danger | What goes wrong | How to avoid it |
|---|---|---|
| **Write access to an attribute is access** | Anyone who can write an attribute a rule reads can put an account into the group. Microsoft warns that the group is only as secure as the write permissions on the attributes its rule references, in Entra ID and in any source directory, and that some synced AD attributes may let users write their own values[^adm-dyn-rules] | Make the provisioning service the only writer; remove help-desk, self-service and Exchange custom-attribute write paths, in AD and Entra ID ([Book 03, Chapter 06](../b03-hr-identity/06-canonical-attribute-schema.md#writers)). Audit the write permissions on every attribute a security-relevant rule reads |
| **One rule edit has a large blast radius** | A typo or a wrong operator adds or drops every matching member at the next evaluation, and a rule change removes existing members who no longer match ([Book 06, Chapter 17](../b06-data-platform/17-dynamic-membership-delegation-and-privilege.md#writing-naming-and-testing-rules)) | Validate the rule (the **Validate rules** tab tests up to 20 users or devices at a time and needs at least Groups Administrator),[^adm-dyn-validate] shadow it against the group it replaces, pilot it, and put rule changes under change control with the rules held in Git ([Book 03, Chapter 10](../b03-hr-identity/10-from-attributes-to-access.md#governance-of-the-rules-themselves)) |
| **Rules that forget the guards** | A rule without `accountEnabled` and `userType` clauses includes disabled accounts and guests. An agent's user account is a kind of user, and user rules include it unless they exclude it[^adm-dyn-rules] | Every access rule requires `accountEnabled -eq true` and `userType -eq "Member"` and excludes agents' user accounts ([Book 03, Chapter 10](../b03-hr-identity/10-from-attributes-to-access.md#rule-patterns)) |
| **Display names instead of codes** | Renames, retyping, case and whitespace move people silently ([Book 06, Chapter 17](../b06-data-platform/17-dynamic-membership-delegation-and-privilege.md#choosing-the-attributes)) | Rules read coded attributes in `extensionAttribute10` to `12` from HR-owned code lists; a value not on the list is drift ([Book 03, Chapter 06](../b03-hr-identity/06-canonical-attribute-schema.md#design-rules); [Attributes](#attributes)) |
| **Empty or missing values** | An account with an empty carrier falls out of every group that tests for a value, and a Conditional Access policy that includes a dynamic group silently misses it ([Book 04, Chapter 03](../b04-access/03-the-conditional-access-model.md#exclusions)) | No rule grants production access until its attributes are populated and verified for a pilot cohort ([Stage 4](#stage-4-materialize-ou-subtrees-as-dynamic-groups)); test for the value you expect rather than the absence of another, and report empty carriers as drift |
| **Processing delay and paused processing** | Membership is usually processed within hours but can take more than 24, and bulk changes can call for pausing groups;[^adm-dyn-processing] a paused rule stops updating. Removal from a group doesn't revoke tokens or sessions already issued ([Book 06, Chapter 16](../b06-data-platform/16-groups-roles-and-membership.md#when-a-change-takes-effect)) | Never make a dynamic group the only control for urgent revocation: pair it with disabling the account and revoking sessions ([Book 03, Chapter 08](../b03-hr-identity/08-joiner-mover-leaver.md#emergency-termination)). Check for paused rules in the drift scan ([Book 02, Chapter 05](../b02-identity/05-delegation-without-ous.md#drift-detection)) |
| **Automatic removal has side effects** | A mover or a mis-coded record leaves a group and loses what it gave: application access, and with group-based licensing the license itself. If a user leaves one licensed group before the new license from another is applied, they're unlicensed until processing finishes, and in large tenants that can last longer than expected.[^adm-gbl] When an Exchange Online license goes, mailbox access goes with it; the data is held for 30 days, and adding the license back in that window restores it[^adm-exo-license] | Base license groups on attributes that don't change on an ordinary move, such as legal employer or worker type, rather than on organization codes. Monitor group-based licensing errors. A mis-coded record is fixed at the source inside the 30-day window. Microsoft also documents an optional Exchange Online delicensing-resiliency setting that delays mailbox loss; confirm it's available in the tenant's cloud before relying on it[^adm-exo-resiliency] |
| **What dynamic groups can't do** | They can't be role-assignable or used by PIM for Groups, they don't nest, a rule body is at most 3,072 characters, a tenant has at most 15,000 of them, and the `memberOf` preview ends November 3, 2026 | Keep privileged access assigned, cloud-only and time-bound; see [Limits](#limits) for the detail rather than restating it here |
| **Slow operators** | `-match` and `-contains` slow dynamic group processing, and Microsoft asks that they be minimized[^adm-dyn-rules] | Prefer `-eq`, `-startsWith` and `-in` ([Book 03, Chapter 10](../b03-hr-identity/10-from-attributes-to-access.md#limits-and-efficiency)) |

### Dynamic device groups (Intune track)

| Danger | What goes wrong | How to avoid it |
|---|---|---|
| **Who can write device extension attributes** | Device slots are written through Graph, with `Device.ReadWrite.All` app-only or, delegated, `Directory.AccessAsUser.All` as at least Intune Administrator.[^adm-device-update] Whoever can write them can retarget compliance, configuration and app policy | Make the device provisioning service the only writer, holding the app-only permission; keep Intune Administrator PIM-eligible rather than standing; reconcile weekly ([Book 05, Chapter 10](../b05-devices/10-operating-and-evidencing-the-fleet.md#device-inventory-reconciliation)) |
| **Autopilot group tag (`OrderID`) and enrollment profile rules** | The group tag becomes the device's `[OrderID]` physical ID and `enrollmentProfileName` comes from enrollment,[^adm-autopilot][^adm-dyn-rules] so a wrong or reused tag or profile name moves a device into the wrong policy set | Take the tag from the procurement intake ([Book 05, Chapter 04](../b05-devices/04-intune-first-onboarding.md#registration-and-group-tags)) as a controlled vocabulary, and reconcile it against the CMDB |
| **Device rules can't read the owner's attributes** | A device group keyed to the user's department finds nothing, because a device rule can reference only device attributes;[^adm-dyn-rules] the primary user's department isn't a source anyway ([Book 05, Chapter 03](../b05-devices/03-where-device-and-server-data-lives.md#which-system-owns-which-fact)) | Write the device's own department or organization value at provisioning from the procurement record, or send user-owned settings to user groups[^adm-intune-assign] |
| **Stale and duplicate device objects** | Reimaging leaves duplicates; a domain-joined device that is also Entra registered has two states that can evaluate nondeterministically;[^adm-hybrid-faq] stale objects still match rules. Intune cleanup rules only hide records (after 30 to 270 days without check-in) and don't remove the Entra device object[^adm-intune-cleanup] | Include `device.accountEnabled -eq true` in device rules.[^adm-dyn-rules] Follow Microsoft's stale-device guidance: a timeframe of at least 21 days, disable for a grace period before deleting, retire in Intune first, delete hybrid-joined devices in AD and let sync carry it, back up BitLocker keys, and don't delete system-managed Autopilot devices.[^adm-stale-devices] Prevent the dual state on Windows 10 1803 and later, or block Entra registration on domain-joined devices[^adm-hybrid-plan] ([Book 05, Chapter 10](../b05-devices/10-operating-and-evidencing-the-fleet.md#stale-records)) |
| **Evaluation delay** | Membership-driven policy is slower than assignment filters, which are evaluated at check-in; a dynamic exclusion computed late lets the policy reach the device first | For time-sensitive assignment, use a filter on a user group or on All devices; don't use dynamic device groups as exclusions ([Book 05, Chapter 08](../b05-devices/08-gpo-to-intune-policy-migration.md#assignment-strategy))[^adm-intune-assign] |
| **Blast radius** | One rule edit can push or pull compliance, configuration, endpoint security and app assignments for a whole fleet. A device that falls out of its tier group lands in none, and the tenant setting marks it noncompliant, so Conditional Access blocks it ([Book 05, Chapter 08](../b05-devices/08-gpo-to-intune-policy-migration.md#the-device-attribute-schema)) | Validate and shadow the rule, move it through the pilot rings, and keep rule changes under change control ([Book 05, Chapter 08](../b05-devices/08-gpo-to-intune-policy-migration.md#testing-at-each-gate)) |
| **Conflicts and overlap** | A device in two groups gets two policies that set the same setting; between configuration policies there's no precedence, and the setting may not apply until the conflict is resolved ([Book 05, Chapter 08](../b05-devices/08-gpo-to-intune-policy-migration.md#policy-types)) | One owning policy per setting, and tier groups that are mutually exclusive by design |
| **Ownership values and enrollment edge cases** | Entra rules use `Company`, `Personal` or `Unknown` while Intune shows `Corporate`, so a rule written with `Corporate` matches nothing; `deviceTrustType` values differ the same way (`AzureAD`, `ServerAD`, `Workplace` in rules).[^adm-dyn-rules][^adm-filter-props] Devices enrolled outside Autopilot carry no group tag ([Book 05, Chapter 03](../b05-devices/03-where-device-and-server-data-lives.md#a-read-only-correlation-pass)) | Use each tool's vocabulary; treat `Unknown` ownership and an enrollment without a registration as findings |

### Monitoring both

*(Design guidance.)*

- **Alert on membership deltas** above a threshold per group per evaluation, from the audit logs routed to Log Analytics ([Book 02, Chapter 10](../b02-identity/10-migrating-and-governing.md#detection-rules)); for devices, add membership counts to the weekly reconciliation report ([Book 05, Chapter 10](../b05-devices/10-operating-and-evidencing-the-fleet.md#alerts)).
- **Review the rule change history**: the rules live in Git and the nightly comparison flags any rule in the tenant that differs ([Book 02, Chapter 10](../b02-identity/10-migrating-and-governing.md#git-based-drift-detection)).
- **Keep emergency-access accounts excluded** from every Conditional Access policy, and dependent on none of this machinery ([Book 03, Chapter 10](../b03-hr-identity/10-from-attributes-to-access.md#where-dynamic-membership-stops)).
- **Know how to pause processing** before a bulk change, and check afterwards that no rule stayed paused.[^adm-dyn-processing]
