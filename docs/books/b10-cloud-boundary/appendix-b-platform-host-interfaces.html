Appendix B — Platform Host Interface Reference

Every interface the program’s Git-based platform host on Windows Server 2025 exposes, grouped into six families and mapped to its boundary, authentication model and controls, with illustrative configuration.

A host that holds the program’s source of truth should have a finite list of conversations, and anything off the list is a finding.

NoteIn this appendix

The interface surface of the platform host once it’s built: client transport, identity, the cloud management plane, governance and telemetry, local management, and outbound integrations. For each plane the appendix gives its listener or endpoint, how it authenticates, which boundary it sits in and what evidence it produces, with illustrative configuration. It closes with the boundary and egress posture, the control crosswalk, and how the inventory changes under other repository options.

What this reference covers

The platform host is the program’s single governed server: one Windows Server 2025 machine, with a standby for recovery, that holds the authoritative repository and runs analysis, planning, delivery and evidence. Book 01, Chapter 03 explains its roles and why one authoritative writer matters. This appendix answers the question that comes after the build: once it’s installed, what does it talk to, what talks to it, and what governs each conversation?

That question belongs in a book about the boundary because the host’s interfaces cross several boundaries at once: the agency’s own network, Active Directory, Microsoft Entra ID, Azure commercial, and the public internet. An unenumerated interface on a control-plane host is exactly what an assessor finds and a drift report can’t score. The program’s position is that the list below is closed: every plane is enforced by the build runbook, pinned by the release manifest, and observed by the conformance adapter, and anything not on it is a drift finding or a decision to record, never a tolerated exception.

The reference architecture runs Gitea behind IIS. Gitea and IIS are the program’s example components, chosen over IIS serving Git directly through the git-http-backend CGI for authentication integration and operational reasons; the reduced surface of that alternative is summarized at the end. Host names use contoso as the example domain throughout.

The six families at a glance

Family Planes Primary consumer
A. Client and operator transport HTTPS Git (Smart HTTP), Gitea SSH, Gitea web UI, Gitea REST API, Git LFS, optional program API Contributors, automation, auditors
B. Identity and authentication Active Directory over LDAPS, Entra ID over OpenID Connect, Windows Authentication for the optional API, the host’s own identities, signed-commit verification Operators and service identities
C. Cloud management plane Azure Arc agent, Azure Policy and machine configuration, Azure Monitor Agent, Azure Blob backup target Platform engineering, security operations
D. Governance and telemetry Server-side Git hooks, Gitea webhooks, the drift reporter, the conformance adapter, IIS W3C logs The program’s governance pipeline and continuous monitoring
E. Local management PowerShell 7.6 (signed scripts only), Windows PowerShell 5.1 for legacy IIS cmdlets, the Gitea CLI, IIS Manager and appcmd, NTFS storage Tier 0 administrators
F. Outbound integrations GitHub upstream pull mirror, PostgreSQL back end (or embedded SQLite), build-time package sources Upstream ingest, supply chain

Two planes are absent on purpose. The host reports no Intune compliance policy and isn’t hybrid joined to Entra ID; neither is possible for Windows Server 2025, as family B and family C explain.

WarningIllustrative configuration

The configuration and PowerShell in this appendix are illustrative and haven’t been tested against a production forest or tenant. Host names, group names and paths are examples. Review every block, check option names against the documentation for the versions you install, and run it first on a test host.

Family A — client and operator transport

A.1 HTTPS Git over Smart HTTP, TCP 443

Attribute Value
Listener IIS site FMPReverseProxy, host name git.fmp.corp.contoso.com, port 443
TLS Enterprise-CA-issued certificate (program template), 4096-bit RSA; private key readable only by the IIS app pool identity
Back end http://127.0.0.1:3000 (Gitea), through URL Rewrite and Application Request Routing
Forwarded headers Host and X-Forwarded-Proto, so Gitea builds correct public URLs1
Security headers HSTS (max-age=31536000, includeSubDomains), set with IIS’s native site-level <hsts> element, available since IIS 10.0 version 1709;2 X-Content-Type-Options: nosniff; X-Frame-Options: DENY
Request size maxAllowedContentLength raised to 524,288,000 bytes (500 MB); the IIS default is 30,000,000 bytes (about 28.6 MB)3
Authentication Interactive sign-in through Entra ID OIDC for the web UI; personal access tokens for git over HTTPS
Audit IIS W3C extended logs, read by the conformance adapter and forwarded by the Azure Monitor Agent

This is the only plane that answers on the host’s network address for HTTP. Gitea is bound to loopback and unreachable directly. The rewrite rule is single, catch-all and stop-processing, with no static-content fall-through. Gitea’s own IIS guidance adds the steps that are easy to miss: install the WebSocket Protocol feature (Gitea’s real-time updates use a WebSocket at /-/ws), don’t let the proxy decode the request URI (an encoded %2F must stay encoded), turn off ARR’s reverse rewrite of the host in response headers (otherwise redirects send browsers to the internal address), and serve a certificate with its full chain so git clone works.4

<!-- Illustrative: D:\inetpub\FMPReverseProxy\web.config (excerpt) -->
<configuration>
  <system.webServer>
    <rewrite>
      <rules>
        <rule name="ReverseProxyToGitea" stopProcessing="true">
          <match url="(.*)" />
          <!-- {UNENCODED_URL} keeps the request path exactly as the client sent it -->
          <action type="Rewrite" url="http://127.0.0.1:3000{UNENCODED_URL}" />
        </rule>
      </rules>
    </rewrite>
    <security>
      <requestFiltering>
        <!-- Large pushes and LFS uploads; IIS default is 30000000 bytes -->
        <requestLimits maxAllowedContentLength="524288000" />
      </requestFiltering>
    </security>
  </system.webServer>
</configuration>

Used by every git clone, git fetch and git push against the canonical repositories, every browser session in the web UI, and every REST call.

A.2 SSH Git transport, TCP 2222

Gitea runs its own SSH server; the operating system’s OpenSSH server isn’t installed and port 22 isn’t used. Gitea’s built-in server needs START_SSH_SERVER = true, which defaults to false; DISABLE_SSH = false alone only leaves the SSH feature enabled. SSH_PORT is the port shown in clone URLs and SSH_LISTEN_PORT the port the built-in server listens on.5 Users authenticate with SSH public keys they upload in the web UI or through POST /api/v1/user/keys.6

The SSH plane is equivalent to HTTPS for git operations but bypasses IIS, so it doesn’t appear in the IIS W3C logs. Its audit trail is Gitea’s own log under D:\Gitea\log\, which the conformance adapter reads alongside the IIS log. HTTPS is the default for people (web UI, README, configured push URLs); SSH is for build agents that can’t reach HTTPS through the agency’s authenticating forward proxy, because SSH doesn’t use HTTP proxies.

; Illustrative: D:\Gitea\custom\conf\app.ini (excerpt)
RUN_USER = svc-fmp-gitea$

[server]
PROTOCOL         = http
HTTP_ADDR        = 127.0.0.1
HTTP_PORT        = 3000
ROOT_URL         = https://git.fmp.corp.contoso.com/
DISABLE_SSH      = false
START_SSH_SERVER = true
SSH_DOMAIN       = git.fmp.corp.contoso.com
SSH_PORT         = 2222
SSH_LISTEN_PORT  = 2222
LFS_START_SERVER = true

[service]
DISABLE_REGISTRATION = true
REQUIRE_SIGNIN_VIEW  = true

Family B — identity and authentication

B.1 Active Directory over LDAPS, outbound TCP 636

The path for users whose identity is still only in the forest. Gitea’s LDAP source binds with a least-privilege account, searches only the governed Users OU, and grants administrator rights through an LDAP filter on the canon stewards group. A successful bind creates a Gitea account on first sign-in. With user synchronization turned on, Gitea’s sync_external_users job (on by default, nightly at midnight) also creates new users, updates existing ones and disables users no longer found in the source.15 The host’s own computer account uses Kerberos, separately, for domain services and Group Policy.

# Illustrative: register the AD source with the Gitea CLI (run under the Gitea service identity)
$gitea  = 'D:\Gitea\gitea.exe'
$config = 'D:\Gitea\custom\conf\app.ini'
$bindPw = Get-Secret -Name 'svc-fmp-ldap' -AsPlainText   # Microsoft.PowerShell.SecretManagement

& $gitea --config $config admin auth add-ldap `
    --name 'corp-ad-ldaps' `
    --security-protocol 'LDAPS' `
    --host 'dc01.corp.contoso.com' `
    --port 636 `
    --bind-dn 'CN=svc-fmp-ldap,OU=ServiceAccounts,DC=corp,DC=contoso,DC=com' `
    --bind-password $bindPw `
    --user-search-base 'OU=Users,OU=ORG-IT-INF-PLATFORM,DC=corp,DC=contoso,DC=com' `
    --user-filter '(&(objectCategory=person)(objectClass=user)(sAMAccountName=%[1]s))' `
    --admin-filter '(memberOf=CN=IT-INF-PLATFORM-CanonStewards,OU=Groups,DC=corp,DC=contoso,DC=com)' `
    --username-attribute 'sAMAccountName' `
    --email-attribute 'mail' `

--name, --security-protocol, --host, --port, --user-search-base, --user-filter and --email-attribute are required; the rest are optional.16 Passing the bind password on the command line exposes it to anyone who can read process arguments on the host, so run this once, at build, from the signed runbook.

B.2 Entra ID over OpenID Connect

The federated sign-in path. The build registers an application in the agency’s tenant with sign-in audience AzureADMyOrg, redirect URI https://git.fmp.corp.contoso.com/user/oauth2/EntraID/callback (Gitea’s callback is /user/oauth2/<source name>/callback), and a groups claim in the ID token. Gitea’s OIDC source then uses the tenant’s discovery document.

# Illustrative: register the Entra ID source with the Gitea CLI
$tenantId = '<tenant ID>'
$clientId = '<application (client) ID>'
$secret   = Get-Secret -Name 'fmp-gitea-oidc' -AsPlainText

& $gitea --config $config admin auth add-oauth `
    --name 'EntraID' `
    --provider 'openidConnect' `
    --key $clientId `
    --secret $secret `
    --auto-discover-url "https://login.microsoftonline.com/$tenantId/v2.0/.well-known/openid-configuration" `
    --scopes 'email profile' `
    --group-claim-name 'groups' `
    --admin-group '<object ID of the canon stewards group>' `
    --group-team-map '{"<object ID of the contributors group>": {"fmp": ["Contributors"]}}' `
    --group-team-map-removal

The Gitea options exist as shown;17 check the --group-team-map JSON shape against the reference for your version. Four points follow from how Entra ID issues the claim:

  • groups isn’t a scope. Don’t request openid profile email groups. Group membership comes from the app registration’s groups claim configuration, not from a requested scope; request the ordinary OIDC scopes.
  • The claim carries object IDs. By default the groups claim contains group object IDs, so --admin-group and the team map are keyed by object ID, not display name. Synchronized groups can instead emit sAMAccountName, and cloud-only groups their display name, through optional claim settings.18
  • Overage. If a user is in more than 200 groups, a JWT carries no groups claim at all, only an overage indicator pointing to Microsoft Graph.19 Gitea’s mapping would then see no groups. Configure the claim as Groups assigned to the application, which Microsoft recommends for large organizations, and assign only the groups that map to Gitea roles.20
  • Mapping happens at sign-in. Gitea applies the group-to-team map when the user signs in, and Gitea’s only background sync of external users is the LDAP job in B.1; nothing re-reads OIDC group membership between sign-ins.21 A user removed from a group keeps their Gitea team membership, personal access tokens and SSH keys until they sign in again or someone acts. The leaver step therefore disables the Gitea account directly (PATCH /api/v1/admin/users/{username} with prohibit_login), and the drift reporter flags any Gitea account whose Entra ID user is disabled.

Dynamic groups need Microsoft Entra ID P1.22 A joiner, mover or leaver event doesn’t reach Gitea in minutes. Microsoft says dynamic membership changes are usually processed within a few hours and can take more than 24 hours, depending on the number of groups, the volume of changes and rule complexity.23 For a synced user, the attribute change also waits for a directory sync cycle first. Treat propagation as hours, not minutes, and close the gap for leavers with the direct disable above.

B.4 The host’s own identities

Three identities matter, and they’re different things:

  • The Gitea service account is a group managed service account (CORP\svc-fmp-gitea$). Services configured through the Service Control Manager, IIS application pools and scheduled tasks can all run as a gMSA, and Windows rotates its password automatically.24 Gitea’s own Windows service instructions register the service with sc.exe and run it as the local system account by default, so the service account is set separately (family E).25
  • The Arc managed identity is the host’s identity in Azure. Arc creates a system-assigned managed identity whose tokens come from a local endpoint, http://localhost:40342.26 A local process can request a token only if it can read the challenge file in the agent’s token directory, which is limited to administrators and members of the Hybrid agent extension applications group,27 so the account that runs backups and the drift reporter must be in that group. The managed identity has no Azure permissions until role assignments grant them.
  • A device object in Entra ID isn’t one of them: the host isn’t hybrid joined, so it has no device extensionAttributes to carry its organizational attributes. Microsoft’s supported devices for hybrid join are Windows 11, Windows 10, and Windows Server 2016, 2019 and 2022; Windows Server 2025 isn’t on the list.28 The host’s organizational attributes therefore live as tags on its Arc resource, as Book 01 describes. The underlying distinction still holds where a device object exists: device extensionAttributes are managed only in Entra ID, while a synced user’s onPremisesExtensionAttributes are read-only in Microsoft Graph because their source of authority is on-premises AD.29

B.5 Signed-commit verification

The hook chain rejects unsigned pushes to main, canon/* and any path under the canon directory. D.2 Gitea webhooks

Configured per repository in the web UI or through /api/v1/repos/{owner}/{repo}/hooks, and used for three receivers: the drift engine (push events alongside the scheduled Arc state), the documentation build (pushes under docs/**), and the public mirror’s CI. Gitea signs each delivery with the webhook secret: X-Gitea-Signature carries the hex HMAC-SHA256 of the raw body, and X-Hub-Signature-256 the GitHub-compatible form. It can also send a custom Authorization header, and an earlier delivery can be resent from the delivery history.44 The receiver verifies the signature before acting.

Two cautions. Gitea’s webhook documentation describes manual redelivery of failed deliveries, not automatic retries with backoff, so the drift engine must tolerate a missed event and reconcile from the scheduled poll. And a GitHub repository_dispatch can’t be sent from a Gitea webhook. GitHub’s dispatch endpoint (POST /repos/{owner}/{repo}/dispatches) takes its own body (event_type, optional client_payload) and a token with the repo scope for classic tokens,45 and Gitea’s webhook types don’t include a GitHub dispatch format.46 Send it from the post-receive hook or a small relay, with a narrowly scoped token held in the secret store. That makes it an authenticated outbound call to api.github.com, which belongs on the egress allowlist.

D.3 Drift reporter

Phase 14.4 registers a scheduled task that runs as the gMSA (scheduled tasks support gMSAs)47 and authenticates to Azure and Graph with the Arc managed identity, so no interactive credential lives on the host. It collects the Arc resource’s tags, the Gitea team list, administrative-unit membership through Graph, the Arc agent’s last heartbeat, and the Gitea accounts whose Entra ID users are disabled, then submits them to the drift engine, which reports DRIFT-SCHEMA, DRIFT-SEMANTIC, DRIFT-PROVENANCE, DRIFT-AUTHZ and DRIFT-IDENTITY findings. Non-zero counts open service-level tickets. The build guide marks this Phase 14 capability as declared but still under operational validation.

D.4 Conformance adapter

The program’s rule is that GitHub is where canon is ingested and the on-premises repository is where canon is authoritative: a commit pushed to GitHub isn’t canon until it has been accepted on the host. Mirrored commits don’t pass through the hook chain that governs operator pushes: a pull mirror updates by fetching, the receive hooks run only on pushes,57 and a pull mirror is read-only: it changes only when it syncs from its upstream,58 and Gitea refuses pushes to a mirror repository over both HTTPS and SSH.59 So the mirror (fmp-upstream above) is a quarantine copy, and canon moves into the authoritative repository only by a push or merged pull request from it, which runs the hook chain and the branch protections. The drift reporter flags any difference between the two that hasn’t been promoted.

Group governance

Gitea roles map to three groups:

Gitea role Group
Owner IT-INF-PLATFORM-CanonStewards
Write IT-INF-PLATFORM-Contributors
Read IT-INF-Users

These groups are driven by user attributes, and a synced user’s attributes are written in on-premises AD and reach Entra ID through directory sync before any group recalculates. The attributes have exactly one writer, the governance plane, and drift against it is a finding, not an accepted edit. A move in the HR feed reaches Gitea after directory sync, dynamic group processing (B.2) and the user’s next sign-in, so the program measures it in hours and handles leavers directly. The group mapping is part of Phase 14, which the build guide marks as under operational validation. Book 03, Chapter 08 covers the joiner-mover-leaver flow.

The program’s key security indicator library tests this host’s posture on every evaluation run: continuous-monitoring presence and freshness (CA-7), repository and TLS inventory completeness (CM-8), IIS log presence and retention (AU-2, AU-6), and monitoring evidence freshness (SI-4). A failure opens a service-level ticket and gates the next authorization review.

Closing position

Every plane in the six families is one of four kinds:

  1. Inbound and gated by IIS, Gitea’s OIDC or LDAPS sources, or the firewall’s subnet allowlist.
  2. Outbound and pinned to a host name on the egress allowlist.
  3. Local and signed, with application control refusing anything the program didn’t sign.
  4. Telemetry, observed by the conformance adapter and reported to the drift engine.

Anything outside that list is a finding: DRIFT-SCHEMA if a plane appeared without a recorded decision, DRIFT-PROVENANCE if its origin can’t be traced, DRIFT-AUTHZ if its authorization drifted from the group mapping. The host is governed by the closure of this list, not by the absence of incidents.
