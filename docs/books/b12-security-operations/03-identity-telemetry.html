Chapter 03 — Identity Telemetry from Entra ID

How to emit Microsoft Entra ID audit, sign-in, provisioning, Graph activity and ID Protection logs through diagnostic settings: which categories to enable and why, the Log Analytics table each lands in, deploying the setting by portal, tenant-scope Bicep or az rest, retention that satisfies the logging baseline, sovereign-cloud endpoints, and Microsoft Graph as targeted evidence rather than the feed.

Identity is the first plane an attacker touches and the first one a defender loses sight of, because Entra ID keeps its own logs for only a month unless someone deliberately sends them somewhere.

NoteIn this chapter

Which Microsoft Entra ID log categories exist, which Log Analytics table each lands in, and which ones the program enables in every tenant. How to deploy the tenant-scope diagnostic setting by portal, Bicep or az rest, why the retention block on that setting does nothing, and how to prove emission is working. It closes with the endpoint changes for GCC High and DoD, and with Microsoft Graph’s audit APIs as a tool for pulling specific evidence, not for feeding a SIEM.

Chapter 02 set the rule that every plane emits deliberately, under one evidence contract. Identity comes first because it is the join key for almost everything else: a mailbox read, a Key Vault secret retrieval and a role assignment all trace back to a sign-in. It is also the plane where the default is most misleading. Entra ID records audit and sign-in activity whether or not anyone configures anything, and the admin center shows it. That makes the tenant look instrumented. But with Entra ID P1 or P2, audit and sign-in data is kept for 30 days (seven days on the Free tier), Microsoft Graph activity logs aren’t kept at all unless they are routed somewhere, and an upgrade never recovers data that already expired.1 An agency that hasn’t created a diagnostic setting has a rolling 30-day window of identity history and nothing older.

The mechanism that fixes this is the Entra diagnostic setting: a tenant-level object that streams selected log categories to a Log Analytics workspace, an Event Hubs namespace, a storage account or a partner solution.2 This chapter is about getting that one object right, keeping it right, and proving it works.

Before you start

Requirement Detail
Role Security Administrator on the tenant, to create or edit a diagnostic setting.3
Custom security attributes The CustomSecurityAttributeAuditLogs category is configured separately, on the Custom security attributes tab, and needs Attribute Log Administrator as well as Security Administrator.4
Destination The workspace, event hub or storage account must exist before the setting is created.5
Event Hubs tenancy The subscription and Event Hubs namespace must both be associated with the Entra tenant whose logs are streamed.6
Licensing Microsoft Graph activity logs need Entra ID P1 or P2.7 Microsoft Sentinel’s Entra ID connector needs P1 or P2 to ingest sign-in logs, and Workload ID Premium for the two service-principal risk tables.8

The log categories and their tables

The category name you tick in the diagnostic setting is not always the table name you query. Microsoft says so directly in the ID Protection export guidance: the names in diagnostic settings “are not the same as the table names” used in KQL, and most of the tables carry an AAD prefix.9 The mapping isn’t mechanical (SignInLogs lands in SigninLogs, with a lowercase i), so detection rules and retention settings must name the table, not the category.

The tier column is the program’s design: Core categories carry the event-logging, record-content and record-generation evidence (NIST SP 800-53 AU-2, AU-3 and AU-12)10 for every tenant regardless of which features it uses; High value categories need ID Protection licensing; Conditional categories produce data only when a feature is deployed.

Category names and descriptions are from Microsoft’s list of identity logs that can be streamed;11 table names from the Sentinel Entra ID connector reference,12 the ID Protection export mapping (including the agent risk tables)13 and the Azure Monitor table reference for custom security attributes.14 Microsoft recommends sending custom security attribute logs to a different destination from the directory audit logs, so attribute assignments aren’t revealed by accident, and only Attribute Log Reader or Attribute Log Administrator can read them.15 The program routes them to a separate workspace with narrower access.

WarningLeave MicrosoftServicePrincipalSignInLogs off

Microsoft describes these preview logs as complex and high in volume, says they are “not essential for security investigations,” and strongly advises against acting on them, for example by disabling applications, because that can cause misconfiguration and even tenant lock-out.16 They cost money to ingest and invite exactly the wrong response. The program doesn’t enable them.

Why all four sign-in streams are core

SignInLogs covers only interactive human sign-ins. It doesn’t see a client app refreshing a token for a user, a service principal authenticating with a client secret, or a managed identity reading from Key Vault. Those are the other three sign-in categories, and they are where unattended credentials (the ones nobody is watching) do their work. A tenant that streams only SignInLogs is blind to every non-human authentication in the estate while appearing, on the sign-ins blade, to be fully instrumented.

The cost argument against them is real but doesn’t change the answer. Microsoft notes that non-interactive and service-principal sign-ins can be five to ten times larger than interactive ones.17 Graph activity logs are larger again: Microsoft’s own planning estimate is about 15 GiB a month of Azure Monitor Logs data for a 1,000-user tenant and about 1,200 GiB for 100,000 users, and diagnostic settings can’t filter them, although a workspace transformation or the Basic table plan can reduce cost.18 The program’s position is that volume is managed with table plans and transformations, never by leaving a sign-in stream off. Microsoft Graph activity logs are what show what a compromised account or app actually did with its token, and Microsoft recommends routing them to the same workspace as the sign-in logs so the two can be joined.19

Path A: the portal

For a one-time setup in a lab or a first tenant:

  1. Sign in to the Microsoft Entra admin center as at least a Security Administrator.
  2. Browse to Entra ID > Monitoring & health > Diagnostic settings. (Export Settings on the Audit Logs or Sign-ins page reaches the same place.)20
  3. Select Add diagnostic setting.
  4. Enter a name. The name can’t be changed when the setting is edited later,21 so choose one an assessor will recognize, such as fmp-siem-emission-core.
  5. Select the Core categories, plus the High value categories if ID Protection is licensed.
  6. Under Destination details, choose Send to Log Analytics workspace (and, for a non-Microsoft SIEM, Stream to an event hub), then the subscription and destination.
  7. Select Save.22

Don’t judge success in the first hour. Microsoft’s general guidance is that logs can take up to three days to start appearing in the destination; its ID Protection guidance suggests around 15 minutes for the risk tables.2324 Graph activity logs usually arrive within 30 minutes and occasionally take up to two hours.25 The verification query later in this chapter is run at 24 hours and again at 72.

NoteThe portal is right for the first tenant and wrong for the fleet

A setting someone clicked once has no source of truth, no review trail and no drift detection. FedRAMP’s Consolidated Rules for 2026 include KSI-MLA-EVC, Evaluating Configurations, which expects the configuration of machine-based information resources, especially infrastructure as code, to be continuously evaluated and tested, and KSI-MLA-LET, which expects a current list of the event types that will be logged.26 The program deploys the Entra setting from code (Path B or C), keeps the category list in the repository as that list, and compares the deployed setting against it on a schedule.

Path B: tenant-scope Bicep

Entra diagnostic settings are the Azure Resource Manager resource type microsoft.aadiam/diagnosticSettings, API version 2017-04-01, and they deploy only at tenant scope.27 That is why the usual resource-scope tooling doesn’t reach them.

WarningIllustrative code

The templates, scripts and queries in this chapter are illustrative. They haven’t been tested against a production tenant. Retention: what the logging baseline asks for

OMB M-26-14 rescinded M-21-31 and set a minimum baseline: retained logs must be searchable for at least six months after creation and retrievable for a year. The memo defines the two words. Searchable data “can be immediately used for cyber defense,” with no preparation step; retrievable data can be used after one or more intermediate steps, such as replaying it from long-term storage.32 The baseline also lists the activities logs must support, including “determining the identity used for performing operations” and “identifying actions that affect changes to privilege levels.”33 Entra audit and sign-in logs are the primary evidence for both.

A Log Analytics workspace maps onto those definitions cleanly. Tables on the Analytics plan keep data in analytics retention, where it can be queried immediately, for up to two years; total retention, which adds low-cost long-term retention, can run to 12 years, and data in the long-term portion is reached through a search job.34 The default for most tables is 30 days.35 The program’s design for every identity table above:

Setting Value Why
Analytics retention At least 180 days Immediately queryable: M-26-14’s searchable
Total retention At least 365 days, longer where a records schedule requires it Long-term retention reached by search job: retrievable
Table plan Analytics for tables that detections query; Basic considered only for high-volume tables (Graph activity) that are hunted rather than alerted on Cost managed by plan, not by leaving categories off

Retention is set per table, by portal, az monitor log-analytics workspace table update with --retention-time and --total-retention-time, or Update-AzOperationalInsightsTable.36 Shortening a table’s total retention takes effect only after a 30-day wait, which protects against mistakes; lengthening it applies to data already in the table.37 The Entra admin center’s own 30-day window is no substitute: it is a viewing convenience, not evidence storage.

Microsoft Graph: targeted evidence, not the feed

Graph’s auditLogs APIs answer the question show me this specific thing: who granted this role, which sign-ins this app made last Tuesday. They are the wrong tool for continuous collection, and Microsoft says so: the API “isn’t designed for pulling large amounts of activity data,” and doing so “might lead to issues with pagination and performance.”44 Graph also returns only what Entra still holds, which is the 30-day default window with P1 or P2.4546 The diagnostic setting is the feed; Graph is the magnifying glass.

Permissions

AuditLog.Read.All is the least-privileged permission, delegated or application, for listing both directory audits and sign-ins; getting a single directory audit item needs AuditLog.Read.All and Directory.Read.All.53 For delegated access the signed-in user also needs a supporting role: Reports Reader, Security Reader or Security Administrator for directory audits, with Global Reader and Security Operator also supported for sign-ins.5455

WarningConditional Access results are separately gated, and silently omitted

The appliedConditionalAccessPolicies property is left out of a signIns response unless the caller can read Conditional Access data: for an app, Policy.Read.All, Policy.Read.ConditionalAccess or Policy.ReadWrite.ConditionalAccess; for a user, a role such as Global Reader, Security Reader, Security Administrator or Conditional Access Administrator.56 Nothing in the response says the property was dropped. An evidence pull built without one of those permissions produces sign-in records that look complete and contain no Conditional Access evaluation, which is exactly what account management and least-privilege assessment (AC-2 and AC-6) turn on.57 Grant the narrowest of the three, Policy.Read.ConditionalAccess, to every evidence-collection app that reads sign-ins.

Verify emission

A setting that saved without error is not proof that logs are arriving. The program runs the query below against the destination workspace 24 and 72 hours after any change, and daily thereafter. It compares an explicit list of expected tables with what actually arrived, so a table that never received data shows up as a row marked MISSING instead of silently disappearing from the results. It uses union isfuzzy=true, which lets the query run when some of the named tables don’t exist yet; without it, a single missing table makes the whole query fail.63

// Entra diagnostic-setting completeness.
// Pass: every expected table returns Status == "OK".
let expected = datatable(TableName: string) [
    "SigninLogs", "AADNonInteractiveUserSignInLogs",
    "AADServicePrincipalSignInLogs", "AADManagedIdentitySignInLogs",
    "AuditLogs", "AADProvisioningLogs", "MicrosoftGraphActivityLogs",
    "AADRiskyUsers", "AADUserRiskEvents"
];
let observed = union isfuzzy=true withsource=TableName
    SigninLogs, AADNonInteractiveUserSignInLogs,
    AADServicePrincipalSignInLogs, AADManagedIdentitySignInLogs,
    AuditLogs, AADProvisioningLogs, MicrosoftGraphActivityLogs,
    AADRiskyUsers, AADUserRiskEvents
    | where TimeGenerated > ago(7d)
    | summarize RecordCount = count(), LastRecord = max(TimeGenerated) by TableName;
expected
| join kind=leftouter observed on TableName
| project TableName, RecordCount, LastRecord,
    Status = case(isnull(LastRecord), "MISSING",
                  LastRecord < ago(24h), "STALE",
                  "OK")
| order by Status asc, TableName asc

MISSING means the category was never enabled, was enabled against a different workspace, or (for the risk tables) has had nothing to report; check the GET output from Path C before concluding anything. STALE is the more dangerous result: emission worked and then stopped, and any query over a wide time range will keep returning the old data and hide the gap. Some tenants legitimately produce no provisioning or risk events in a quiet week, so the program records an expected-quiet exception for those tables rather than lowering the bar for the sign-in tables.

Where the workspace is Microsoft Sentinel, its Microsoft Entra ID data connector writes these same categories to these same tables, and needs read and write permission on the Entra diagnostic settings to show its status.64 The program still treats the tenant diagnostic setting, deployed from code, as the control of record, and checks for duplicate settings sending the same categories to the same workspace. How the tables become detections is Chapter 05, and the control-level detail is in the compliance volume Vol III Book 06, SIEM, XDR and Detection.

Privacy: identity telemetry is PII

Every record this chapter collects is about a person. A sign-in event identifies the user by name, username and user ID, and records the application and resource, the IP address and an approximate location, and the browser, operating system and compliance state of the device.65 Under A-130’s definition that is personally identifiable information, and a workspace holding a year of it is a profile of each worker’s day.66 M-26-14 sets what to log and for how long; it doesn’t address privacy, and the Privacy Act and A-130 apply to the logs as to any other PII. Where the agency retrieves log records by a person’s name or identifier, they are records in a system of records, and the privacy office decides which notice covers them.67

Three controls in the privacy baseline, which applies at every impact level, shape the design: AU-3(3) limits the PII in audit records to the elements the agency names, PT-3 confines processing to its documented purposes, and SI-12 governs retention and disposal.68 The program’s position is that identity logs are collected for security monitoring and incident response, and that using them to measure an individual’s productivity or attendance is a new purpose that needs the privacy office’s approval first. Pipelines the program writes log the enterprise person key and a hash, not names or payloads (Book 03, Appendix B); Microsoft’s logs arrive as Microsoft defines them, so access to the workspace is the control that matters there. Book 03, Chapter 14 covers the wider obligations.

Obligation What the engineer does Who signs off

What this chapter doesn’t cover

Entra diagnostic settings emit identity events. They don’t emit Azure control-plane or resource activity, and they don’t emit the Microsoft 365 unified audit log; both are Chapter 04. Conditional Access and PIM policy design, which produce many of the events logged here, is Book 04. Telemetry that the authorization boundary itself blocks, and its compensating controls, is a boundary question for Book 10.
