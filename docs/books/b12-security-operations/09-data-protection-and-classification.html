Chapter 09 — Data Protection and Classification

Why network and identity controls can’t tell a press release from a Privacy Act record, what the federal CUI framework in 32 CFR Part 2002 actually defines, how the program maps CUI Basic and CUI Specified to Microsoft Purview sensitivity labels and deploys the taxonomy as code, how DLP enforces label-derived signal on the service, the endpoint and the network, how customer-managed keys, BYOK and Double Key Encryption differ, and why a CASB alone can’t close the payload gap.

Every control in the pipe can be satisfied while the payload leaves, because nothing upstream ever said what the payload was.

NoteIn this chapter

The classification gap that remains after network and identity hardening, and why a cloud access security broker (CASB) can’t close it alone. What the federal CUI framework in 32 CFR Part 2002 and the CUI Registry actually define, and how the program maps CUI Basic and CUI Specified to Microsoft Purview sensitivity labels, deployed as code. Automatic labeling, DLP on three enforcement surfaces, and the three different things “customer-managed key” can mean in Microsoft 365, with each feature’s availability in GCC and GCC High checked on Microsoft Learn.

Network controls decide which paths traffic can take. Authentication decides who is asserting an identity, Conditional Access decides whether that identity may reach a workload from a given device, and privileged access management decides how long an administrator holds elevated scope. Book 09, Book 02 and Book 04 build those controls. None of them answers a different question: what is in the file?

A user who is legitimately authenticated, on a compliant device, sending a file to an approved destination passes every one of those controls. If the file holds a Social Security number list extracted for a workflow, it leaves anyway, because nothing upstream identified it as sensitive before it moved. This chapter closes that gap with three coordinated mechanisms: a classification taxonomy enforced through sensitivity labels, DLP policies that act on the label and on content inspection, and encryption under keys the agency controls. They are the data-layer contributions to AC-4, the AC-16 attribute controls, MP-3, SC-12, SC-13 and SC-28.

The classification gap

An assessment of a Microsoft 365 tenant that has finished network and identity hardening, but has no classification program, finds the same structural gaps from agency to agency. They are framing patterns drawn from the program’s assessments, not findings from a named engagement.

  • No classification scheme. Documents carry no labels. Sensitivity, where it’s recorded at all, lives in a file name, a free-text metadata field or a folder name, none of which a control can read or enforce.
  • Sharing is set per container, not per document. SharePoint external sharing is configured for a site or library, so a CUI document and a public document in the same library get the same policy.
  • No DLP on Teams. A Social Security number pasted into a Teams chat reaches the service without any rule looking for it.
  • Keys without an owner. Database encryption keys, certificate private keys and application secrets sit in configuration files, local certificate stores or individual subscriptions, with no central inventory, rotation policy or access audit. Nobody can show whether keys were rotated after an administrator with access left.
  • Access is granted to containers. Read access to a site is read access to everything in it, whatever its sensitivity.

Why CASB alone is insufficient

A CASB sees the application, the user, the device’s compliance state, the destination and the volume. It enforces access policy on those signals (Book 09, Chapter 05 places it in the SASE design). What it can’t do by itself is tell a released press statement from a Privacy Act record. Without a classification on the file it can apply only coarse policies, such as blocking all uploads to consumer storage or all downloads above a size, and it can’t enforce “block external sharing of CUI” because it can’t tell which files are CUI.

The sensitivity label supplies that signal. Microsoft describes the label as stored “in clear text in the metadata for files and emails,” so third-party apps and services can read it, and as persistent: it “stays with the content, no matter where you save or store it.”1 (An earlier draft of this program said the label travels as an encrypted property; that is wrong. The label is readable; the content is what label encryption protects.) Defender for Cloud Apps session policies can filter on the label: block the download of labeled files to unmanaged devices, or block the upload of a file that contains sensitive data and doesn’t carry the right label.2 Purview classifies; the CASB enforces on the classification. They work on different layers, and neither substitutes for the other.

The federal CUI framework

The framework for unclassified federal information that needs protection is Executive Order 13556, which designates the National Archives and Records Administration as the CUI Executive Agent; NARA’s Information Security Oversight Office issued 32 CFR Part 2002 to implement it.3 Four provisions shape any label design:

  1. CUI is the only lawful category of controlled unclassified information. “All unclassified information throughout the executive branch that requires any safeguarding or dissemination control is CUI,” and agencies “may not implement safeguarding or dissemination controls for any unclassified information other than those controls consistent with the CUI Program.”4
  2. There are two control levels, not four. CUI Basic is CUI whose authorizing law, regulation or policy “does not set out specific handling or dissemination controls.” CUI Specified is CUI whose authority “contains specific handling controls that it requires or permits agencies to use that differ from those for CUI Basic.”5 Everything else is uncontrolled unclassified information, which “agencies must still handle … in accordance with” FISMA.6
  3. CUI sets a confidentiality floor. Systems that process, store or transmit CUI Basic are categorized at “no less than the moderate confidentiality impact level,” with NIST SP 800-53 controls applied.7 NIST SP 800-171 is the requirement set for CUI on non-federal systems.8
  4. Marking is prescribed. Every CUI item carries a banner marking whose control marking is “CUI” (or “CONTROLLED”); category markings are mandatory for CUI Specified and optional for CUI Basic unless agency policy requires them; and “authorized holders who designate CUI may not use alternative markings.”9

The CUI Registry decides which category a record falls in and whether its authority is Basic or Specified. Three examples from the registry correct the program’s earlier drafts:

CUI Registry entries that drive the label design
Information Registry category Basic or Specified Banner marking
Privacy Act records (5 U.S.C. 552a(b)) Privacy (PRVCY) Basic CUI, or CUI//PRVCY where agency policy requires category markings10
Federal taxpayer information (26 U.S.C. 6103) Federal Taxpayer Information (TAX) Specified CUI//SP-TAX11
Health information Health Information (HLTH) Specified or Basic, depending on the authority CUI//SP-HLTH for specified authorities, CUI for basic ones12
Law enforcement techniques and procedures General Law Enforcement (LEI) Basic for the authorities listed CUI or CUI//LEI13

Two of the program’s earlier assumptions don’t survive that reading. Privacy Act records aren’t CUI Specified: the registry lists 5 U.S.C. 552a(b) as a Basic authority, so a “CUI Specified — Privacy Act” label with a CUI//SP-PRVCY banner would mark them wrongly. And “Internal” and “Law Enforcement Sensitive” aren’t CUI categories. “Internal” is the program’s name for uncontrolled unclassified information that isn’t cleared for release; it may not carry a dissemination control of its own.

Mapping CUI to sensitivity labels

The program’s label taxonomy is a design built on that framework. The parent and sublabel structure follows Purview: a parent label groups sublabels, and the sublabel carries the protection.14

The program’s CUI label taxonomy (design)
Tier Label (parent / sublabel) Content marking Encryption Who can open it
Public Public None None Anyone
Uncontrolled, not for release Internal None (no CUI or dissemination legend) None Not restricted by the label
CUI Basic CUI / CUI Basic Header CUI Yes, tenant key Everyone in the agency’s tenant
CUI Basic with category marking (where agency policy requires it) CUI / CUI//PRVCY Header CUI//PRVCY Yes, tenant key Everyone in the agency’s tenant
CUI Specified CUI / CUI//SP-TAX (one sublabel per specified authority the agency holds) Header with the category marking Yes, tenant key; Double Key Encryption for the narrowest set A named, mail-enabled security group of authorized holders

Three rules come with the taxonomy:

  • Use groups, not people. Encryption permissions can be granted to “any specific user or email-enabled security group, distribution group, or Microsoft 365 group,” but not to a security group that isn’t email-enabled.15 Holders of a specified category are a group whose membership the identity lifecycle maintains (Book 03).
  • Don’t let records expire by default. A label can set encrypted content to expire after a number of days.16 For federal records under a retention schedule, an expiry date is a decision for the records officer, not a default.
  • The label carries the banner. The header marking is how the program applies the CUI banner on screen and on paper. Content markings are inserted by Office apps, while labels applied by services such as SharePoint auto-labeling apply the metadata and encryption without inserting the marking until the file is relabeled in an Office app.17

The label taxonomy as code

The taxonomy is declared, reviewed and deployed from source control, not clicked into the portal, so that the protection settings at each tier are visible in review and identical across environments. The same applies to label policies, auto-labeling and DLP. The program’s pipeline treats each as a versioned artifact, and a change goes through review like any other configuration (Chapter 07).

Automatic labeling

Manual labeling puts the classification decision on the author. Authors label the obviously sensitive document correctly and miss the routine one: a spreadsheet of Social Security numbers extracted for a workflow, or a chat message with a taxpayer number sent while answering a question. Automatic labeling classifies on content, whether or not the author recognized it as sensitive.

Sensitive information types

Sensitive information types (SITs) are pattern classifiers. The built-in U.S. types include U.S. social security number (SSN), U.S. individual taxpayer identification number (ITIN), U.S. bank account number, U.S. driver’s license number and U.S./U.K. passport number, plus Drug Enforcement Agency (DEA) number and IP address.22 There is no built-in U.S. employer identification number (EIN) type, so EINs need a custom SIT, as do agency identifiers such as case or claim numbers. Custom SITs are defined as XML rule packages and imported with New-DlpSensitiveInformationTypeRulePackage -FileData.23 An earlier program script built the rule package as a PowerShell hashtable converted to JSON; that format isn’t accepted.

Trainable classifiers

For categories that have no pattern, such as case notes, budget working papers or policy drafts, trainable classifiers use machine learning. Microsoft provides pretrained classifiers. A custom classifier needs “at least 50 positive samples (up to 500) and at least 150 negative samples (up to 1,500),” supports English only and is seeded from dedicated SharePoint folders.24 Draw the samples from the real document population, informal documents included; a classifier trained only on formally formatted documents will miss the rest.

Auto-labeling policies

Service-side auto-labeling labels content at rest in SharePoint and OneDrive and messages in Exchange. Client-side labeling in Office apps recommends or applies a label as the author works. Both are available in GCC and GCC High, along with machine learning classifiers for client-side auto-labeling.2526

# Service-side auto-labeling for SharePoint and OneDrive, in simulation first.
New-AutoSensitivityLabelPolicy -Name 'FMP-Auto-CUI-Basic' `

$ssn = @(@{ Name = 'U.S. Social Security Number (SSN)'; minCount = '1'; minConfidence = '85' })

A false-positive spike that stamps CUI Specified on routine documents becomes a help desk event across the agency.

Keys the agency controls

“Bring your own key” means three different things in Microsoft 365, and an assessor will ask which one the system security plan means. All three are listed as available in GCC and GCC High.3940

Three meanings of “customer-managed key” in Microsoft 365
Option What it protects Where the key lives What the agency gives up
BYOK for the Azure Rights Management root key Every item protected by label encryption, tenant-wide. The tenant key is “your organization’s root key” for that encryption service, and other keys chain to it.41 An RSA 2048-bit key in the agency’s Azure Key Vault (Premium for HSM protection), ideally a dedicated vault; the service needs get, decrypt and sign on it42 Nothing functional; it adds a key the agency must keep available
Microsoft Purview Customer Key Service encryption at rest for Exchange, SharePoint and OneDrive, and multiple workloads, through data encryption policies Two keys in two Azure Key Vaults in two separate subscriptions, per workload43 Nothing functional; it adds two vaults per workload and strict key hygiene
Double Key Encryption (DKE) Only the content labeled with a DKE label One key in the agency’s own DKE service, one in Azure; “viewing data protected with Double Key Encryption requires access to both keys”44 eDiscovery, search and indexing, Office for the web and coauthoring, and Copilot for that content45

That table corrects the program’s earlier label mapping, which showed “AIP BYOK” as a per-tier encryption setting. BYOK replaces the tenant root key for every encrypted label at once; it doesn’t distinguish CUI Basic from CUI Specified. The per-label key choice is DKE, and Microsoft positions it for the small set of “highly sensitive” content that justifies losing those services.46 The program’s design is BYOK or Microsoft-managed for the tenant key, Customer Key where the authorizing official requires agency-held keys for service encryption at rest, and DKE only for the narrowest CUI Specified categories whose authority demands it.

Customer Key has rules that an ordinary key-rotation policy would break:

  • Each vault must have soft delete and purge protection enabled at creation with a 90-day retention period.47
  • Keys must be RSA (up to 4,096 bits), and Customer Key “can’t use expired keys”: the onboarding service “only accepts keys without an expiration date,” and Microsoft cautions against setting one.48
  • Microsoft keeps an availability key that lets the service recover if both customer keys are lost; its use is logged in the unified audit log as CustomerKeyServiceEncryption with the activity “Fallback to availability key.”49

A rotation policy that sets an expiry, appropriate for an Azure SQL protector, will cause an outage if applied to a Customer Key key.

Azure workloads: Key Vault and TDE with a customer-managed key

For Azure workloads, the customer-managed key sits in Key Vault Premium or Managed HSM. Microsoft states that Premium HSM-protected keys are “generated and protected by FIPS 140-3 Level 3 validated Marvell LiquidSecurity HSMs,” and Managed HSM is a single-tenant FIPS 140-3 Level 3 service whose security domain the customer holds.5051 SC-13 is a property of the validated module, so check the CMVP certificate for each one. FIPS 140-2 certificates moved to the CMVP Historical List in September 2026; NIST says the CMVP “supports the purchase and use of these modules for existing systems,” so a 140-2 module in an existing system isn’t automatically noncompliant, but new procurements should rely on 140-3 modules.52

Keys on other clouds

Key custody is per platform. Each provider runs its own key management service, and a key in one doesn’t protect data in another. AWS Key Management Service and AWS CloudHSM, for example, appear in the certified-services lists of both AWS FedRAMP offerings.57 The program’s position is that classification and DLP policy can coordinate across the estate, while key custody stays native to each platform and is unified only at the governance layer: an inventory of which keys protect which classified data, emitted under the evidence contract. Purview’s labeling for multicloud data sources through the Data Map is in preview, so the program doesn’t yet rely on it for evidence.58

Non-repudiation is a separate question

The program’s earlier drafts argued that Purview Audit (Premium) satisfies AU-10’s irrefutability standard through signed records in storage tenant administrators can’t reach. Microsoft doesn’t describe the product that way. It documents Audit (Premium) as audit log retention policies, longer retention (one year by default for some workloads, up to ten years with an add-on), intelligent insights such as MailItemsAccessed and search events, and higher bandwidth to the Management Activity API.59 None of those is a non-repudiation mechanism, and the claim has been removed.

AU-10 is in the NIST SP 800-53B High baseline and not the Moderate baseline.60 An agency that adopts it above the Moderate floor needs a design for it: exporting the high-value events this chapter and Chapter 04 name into write-once storage that tenant administrators can’t alter, with the export itself evidenced. That is program design. Chapter 04 carries audit retention and the license that decides it.

The certificate practice statement the source volume pairs with SC-17 belongs to the PKI: Book 07, Chapter 05 covers the certificate policy and trust anchors, and the full RFC 3647 outline stays in the Federal Compliance volume linked below.

Deployment sequence

The order matters because each step depends on the one before it. It is the program’s design:

  1. Decide the key options first. Choose Microsoft-managed or BYOK for the tenant key, whether Customer Key applies, and which categories, if any, need DKE, before labels encrypt production content.
  2. Deploy the taxonomy as code to a pilot. Publish labels to a pilot group, confirm markings and encryption in Office apps and in SharePoint, then widen the policy.
  3. Run auto-labeling and DLP in simulation, then enforce. Measure false positives against real content before any policy acts.
  4. Turn on the detections. Label downgrade, mass label removal and DLP override patterns (FMP-DET-05 and FMP-DET-06) go to the SIEM before enforcement begins (Chapter 11).
  5. Set audit retention to the requirement. Licenses and retention policies decide how long label and DLP events survive (Chapter 04).

Honest limits

  • Auto-labeling is only as accurate as its classifiers. Manual labeling discipline and the label-removal detection compensate for mislabeled or stripped content.
  • Agency-held keys move the burden of custody to the agency. Rotation, backup and recovery become the agency’s job, and a deleted key without a backup is unrecoverable data.61
  • DLP restricts the movement of content it matches. It doesn’t model behavior; insider risk and detection engineering cover what pattern matching misses.

What to take from this chapter

  1. Network and identity controls regulate the pipe. Only classification tells any control what the payload is, and a CASB can enforce on it only once the label is there.
  2. The CUI framework has two control levels. Basic or Specified is decided by the authority in the CUI Registry, not by how sensitive the content feels: Privacy Act records are CUI Basic, federal taxpayer information is CUI Specified.
  3. Non-CUI information can’t carry a dissemination control of its own. “Internal” is a label for uncontrolled information, not a fifth control level.
  4. Deploy labels, auto-labeling and DLP as code, simulate before enforcing, and watch the override path once enforcement starts.
  5. BYOK, Customer Key and Double Key Encryption are three different choices. Only DKE is per label, and it costs search, eDiscovery, coauthoring and Copilot for that content.
  6. Customer Key keys must never expire. A rotation policy written for an Azure SQL key will break Microsoft 365 if applied to them.
