Chapter 11 — Detection Engineering and Response Automation

How the program builds and keeps a detection rule library inside its own authorization boundary, manages it as code through a tested lifecycle, and turns firings into bounded response: a confidence-gated response ladder on Book 01’s actuation rungs, playbooks for session revocation, account and device containment, approval gates, an incident response plan an assessor can test, and the limits of all of it.

A rule that fires without a response shortens the time to know, not the time to contain; a response that acts without a gate turns a noisy rule into an outage.

NoteIn this chapter

The in-boundary principle that lets the program rebuild detections it cannot inherit, and the rule library that results, kept as code with example queries verified against current table schemas. How a rule moves from authoring through testing and an alert-only tuning window into production, and how the library is kept from rotting. Then response: the confidence-gated ladder mapped onto Book 01’s actuation rungs with gated actuation (L3) as the default, playbooks for session revocation, account disablement and device isolation, the approval gates around them, the incident response plan they sit inside, and the honest limits.

Chapter 05 built the connector fabric and argued that a workspace with no rules is a warehouse. This chapter carries the rules and the response. It consolidates two Federal Compliance volumes, Vol VI Book 03, Detection Engineering and Vol VI Book 04, Response Automation, with the detection and incident-handling parts of Vol III Book 06. The volumes stay in the repository for control-level depth.

The in-boundary principle

Some of the richest detections a modern cloud offers are computed in the vendor’s multi-tenant analytics: risk scoring trained on signals from many customers, travel and location anomalies, behavioral data-loss analytics. Microsoft describes Entra ID Protection, for example, as drawing on trillions of anonymized signals a day.1 An agency should use those detections wherever they are available in its cloud and within its authorization. But two things can put one out of reach. The capability may not exist in the agency’s cloud: Microsoft lists Sentinel’s peer and blast-radius UEBA enrichments, its threat intelligence matching analytics and SOC optimization as unavailable in Azure Government, for instance.2 Or the authorization decision may keep a given flow of identity-attributed telemetry from leaving the boundary for a service outside it. Book 10 explains how to tell those cases apart.

The program’s principle for both, which the source volume stated and this book keeps as design: the boundary constrains where raw telemetry may go, not whether it may be analyzed. Routing the same telemetry to the agency’s own analytics workspace, inside its own authorized boundary, is exactly the in-boundary monitoring SI-4 contemplates. So where a vendor analytic is unavailable, the program reconstructs a deterministic equivalent: a rule, a baseline, a watchlist, running on telemetry the connector fabric already lands. Every component the rebuilt detection depends on, the workspace and any compute that trains a baseline, must itself be inside the boundary. The moment the telemetry is shipped somewhere out of scope for convenience, the library has recreated the flow the boundary was drawn to prevent.

Reconstruction is not parity. The rebuilt detections see one tenant, not many; they run at rule cadence, not continuously; and their thresholds are the agency’s own guesses until tuned. The honest limits at the end of this chapter say so in the form an assessor can read.

A rule library as code

The rule library is a version-controlled set of analytics rules, each with its query, schedule, entity mappings, MITRE ATT&CK tactics and techniques, severity, tuning notes and the controls it operationalizes. Microsoft’s own rule templates use the same shape: a YAML file with an id, name, description, severity, requiredDataConnectors, queryFrequency, queryPeriod, triggerOperator, triggerThreshold, tactics, relevantTechniques, query, entityMappings and version.3 Keeping the program’s rules in that format means Microsoft’s templates and the program’s rules can be reviewed side by side, and a template Microsoft updates can be diffed against the program’s tuned copy.

The library is the source of truth, not the portal. Sentinel’s Repositories feature connects a workspace to a GitHub or Azure DevOps repository and deploys analytics rules, automation rules, hunting queries, parsers, playbooks, workbooks and (in preview) Defender custom detection rules from it; content deployed that way overwrites changes made in the portal.4 Repositories is in public preview and is not available in Azure Government.5 Where it is unavailable or not authorized, the program deploys the same content through its own change-controlled pipeline using the Azure Resource Manager templates that Sentinel’s export feature produces, which Microsoft documents as the format for rules and automation rules managed as code.6 Either way, nobody edits a production rule in the portal; a change is a commit, reviewed and deployed.

Example rules

WarningIllustrative code

The queries, payloads and scripts in this chapter are illustrative. They have not been tested against a production tenant or workspace. Every threshold marked TUNE is a starting point to calibrate against the agency’s own data. Run response automation first against test identities and devices, with the narrowest permissions shown.

FMP-DET-01, impossible travel. Successful sign-ins in time order per user, flagged when the implied speed between consecutive locations exceeds a commercial flight. In SigninLogs, ResultType is a string with “0” for success and LocationDetails is dynamic; geo_distance_2points takes longitude before latitude and returns meters.8 9 The source volume’s version compared ResultType to a number and used a self-join that compared every pair of sign-ins; this version compares only consecutive ones.

// FMP-DET-01 Impossible travel. Schedule: every 1h, lookback 1d.
let MaxKmPerHour = 900;   // TUNE: faster than a commercial flight
let MinKm        = 500;   // TUNE: ignore short hops and geolocation noise
let Egress = _GetWatchlist('FMP-ApprovedEgress') | project SearchKey;  // VPN and proxy exits
SigninLogs
| where TimeGenerated > ago(1d)
| where ResultType == "0"
| where IPAddress !in (Egress)
| extend Lat = todouble(LocationDetails.geoCoordinates.latitude),
         Lon = todouble(LocationDetails.geoCoordinates.longitude),
         Country = tostring(LocationDetails.countryOrRegion)
| where isnotnull(Lat) and isnotnull(Lon)
| project TimeGenerated, UserPrincipalName, IPAddress, Lat, Lon, Country, AppDisplayName
| sort by UserPrincipalName asc, TimeGenerated asc
| extend PrevUser = prev(UserPrincipalName), PrevTime = prev(TimeGenerated),
         PrevLat = prev(Lat), PrevLon = prev(Lon),
         PrevIP = prev(IPAddress), PrevCountry = prev(Country)
| where UserPrincipalName == PrevUser
| extend Km    = geo_distance_2points(PrevLon, PrevLat, Lon, Lat) / 1000.0,
         Hours = datetime_diff('second', TimeGenerated, PrevTime) / 3600.0
| where Km >= MinKm and Hours > 0 and Km / Hours > MaxKmPerHour
| project TimeGenerated, UserPrincipalName, PrevIP, PrevCountry, IPAddress, Country,
          Km = round(Km), Hours = round(Hours, 2), AppDisplayName

The watchlist of approved egress addresses is the exception list, maintained outside the rule so analysts can add a VPN exit without editing the query; Sentinel’s _GetWatchlist function returns a watchlist’s rows with its SearchKey column for joins.10 Travel that actually happened, split tunneling and mobile carriers that geolocate far from the user are the expected false positives.

FMP-DET-10, repeated declined MFA prompts. The source volume read MfaDetail, which is deprecated.11 Authentication step results are in AuthenticationDetails, whose authenticationStepResultDetail explains why each step succeeded or failed.12 The result strings below are the ones Microsoft’s own MFA-spamming template matches.13 CISA’s guidance on push bombing is to move to phishing-resistant MFA and, until then, to use number matching, under which a flood of prompts no longer works on its own;14 the rule still matters, because a burst of declined prompts means someone holds the user’s password.

// FMP-DET-10 Repeated declined or unanswered MFA prompts. Schedule: every 15m, lookback 1h.
let Threshold = 5;   // TUNE
SigninLogs
| where TimeGenerated > ago(1h)
| where AuthenticationRequirement == "multiFactorAuthentication"
| mv-expand Step = todynamic(AuthenticationDetails)
| extend StepResult = tostring(Step.authenticationStepResultDetail)
| summarize
    Declined  = countif(StepResult in ("MFA denied; user declined the authentication",
                                       "MFA denied; user did not respond to mobile app notification")),
    Completed = countif(StepResult == "MFA successfully completed"),
    SourceIPs = make_set(IPAddress, 20),
    Apps      = make_set(AppDisplayName, 10),
    First     = min(TimeGenerated),
    Last      = max(TimeGenerated)
    by UserPrincipalName
| where Declined >= Threshold
| extend RuleSeverity = iff(Completed > 0, "High", "Medium")   // a completion after a burst is worse

Users can also report an unexpected prompt. With the Report suspicious activity setting turned on, a report sets the user to high risk and appears as the ID Protection detection userReportedSuspiciousActivity, which lands in AADUserRiskEvents; the program treats any such event as an incident.15 16

// FMP-DET-10b User reported an MFA prompt as suspicious. NRT.
AADUserRiskEvents
| where RiskEventType == "userReportedSuspiciousActivity"
| project TimeGenerated, UserPrincipalName, IpAddress, RiskLevel, RiskState, Location

FMP-DET-11, privileged role activation outside business hours. PIM records an activation in the audit log as “Add member to role completed (PIM activation),” and Microsoft’s guidance is to alert on elevations outside a user’s standard pattern.17 The source volume shifted the time by a fixed five hours and compared dayofweek to an integer; datetime_utc_to_local handles daylight saving, and dayofweek returns a timespan, so Sunday is 0d and Saturday 6d.18 19

// FMP-DET-11 PIM activation outside business hours. NRT, or every 5m.
let Tz = "US/Eastern";              // the agency's primary time zone
let StartHour = 7; let EndHour = 19;  // TUNE: the agency's business day
AuditLogs
| where OperationName == "Add member to role completed (PIM activation)"
| extend Local = datetime_utc_to_local(TimeGenerated, Tz)
| extend LocalHour = hourofday(Local), LocalDay = dayofweek(Local)
| where LocalHour < StartHour or LocalHour >= EndHour or LocalDay in (0d, 6d)
| extend Initiator = tostring(InitiatedBy.user.userPrincipalName)
| mv-apply R = TargetResources on (
    where R.type =~ "Role"
    | extend RoleName = tostring(R.displayName))
| project TimeGenerated, Local, Initiator, RoleName, Result, CorrelationId

An off-hours activation is a signal to verify, not proof of compromise. Tier 0 activations (Book 04) go to the queue as high severity; others as medium.

FMP-DET-12, privileged role assigned outside PIM. Any direct assignment to a sensitive role is suspect in a tenant where privileged roles are eligible-only. The query follows the structure of Microsoft’s privileged-role template: role-management category, assignment operation types, and the role name from the target’s modified properties.20 The audit activity “Add member to role outside of PIM (permanent)” is the PIM service’s record of the same event.21

// FMP-DET-12 Sensitive role assigned outside PIM. NRT.
let Sensitive = dynamic(["Global Administrator", "Privileged Role Administrator",
                         "Privileged Authentication Administrator", "Security Administrator",
                         "Conditional Access Administrator", "Application Administrator"]);
AuditLogs
| where Category =~ "RoleManagement"
| where OperationName in ("Add member to role", "Add member to role outside of PIM (permanent)")
| mv-apply T = TargetResources on (
    where T.type in~ ("User", "ServicePrincipal")
    | extend Target = iff(T.type =~ "ServicePrincipal", tostring(T.displayName),
                          tostring(T.userPrincipalName)),
             Props = T.modifiedProperties)
| mv-apply P = Props on (
    where P.displayName =~ "Role.DisplayName"
    | extend RoleName = trim('"', tostring(P.newValue)))
| where RoleName in (Sensitive)
| extend Initiator = coalesce(tostring(InitiatedBy.user.userPrincipalName),
                              tostring(InitiatedBy.app.displayName))
| project TimeGenerated, OperationName, RoleName, Target, Initiator, Result, CorrelationId

FMP-DET-15, DNS beaconing. Command-and-control over DNS often looks like one host resolving one name at a regular interval. The source volume’s rule claimed to test for regular timing but only counted queries; this one computes the spread of the gaps. It reads the ASIM unifying parser, so it runs unchanged over any DNS source Chapter 05 connected.22

// FMP-DET-15 DNS beaconing. Schedule: every 1h, lookback 1h.
let MinQueries   = 20;    // TUNE
let MaxJitterSec = 5.0;   // TUNE: standard deviation of the gap, in seconds
let Allow = _GetWatchlist('FMP-DnsBeaconAllow') | project SearchKey;  // monitoring and health-check hosts
_Im_Dns(starttime = ago(1h), endtime = now())
| where isnotempty(SrcIpAddr) and isnotempty(DnsQuery)
| where SrcIpAddr !in (Allow)
| summarize Times = make_list(TimeGenerated, 1000), Queries = count() by SrcIpAddr, DnsQuery
| where Queries >= MinQueries
| mv-apply T = Times to typeof(datetime) on (
    order by T asc
    | extend GapSec = datetime_diff('second', T, prev(T))
    | where isnotnull(GapSec)
    | summarize MeanGapSec = avg(GapSec), StdGapSec = stdev(GapSec))
| where StdGapSec <= MaxJitterSec
| project SrcIpAddr, DnsQuery, Queries, MeanGapSec = round(MeanGapSec, 1), StdGapSec = round(StdGapSec, 2)

Monitoring agents, load balancer probes and software update checks are regular too. They belong on the allow watchlist with a named owner and an expiry, not in the query.

FMP-DET-17, database login from an unexpected address. For Azure SQL, audit records in AzureDiagnostics carry client_ip_s, server_principal_name_s, action_name_s and succeeded_s.23 The expected application subnets are a watchlist; ipv4_lookup matches addresses against it.24

// FMP-DET-17 Azure SQL login from outside the expected subnets. Schedule: every 15m, lookback 15m.
let Expected = _GetWatchlist('FMP-SqlClientSubnets') | project Network = SearchKey;  // CIDR ranges
AzureDiagnostics
| where TimeGenerated > ago(15m)
| where Category == "SQLSecurityAuditEvents"
| where action_name_s has "DATABASE AUTHENTICATION SUCCEEDED"
| evaluate ipv4_lookup(Expected, client_ip_s, Network, return_unmatched = true)
| where isempty(Network)
| summarize Logins = count(), First = min(TimeGenerated), Last = max(TimeGenerated)
    by client_ip_s, server_principal_name_s, database_name_s, application_name_s

For SQL Server on Windows, the same pattern runs against audit records in SecurityEvent (Chapter 05); the sa rule (FMP-DET-18) looks there for an ALTER LOGIN statement that enables the login. Confirm the action names and event layout on a test instance before enabling either.

Rule lifecycle and testing

Every rule passes through the same lifecycle, and every step leaves a record in the repository or the tuning log. The lifecycle is the program’s design; the Sentinel features it uses are Microsoft’s.

  1. Author. The rule is written in the repository with its thresholds marked TUNE, its entity mappings and the reason it exists. Where Microsoft ships a template for the pattern, the rule starts from the template.
  2. Test against history. The analytics rule wizard’s results simulation shows how many results the query would have produced over its last 50 scheduled runs, so a rule that would fire constantly is caught before it ships.25 The program also replays a known-bad sample, from a tabletop exercise or a test tenant, to confirm the rule fires when it should. A rule that cannot be shown to fire on a true positive is not finished.
  3. Deploy alert-only. The rule is enabled with incident creation turned off, so it produces alerts that analysts review daily without flooding the queue. Sentinel supports disabling incident creation per rule, and alert-triggered automation exists precisely for rules that do not create incidents.26 27 The source volume set a two-week window; the program’s rule is to stay alert-only until the false-positive patterns are documented and the thresholds adjusted, with two weeks as the minimum. One caution for workspaces onboarded to the Defender portal: there, Defender creates the incidents, and a rule’s incident-creation setting must be enabled for its alerts to become incidents at all.28
  4. Promote. Incident creation is turned on, the measured false-positive rate is recorded in the rule’s metadata, and the rule’s response is wired (the next section). Promotion is a commit.
  5. Review on a schedule. Each rule is reviewed at least quarterly (program design): is it still firing at the expected rate, is every table it reads still fresh (Chapter 05), has its template changed? Sentinel disables a scheduled rule after repeated permanent failures, such as a deleted table or a changed function, and prefixes its name with “AUTO DISABLED”; Microsoft advises SOC managers to check the rule list for them regularly.29 The program’s review query checks for them every day. Sentinel’s analytics rule health monitoring, in public preview in both commercial and government Azure, records rule runs in SentinelHealth.30

Detections rot. Thresholds drift as the environment changes, sources stop emitting without an error, and a parser update can change a field name. The standing detection-engineering effort that reviews and re-tunes the library is the real cost of having one, and Chapter 10 staffs it. Telemetry-completeness testing and detection-efficacy testing feed the metrics in Chapter 12. Sentinel’s limits bound the library’s size: 512 enabled scheduled rules per workspace by default and 50 enabled NRT rules.31

The response ladder

Detection without response shortens the investigation, not the exposure. The design rule for every playbook is confidence-gated action: high-confidence detections prepare containment, medium-confidence detections enrich and ticket for a human, and nothing low-confidence acts at all. Auto-containment on a noisy rule is its own denial of service.

The program places every response on the actuation ladder of Book 01, Chapter 11. There, each operation class has a ceiling; gated actuation (L3), where a human authorizes a prepared action, is the default ceiling for anything with a large blast radius, and autonomous action (L4) is allowed only for enumerated low-blast-radius classes. NIST frames the same idea from the control side: SI-4(7) asks the organization to notify defined personnel of suspicious events and to take defined “least-disruptive actions” on detection.32

Rung Confidence What happens Human in the loop Examples
L1 Observe Any Incident opened, entities mapped, evidence kept Triage Every promoted rule
L2 Advise Medium Enrichment playbook adds identity, device and IP context; ticket opened Analyst decides Off-hours PIM activation; database login from an unexpected address
L3 Gated actuation High Playbook evaluates preconditions and prepares the containment; a named approver releases it Approver releases; analyst investigates Session revocation; disabling a standard user; isolating a workstation
L4 Within guardrails High, enumerated class Runs without a person, logged, reversible Reviewed after the fact Closing incidents matching a known-benign watchlist; vendor attack disruption where the authorizing official has accepted it
Standing control n/a Configuration that bounds exposure if detection misses n/a Sign-in frequency and token policies (Book 04)

The mapping is the program’s design. Three operation classes stay at L3 or below permanently, whatever the program’s maturity: isolating a server, disabling a privileged or emergency-access account, and any tenant-wide change. A false-positive isolation of a production database server is an outage, and a disabled emergency account during an incident is a lockout.

Defender XDR’s automatic attack disruption is the case that tests the ladder. It contains assets on its own when Defender correlates a high-confidence attack, revoking sessions, suspending users and containing devices and users at the endpoint layer, with every action logged, reversible, and subject to exclusions for named users, device groups and IP ranges.33 That is L4 by the vendor’s design. The program does not leave it as a default nobody chose. The authorizing official either accepts attack disruption as an enumerated L4 class, with exclusions configured for emergency-access accounts and the server device groups the permanent-L3 rule protects, or the program records why it is limited. Either way the decision is written down, which is what the ladder exists to produce. Confirm attack disruption’s availability in the agency’s cloud before relying on it.

Playbooks

Sentinel automation has two layers. Automation rules run inside Sentinel when an incident is created or updated or an alert is created; they can change status and severity, assign an owner, add tags and tasks, close incidents with a reason, and run playbooks, in a defined order, and they can carry an expiration date. Playbooks are Azure Logic Apps workflows that act on other systems, and Sentinel runs them under a dedicated service account that must be granted permission on the playbooks’ resource group.34 The program keeps automation rules for triage and suppression, and playbooks for anything that touches an identity, a device or a ticket.

Every playbook follows four rules (design): it uses a managed identity with only the permissions its actions need, never a client secret; it writes each action, with the approver and timestamp, back to the incident as a comment, which is the response documentation Chapter 05’s evidence record needs; it evaluates its preconditions and stops if they fail, which is the playbook’s dry run; and it starts in alert-only mode, preparing its action without taking it, until the triggering rule’s false-positive rate has been measured.

Session revocation

The containment path for a high-confidence session anomaly (FMP-DET-04) or a confirmed compromise. Microsoft Graph’s revokeSignInSessions invalidates the refresh tokens issued to a user’s applications and their browser session cookies by resetting signInSessionsValidFromDateTime; Microsoft notes a delay of a few minutes before tokens are revoked, and that the call does not revoke sessions for external users. Its least-privileged permission is User.RevokeSessions.All.35 Marking the user confirmed-compromised in ID Protection sets the user’s risk to high, which risk-based Conditional Access can then act on; it is a POST to /identityProtection/riskyUsers/confirmCompromised with the user IDs, needs IdentityRiskyUser.ReadWrite.All, and requires Entra ID P2. The source volume showed it as a PATCH.36

// revoke-session playbook: logic as a Logic App would run it (pseudocode, not a deployable definition)
{
  "trigger": "Sentinel incident created by FMP-DET-04 or FMP-DET-01 with corroboration",
  "identity": "managed identity: User.RevokeSessions.All, IdentityRiskyUser.ReadWrite.All",
  "steps": [
    { "guard": "incident.severity == 'High' && entities.Account.count == 1" },          // confidence gate
    { "guard": "account not in watchlist FMP-EmergencyAccess and not privileged" },      // permanent-L3 classes go to a human
    { "prepare": "comment: proposed action, evidence, rollback (none needed: user re-authenticates)" },
    { "approve": "named approver from the on-call roster releases or rejects; timeout = reject" }, // L3 gate
    { "graph": "POST /users/{id}/revokeSignInSessions" },                                // AC-12
    { "graph": "POST /identityProtection/riskyUsers/confirmCompromised  { userIds: [id] }" },
    { "comment": "actions taken, approver, UTC timestamps" },                            // response record
    { "ticket": "link incident to the IR ticket" }                                       // IR-4
  ]
}

Revocation is not instant everywhere. Continuous access evaluation lets CAE-capable services such as Exchange Online, SharePoint Online and Teams act on critical events, including an administrator revoking a user’s refresh tokens, account disablement and high user risk, in near real time, but Microsoft states that latency of up to 15 minutes can be observed because of event propagation.37 Clients and resources that are not CAE-aware keep an existing access token until it expires; the default access token lifetime is a random value between 60 and 90 minutes, and CAE-aware sessions can receive tokens that live up to 28 hours because they can be revoked.38 So containment latency is the rule’s cadence plus the approval plus revocation propagation, and for non-CAE applications the remaining token lifetime. The source volume called the in-boundary playbook a minutes-scale substitute for “sub-second” CAE revocation; CAE itself is not sub-second, and this playbook triggers it rather than replacing it.

The source volume’s standing control, bounding token lifetime to 60 to 90 minutes, describes the platform default rather than a setting the program adds. Microsoft recommends Conditional Access session controls, such as sign-in frequency, over configurable token lifetimes, and notes that reduced token lifetimes degrade user experience and reliability without eliminating risk.39 40 The program’s standing controls are the Conditional Access policies in Book 04.

Account disablement

For a high-confidence compromise of a standard user, the program disables the account as well as revoking sessions. In Graph, that is a PATCH to the user setting accountEnabled to false, and the least-privileged combination is User.EnableDisableAccount.All with User.Read.All.41 In a hybrid environment, though, the authoritative account is in Active Directory. Microsoft’s procedure for revoking a hybrid user’s access starts there, disabling the account and resetting the password twice to mitigate pass-the-hash, and then disables the user in Entra ID, revokes refresh tokens and disables the user’s registered devices.42 A playbook that disables only the cloud object of a synchronized user is undone at the next synchronization, and leaves the on-premises account usable. The program’s playbook therefore runs the Active Directory step through an on-premises runbook worker, inside the boundary, as part of the same approved action.

The cloud half looks like this with the Microsoft Graph PowerShell cmdlets Microsoft documents for the procedure, connecting with the automation account’s managed identity:43 44

# disable-principal, cloud half: run by an automation account's managed identity after approval
# Graph permissions: User.EnableDisableAccount.All + User.Read.All, User.RevokeSessions.All,
# and device write permission for the device step
param(
    [Parameter(Mandatory)] [string] $UserId,             # Entra object ID from the incident entity
    [Parameter(Mandatory)] [string] $IncidentNumber,
    [Parameter(Mandatory)] [string] $ApprovedBy
)
Connect-MgGraph -Identity -NoWelcome

Update-MgUser -UserId $UserId -AccountEnabled:$false
Revoke-MgUserSignInSession -UserId $UserId

Get-MgUserRegisteredDevice -UserId $UserId -All | ForEach-Object {
    Update-MgDevice -DeviceId $_.Id -AccountEnabled:$false
}

# The playbook writes this line back to the incident as the response record
"{0:u} FMP disable-principal: user {1} disabled, sessions revoked, devices disabled; incident {2}; approved by {3}" -f `
    (Get-Date).ToUniversalTime(), $UserId, $IncidentNumber, $ApprovedBy

Re-enablement is a separate, recorded decision by the identity team after investigation: password reset, MFA re-registration and the account owner’s manager confirming the person is who they say they are. A wrongly disabled person is restored through that process with a recorded exception, the same principle Book 03 applies to leavers.

Device isolation

When Defender for Endpoint reports active exploitation or hands-on-keyboard activity on a device, isolation cuts the device off from the network while keeping its connection to the Defender service, preserving forensic state. The Defender for Endpoint API’s isolate action takes a required comment and an isolation type of Full, Selective or UnManagedDevice; it needs the Machine.Isolate permission, is limited to 100 calls a minute, and, Microsoft warns, a device behind a full VPN tunnel may lose its connection to the Defender service once isolated.45 The API host differs by cloud: Microsoft documents api.security.microsoft.com for commercial, and for the Defender for Endpoint API api-gcc.securitycenter.microsoft.us for GCC and api-gov.securitycenter.microsoft.us for GCC High and DoD, with sign-in through login.microsoftonline.us for the latter two.46 47 The source volume used the older commercial host and a client secret.

The program’s isolation playbook isolates workstations at L3 and never isolates a server without a human decision outside the playbook, per the permanent-L3 rule. The trigger is a Defender alert of active exploitation, not a vulnerability finding: a vulnerable package is a remediation item for Chapter 06, not an incident.

Enrich and ticket

For medium-confidence detections, the playbook gathers context and hands the decision to an analyst: the user’s ID Protection risk level and recent risk events, their PIM eligibilities, the device’s compliance and Defender exposure, recent sign-ins, and any watchlist the entities appear on. It writes the context to the incident as a comment, opens or updates the ticket in the agency’s service-management system with the incident’s ID, and tags the incident as enriched. This is L2: it changes nothing except the record.

Suppression of known-benign incidents

Health-check hosts that trip the beaconing rule, scheduled penetration tests and maintenance windows produce incidents the SOC already understands. An automation rule closes them as they are created, with a closing reason and a comment, and can carry an expiration date so a time-limited exception cannot become permanent.48 This is the one L4 class the program enables by default, because its blast radius is the incident queue, its condition is a watchlist with a named owner, and every closure is recorded. Better still is fixing the rule so it does not fire, which the lifecycle review does.

The incident response plan

The playbooks operate inside an incident response plan, and the plan is assessed separately from the tooling. An agency can run a mature Sentinel deployment and still fail IR-8 for want of documents.

NIST SP 800-61 Rev. 3, published in April 2025, superseded Rev. 2 and recasts incident response recommendations as a CSF 2.0 Community Profile.49 The program keeps Rev. 2’s familiar phase names as an internal operating convention, and maps them to the CSF 2.0 functions that Rev. 3 uses. IR-4 itself still names the activities: an incident handling capability that “includes preparation, detection and analysis, containment, eradication, and recovery,” coordinated with contingency planning, with lessons learned fed back into procedures, training and testing.50

Phase (program convention) Sentinel and Defender mechanism Record kept
Preparation Rule library deployed; playbooks configured; on-call roster and contacts as watchlists Plan document; contact list; training records
Detection and analysis Rule fires; incident opened; enrichment appended Incident with timeline and evidence
Containment Gated playbook action or manual containment Action, approver and timestamps on the incident
Eradication Patch, credential reset or policy fix; rescan confirms Eradication record and verification output
Recovery System returned to service; heightened monitoring Recovery record; post-isolation validation
Post-incident activity Lessons learned; plan updated; rule tuned Lessons-learned record; tuning log entry

IR-8 requires a plan that, among other things, provides a roadmap for the capability, defines reportable incidents, provides metrics for measuring the capability, addresses sharing of incident information, is reviewed and approved at a defined frequency, explicitly designates responsibility for incident response, and is distributed, updated and protected from unauthorized disclosure and modification. IR-3 requires the capability to be tested at a defined frequency.51 FedRAMP’s 2026 incident response indicators ask that the effectiveness of incident response procedures and past incidents be persistently reviewed and that after-action reports feed lessons learned back in.52

The program’s plan carries seven artifacts, which are its own design built on those requirements: the plan itself, reviewed annually; a contact list reviewed at least quarterly, including the CISA reporting channel; notification templates; an evidence preservation procedure (incident export, query results exported to immutable storage, device forensic collection, chain of custody); a lessons-learned template used after every high-severity incident; a tabletop exercise record from the last 12 months; and the annual test record. CISA’s Federal Incident Notification Guidelines, effective April 1, 2017, require agencies to report incidents to CISA within one hour of identification by the agency’s top-level CSIRT, SOC or IT department, and the plan documents that path explicitly.53 The source volume tied the one-hour requirement to a particular year’s FISMA guidance memo; the program cites the guidelines themselves and checks the current year’s FISMA guidance for any change. A tabletop built from this book’s own sources, a DNS beacon that leads to an off-hours privileged activation, exercises the rule library, the response ladder and the plan in one sitting. For testing response automation without a real attack, Defender for SQL Servers on Machines can simulate alerts that exercise downstream automation.54

Honest limits

Carry these into every assessment. The library and the playbooks do not claim parity with what they replace.

  • Detection is minutes to hours. Scheduled rules run no more often than every five minutes plus a five-minute ingestion delay, NRT rules about every minute, and baselines take as long as their windows.55 That is not the continuously tuned fidelity of a vendor’s multi-tenant pipeline.
  • The library sees one tenant. It has no global view; atypical-address and leaked-credential logic is only as good as the threat intelligence feeds the agency subscribes to.
  • Containment is bounded by cadence, approval and propagation. Session revocation takes effect in minutes, up to about 15 for CAE-aware services, and non-CAE clients keep tokens until they expire. The gated design adds an approver’s response time on purpose.
  • Hybrid identities need both halves. Cloud-only containment of a synchronized user is incomplete and reversible by synchronization.
  • Automation amplifies a noisy rule. The confidence gate, the alert-only ramp and the permanent-L3 classes are mandatory, not optional.
  • The playbooks act only on the agency’s own tenant. An identity federated from elsewhere, or an external guest, is outside their reach; revocation does not apply to external users.56
  • Detections rot. Without the standing engineering effort that reviews and re-tunes the library, the maturity this chapter describes decays quietly, and the freshness and auto-disable checks are what reveal it.
