# Chapter 09 — Deploying to Test and Production

*The kit never writes to Purview, so deploying it is about trust in what it reads: the right tenant, the right versions, the right account, and evidence that test passed before production starts.*

::: {.callout-note}
## In this chapter
The runbook behind the guide's [G12 Operations and evidence](../../../books/guides/information-protection-implementation.md#step-12-operations-and-evidence) monthly cadence. You read the settings template, the preflight's six checks and the scheduled run. Lab 1 runs the runbook's tests with stand-in modules and a fixture tenant; Lab 2 runs the preflight and one scheduled run in a test tenant, then sets out the production step.
:::

## Goal and audience

For the developer who deploys the kit and the operator who owns the schedule. By the end the monthly run happens in test under a change record, its evidence passes the test stage's go/no-go, and production can start from that evidence.

## Start with the guide and Book 20

The guide's G12 runs the baseline export monthly "under a read-only role"; [Book 20, Chapter 12](../../../books/b20-information-protection/12-operations-and-evidence.md#the-configuration-baseline) adds that an unattended schedule uses app-only authentication with a certificate, as Microsoft documents, registered as a workload identity with an owner. Learn's app-only page gives the two connection commands, the primary `.onmicrosoft.com` domain as the organization, and the thumbprint as Windows only.[^ip09-app] Learn's `Connect-AipService` page doesn't give certificate sign-in clearly, so the Rights Management read stays delegated: a scheduled app-only run sets `reads.rightsManagement` to `false`, and the operator runs that read by hand under PIM.

## The code

- **`deploy/settings.template.json`:** environment, cloud, tenant, the operator's UPN or the app's ID, certificate thumbprint and organization, the reads, the output root, the last approved export and the inputs. No secret is stored; the certificate stays in the Windows certificate store.
- **`deploy/Test-IpPreflight.ps1`:**
  - **PF-01** settings and inputs: every input exists and nothing is a placeholder.
  - **PF-02** ExchangeOnlineManagement: 3.0.0 or later, and not 3.10.0 or later on PowerShell before 7.6.
  - **PF-03** AIPService 3.1.0.0 or later when the Rights Management read is on.
  - **PF-04** the app-only certificate is in the store and the organization is a `.onmicrosoft.com` domain.
  - **PF-05** the output root is writable.
  - **PF-06** production only: the test stage's evidence passes `Test-IpEvidence -Stage test`.
- **`deploy/Invoke-IpScheduledRun.ps1`:** preflight, recorded as evidence (and the run stops if it fails); the live export, recorded; every check and drift against `baselinePath`, each recorded; a summary run folder, recorded. All under one change record.

The stages' steps are in `config/requirements.json`: test needs preflight, export, access, labels, protection, DLP, auto-labeling and audit; production adds drift and the scheduled run.

## Lab 2: a test tenant

Use a test tenant, never production. Work in `examples/information-protection`. You'll replace `<settings-file>` (your filled copy of `deploy/settings.template.json` with `environment` `test`), `<run-folder>`, `<evidence-folder>` and `<change-record>` (the change record that approves the test run).

<!-- labs:begin lab-2-commands (generated by scripts/generate_labs.py; not part of the reviewed page) -->

::: {.callout-note #lab-2-commands collapse="false" title="Every command in Lab 2"}
Every command in this lab, in order, from `examples/information-protection`. Each step below says what it does and what to look for.

```powershell
# Step 1: Run the preflight
./deploy/Test-IpPreflight.ps1 -SettingsPath <settings-file> -OutputPath <run-folder>/preflight

# Step 2: Run one scheduled run by hand
./deploy/Invoke-IpScheduledRun.ps1 -SettingsPath <settings-file> -RunRoot <run-folder> -EvidencePath <evidence-folder> -ChangeRecord <change-record>

# Step 3: Ask for the test stage's go/no-go
./Invoke-IpEvidence.ps1 -EvidencePath <evidence-folder> -Check -Stage test

# Step 4: Back it out
Remove-Item -Recurse -Force <run-folder>
```

:::

<!-- labs:end -->

1. **Run the preflight:**

   ```powershell
   ./deploy/Test-IpPreflight.ps1 -SettingsPath <settings-file> -OutputPath <run-folder>/preflight
   ```

   Fix each failing row before going on. PF-02 tells you which module version or PowerShell version to install.

2. **Run one scheduled run by hand:**

   ```powershell
   ./deploy/Invoke-IpScheduledRun.ps1 -SettingsPath <settings-file> -RunRoot <run-folder> -EvidencePath <evidence-folder> -ChangeRecord <change-record>
   ```

3. **Ask for the test stage's go/no-go:**

   ```powershell
   ./Invoke-IpEvidence.ps1 -EvidencePath <evidence-folder> -Check -Stage test
   ```

   Each `STEP` row that fails names a check whose findings are still open. Close them in the tenant or the plan, run again, and ask again.

4. **Back it out.** Nothing changed in the tenant. Keep the evidence folder; it is what production's PF-06 reads.

   ```powershell
   Remove-Item -Recurse -Force <run-folder>
   ```

**Production** uses a second settings file with `environment` `production`, `baselinePath` naming the last approved production export, and the scheduled run given `-TestEvidencePath <evidence-folder>` so PF-06 can read the test stage's go/no-go.

## Dangers

| Danger | Mitigation |
|---|---|
| Production started on hope | PF-06 holds it until the test stage's evidence passes |
| A certificate secret in a settings file | The thumbprint only; the certificate stays in the store |
| An app-only run expected to read Rights Management | Set `reads.rightsManagement` to `false` and run that read delegated under PIM |
| A module upgrade breaks the schedule | PF-02 catches 3.10 on PowerShell before 7.6 before anything connects |
