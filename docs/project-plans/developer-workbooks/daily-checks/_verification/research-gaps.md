# Research gaps for the developer workbook *Building the Daily Checks Workbook*

Found while building the kit and writing the chapters, November 18, 2026, on Microsoft Learn (WebFetch) and in the repository. None conflicts with the guide or the books: each is something Learn doesn't state, or a value only the agency's own workspace can give.

| # | Gap | Finding | Status | Source |
|---|---|---|---|---|
| 1 | The workbook item schema (Chapter 02) | Learn documents the `Microsoft.Insights/workbooks` resource and shows sample `serializedData` with text and query items (`type` 1 and 3, `KqlItem/1.0`, `queryType`), but not every field of the Notebook/1.0 format the kit writes: parameters (`type` 9, `KqlParameterItem/1.0`), tabs (`type` 11, `LinkItem/1.0`), groups (`type` 12, `NotebookGroup/1.0`, `conditionalVisibility`). | open: the kit follows the shape the portal's Advanced Editor exports; Chapter 02's Lab 2 round-trips the template through the portal and records any difference | Learn, Azure Monitor workbooks and ARM templates |
| 2 | `ProductName` values for DLP and label alerts in `SecurityAlert` (Chapter 01) | Learn documents the column, not its values for Purview alerts arriving through Defender XDR. The fixtures use a fictional value. | open: the settings file holds the agency's values, read from its own workspace (the Copilot prompt helps) | Learn, SecurityAlert table reference; Defender XDR integration |
| 3 | `ComplianceState` values in `IntuneDeviceComplianceOrg` (Chapter 01) | Learn documents the column, not its values; Book 05, Chapter 10 says not to hard-code them. | open: a settings value, read from the workspace | Learn, IntuneDeviceComplianceOrg; Book 05, Chapter 10 |
| 4 | `Owner.assignedTo` in `SecurityIncident` (log review query) | Learn lists `Owner` as dynamic, "The user the incident is assigned to," without its fields. | open: Chapter 03's Lab 2 confirms the field; if absent the column is empty, not wrong | Learn, SecurityIncident table reference |
