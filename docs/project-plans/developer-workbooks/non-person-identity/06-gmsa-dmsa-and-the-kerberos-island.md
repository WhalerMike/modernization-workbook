# Chapter 06 — gMSAs, dMSAs and the Kerberos Island

*A gMSA is a good credential with a known expiry date: the day the last domain controller is demoted. The code's job is to make sure every one of them is gone, or on a dated list, before that day.*

::: {.callout-note}
## In this chapter
The Kerberos-only part of credential modernization (the project plan's NP3.5 and NP3.6) and the reconciliation before AD is retired (NP7.3). You start with Learn's own procedures for group managed service accounts (gMSAs), delegated managed service accounts (dMSAs, Windows Server 2025) and the KDS root key, which the repository keeps as a pinned copy, and you run them against stand-ins to see what they do and what they leave to you. Then you use `examples/non-person-identity` for the rest: a plan per Kerberos account from reviewed data, the KDS root key checked without reading the key, the password retrievers held as reviewed data, new accounts held to the program's [managed service account standard](../../../books/guides/service-account-migration.md#msa-standard), a separate write path that creates, migrates, disables and moves to a holding OU but never deletes, with the pipeline's own gMSA sending its steps and a person the dMSA steps, the island list for the program's SPN retirement, and the reconciliation with the program's end state. Lab 1 runs on a laptop with no domain; Lab 2 uses a test domain.

## Goal and audience

**Goal.** By the end of this chapter you can produce, from code and reviewed data, the three things the plan asks for here: NP3.5, "MSAs upgraded to gMSAs; traditional accounts, IIS application pools and scheduled tasks moved to a gMSA or a dMSA"; NP3.6, the Kerberos accounts that stay, each with "SPN owner and an end date within D08 recorded" (an end date recorded by D08 and, as WD-165 bounds it, no later than program G5 or the island's end of life), and "the islanded list handed to the program's SPN retirement" (P4.6); and NP7.3, "gMSAs and dMSAs reconciled with the provisional end state: moved to a workload identity, or listed for the Kerberos island with an end-of-life date". Every change to the domain is a plan file a reviewer approves by its SHA-256 before anything runs. You can say, for each rule, whether it is Learn's, Learn's procedure, or the program's design.

**Audience.** Developers who build the project's Active Directory code, the server and Active Directory engineers who own the pipeline that runs the write path, run its dMSA steps and change the hosts, the application owners who name an SPN owner and an end date, and the ISSO who reviews the island list. You should read PowerShell 7 and know Chapter 01's register. You don't need a domain until Lab 2.

## The context the code depends on

**What a gMSA and a dMSA are.** A gMSA is a domain account whose password the domain controllers manage and which several servers can retrieve; services that use the Service Control Manager, IIS application pools and Task Scheduler tasks can run as one.[^np06-gmsa-manage] Learn's Entra guidance says to use gMSAs for on-premises services unless a service, such as failover clustering, doesn't support them, and that Windows changes the password every 30 days.[^np06-entra-gmsa] A dMSA, new in Windows Server 2025, supersedes a traditional service account: once the migration completes, the old account's password can no longer be used, authentication is tied to the machines mapped to the dMSA, and the original account is disabled.[^np06-dmsa-overview] Learn's gMSA page adds four rules the plan has to respect: a gMSA's name must be unique in the forest, not just the domain; its password interval (30 days by default) can be set only when it's created; a gMSA can be created for outbound authentication only (`-RestrictToOutboundAuthenticationOnly`); and each host tests that it can retrieve the password with `Test-ADServiceAccount` after `Install-ADServiceAccount`.[^np06-gmsa-manage] Learn's containers page adds that a forest should have only one KDS root key, because more than one makes gMSAs fail after a password rotation.[^np06-containers] The same moves done by hand, step by step with Learn's commands, and the Entra targets compared side by side, are in the guide [*Service Accounts: From User Accounts to gMSAs to Microsoft Entra Workload Identities*](../../../books/guides/service-account-migration.md). Book 02's [matrix](../../../books/b02-identity/09-building-the-entra-target.md#the-migration-path-matrix) gives the targets: a traditional account that serves Kerberos on-premises goes to a gMSA, or a dMSA on a Windows Server 2025 domain; an MSA is upgraded to a gMSA first; IIS application pools and scheduled tasks go to a gMSA now and to a managed identity once they move to Azure.

**Why this chapter has an end date built in.** A gMSA works only while AD is authoritative ([companion guide](../../../books/guides/attribute-driven-migration.md#service-accounts-msas-gmsas-and-dmsas)). The program decides at G0 whether its end state is AD retired or a dated Kerberos island (D11, provisional), sets end dates for legacy authentication and NTLM at D08, and retires AD at program G5. The project plan's risk register is blunt: a workload still running under a gMSA loses its credential when the last domain controller is demoted. So the code doesn't stop at "converted": every gMSA and dMSA ends this chapter either moving to a workload identity (Chapter 05), retiring, or on the island list with an end date, and the island list is what the program's SPN retirement (P4.6) works from. Book 02, Chapter 10's [What still needs AD after Phase 10](../../../books/b02-identity/10-migrating-and-governing.md#what-still-needs-ad-after-phase-10) lists Kerberos applications as one of the dependencies AD retirement has to clear.

The program's rules for this chapter *(Design guidance)*:

- **Every Kerberos account has a reviewed disposition, and it is Chapter 03's:** the application owner's D-NP3 decision, `Retire`, `Replatform`, `Keep` or `KeepKerberos`, which this chapter reads from [Chapter 03](03-the-migration-path-matrix-as-code.md)'s run, never from a second list. `Replatform` to a gMSA or a dMSA is converted here; `Replatform` to a managed identity or an app registration moves in Chapter 05; `Keep` and `KeepKerberos` stay, with an end date and, where Chapter 03 asks for one, an SPN owner, and `KeepKerberos` carries the authorizing official's acceptance onto the island list; `Retire` goes through the decommission process. For each account it re-platforms, `kerberos-replatform.csv`, kept with the application records, names the new account, its workload and its hosts. A Kerberos account here is an enabled traditional account with an SPN, an MSA, a gMSA or a dMSA from Chapter 01's register. SQL Server's go to the Data Platform plan.
- **Who may retrieve a managed password is reviewed data**, in `password-retrievers.json`, not whatever AD holds today. A gMSA's entry is exactly one domain local group of the hosts that run it, `DL-gMSA-<app>-Hosts`, never a computer account ([WD-160](../../../about/decision-register.md#wd-160)). A dMSA's entry is the hosts it learned during its migration, so the group rule doesn't apply to it.
- **Every new account follows the [managed service account standard](../../../books/guides/service-account-migration.md#msa-standard)**, read from the reviewed `ad-standard.json`: named `gmsa-<app>` or `dmsa-<app>`, 15 characters or fewer before the `$` ([WD-159](../../../about/decision-register.md#wd-159)); created with `-Path` in the service-account OU ([WD-161](../../../about/decision-register.md#wd-161)) with the 30-day password interval stated at creation; and, when the account it replaces holds no SPN and the owner recorded no reason, outbound-only ([WD-154](../../../about/decision-register.md#wd-154)). [Chapter 12](12-the-managed-service-account-standard.md) checks the requests against the same standard and writes this chapter's input rows for the ones that pass.
- **Every write carries its approval.** SailPoint approves every managed service account request and ServiceNow records the change ([WD-162](../../../about/decision-register.md#wd-162)); the plan names both on each write, or blocks it.
- **The pipeline sends what it can; a person sends the rest** ([WD-163](../../../about/decision-register.md#wd-163)). The pipeline's own gMSA, `gmsa-msapipe$`, sends the gMSA creations, retriever changes, disables and moves; a person sends the dMSA steps, which need Domain Admins. Every production write goes through the approved plan ([WD-168](../../../about/decision-register.md#wd-168)).
- **A dMSA migration runs for 30 days before it completes.** That is the program's choice, its parallel run for every conversion ([WD-124](../../../about/decision-register.md#wd-124)), and it's longer than Learn's wait: at least two ticket lifetimes ("equivalent to 14 days") before completing, with four ticket lifetimes (28 days) in the start state recommended.[^np06-dmsa-overview]
- **Every account that stays on Kerberos has an end date, bounded as in Chapter 03** and as the standard's end-date rule sets it: one the authorizing official accepts, recorded by program D08 and never later than program G5, or the island's end of life where D11 keeps one ([WD-165](../../../about/decision-register.md#wd-165)). The code checks it against that one bound for every account that stays, a `KeepKerberos` account and a kept or planned gMSA or dMSA alike, as Chapter 03 does: no later than program G5, or the island's end of life where D11 keeps one. D08 bounds no end date. **It has an SPN owner where Chapter 03 asks for one:** a `KeepKerberos` account, or any account with SPNs; a kept account with no SPNs needs none. Every gMSA and dMSA also ends no later than program G5 if D11 retires AD, or than the island's end of life if D11 keeps one.
- **Never delete.** The old account is disabled at most, by `Complete-ADServiceAccountMigration` for a dMSA or by `Disable-ADAccount` after a clean 30-day parallel run on a gMSA ([Book 02, Chapter 10, Phase 4](../../../books/b02-identity/10-migrating-and-governing.md#phase-4-service-account-modernization)), and the same plan then moves it to the holding OU with `Move-ADObject` ([WD-168](../../../about/decision-register.md#wd-168)). Retirement goes through the plan's reviewed decommission process: a person deletes the account through the decommission ticket, 90 days after the disable with no sign-in seen ([WD-167](../../../about/decision-register.md#wd-167)).

### Which domain, and which cloud

Every call in this chapter is an Active Directory cmdlet against the program's domain (`corp.contoso.example` in the fixtures), sent to the domain controller named with `-Server`. The writes don't work against a read-only domain controller.[^np06-new-adsa] [^np06-start-mig] No Graph or Resource Manager endpoint is called, so the cloud doesn't change anything here; the run still takes `-Cloud` and refuses a register read in another cloud, so the evidence matches Chapter 01's. The moves to a workload identity happen in Chapter 05, against the cloud's own endpoints.

## Start with Microsoft's sample

### What Microsoft gives you

Learn has four procedures for this chapter. *Setting up delegated Managed Service Accounts* is a PowerShell walk-through: check the KDS root key with `Get-KdsRootKey`, create a dMSA with `New-ADServiceAccount -CreateDelegatedServiceAccount`, grant a machine its password with `Set-ADServiceAccount`, set `msDS-DelegatedMSAState`, start the migration with `Start-ADServiceAccountMigration`, set a registry value on the host, restart the host's services, complete it with `Complete-ADServiceAccountMigration`, and undo or reset it.[^np06-dmsa-setup] *Delegated Managed Service Accounts overview* gives the limits and what each step changes in AD.[^np06-dmsa-overview] *Manage group Managed Service Accounts* (formerly *Get started with group managed service accounts*) creates a gMSA with `New-ADServiceAccount -PrincipalsAllowedToRetrieveManagedPassword` and installs it on each host.[^np06-gmsa-manage] *Create a Key Distribution Service (KDS) root key* covers the one-time prerequisite.[^np06-kds] Learn's Entra page *Secure group managed service accounts*, pinned for Chapter 01, gives the seven steps to move a service to a gMSA.[^np06-entra-gmsa]

### The pinned copy

The procedures exist only inside the Learn pages, so the repository pins the pages' source, unmodified, in [`examples/third_party/windows-server-msa-pages`](https://github.com/WhalerMike/modernization-workbook/tree/main/examples/third_party/windows-server-msa-pages): four pages from MicrosoftDocs/windowsserverdocs at commit `2205ce8` (October 30, 2026), retrieved October 30, 2026, with the repository's licenses (Creative Commons Attribution 4.0 for documentation, MIT for code).[^np06-src] `snapshot.json` records each file's SHA-256 and git blob hash, checked against the upstream tree, and a unit test checks them. The weekly source watch reports new commits to each page. Updating the copy is a reviewed pull request.

`tests/KerberosIslandSampleHarness.ps1` finds each PowerShell block by its content in the page's source, strips the Markdown quote and list indentation, and runs it unmodified against stand-ins for the Active Directory, registry and service cmdlets it calls. The stand-ins take the parameters Learn's cmdlet references list, so a parameter a cmdlet doesn't have fails here as it would on a server.

**The verdict.** Use Learn's cmdlets and their order as the model for every write. Don't use the procedures as the program: they read the KDS key, skip the migration's own limits and waits, and stop at "migrated", with nothing that keeps the account from being forgotten at program G5.

## The code: what `examples/non-person-identity` adds

| `Island`, `MovesToWorkloadIdentity`, `RetireThroughDecommission`, `MigrationComplete`, `Superseded` (disabled and in the holding OU: a person deletes it through the decommission ticket, 90 days after the disable), `HandedOff`, `Blocked`, `AwaitDisposition` | Recorded, with the reason | No |

The plan is written as `kerberos-plan.json` (`planVersion` 2) with the register's SHA-256, the SHA-256 of each input, the tenant, the cloud, the domain, the date, the standard it was built with (`adStandard`) and the pipeline's identity. Each write carries its call's `RunBy` (`pipeline` or `person`), the `RequestId` and `ChangeRecord` that approved it, and the `Controls` and `Ksis` its call declares in `calls-ch06.json`. The same inputs give the same plan, byte for byte, so a reviewer approves a hash.

### The island list and the reconciliation

`island-list.csv` holds every account that stays on Kerberos under the name it will have (the dMSA or gMSA a conversion creates, or the account itself), with its SPNs, its D-NP3 disposition, SPN owner, end date, the date that bounds it (`EndBound`: `D08` for a `KeepKerberos` account, `G5` for any other) and whether the end date is within it (`WithinBound`), the authorizing official who accepted an account kept on Kerberos (`AoAcceptedBy`, carried from Chapter 03) and whether it is ready for the program's SPN retirement (P4.6). A `KeepKerberos` account without that acceptance isn't ready, and neither is an account that needs an SPN owner and has none. The run's manifest records `islandHandoffReady`, true only when every row is ready; a row whose bounding date isn't set isn't.

`reconciliation.json` holds every gMSA and dMSA, existing or planned, with its destination and outcome: `MovesToWorkloadIdentity`, `Retires`, `OnIslandList`, `HandedOff` or `Unreconciled`. When the program confirms or revises D11 (D09, week 36), `program-dates.json` changes in a reviewed pull request, and Chapter 03's run and this one are repeated inside the 72-day margin before program G5.

### The separate write path

`Invoke-NpiKerberosIslandAction.ps1` is the only code in this chapter that can write, and it writes only through `New-NpiKrbWriter`, whose calls are the `kerberos-apply` task's. It refuses to run unless:

- the plan file's SHA-256 is the one passed as `-ApprovedSha256`;
- the plan is for this tenant and this domain, and no more than seven days old (*Design guidance*);
- each write is a declared `kerberos-apply` call with its cmdlet and only its `allowedParams`; a new account is AES256 in the plan's service-account OU, a new gMSA states the plan's password interval, a retriever list is never empty, a superseded account is a distinguished name, a move goes only to the plan's holding OU, and no cmdlet that removes, uninstalls, undoes or resets is ever run;
- each write carries its SailPoint request and ServiceNow change;
- `-RunAs` says who is running it, and a live run checks it: `Pipeline` only as the pipeline's gMSA `gmsa-msapipe$`, `Person` only as a person, never a computer, a managed account or a system identity, against a read-write domain controller.

Who sends each write is declared per call, as `runBy` in `calls-ch06.json` ([WD-163](../../../about/decision-register.md#wd-163)). A run sends only the writes that are its own and reports the others as `Refused`, so one approved plan is applied in two runs: the pipeline's, then a person's.

| Call | Action | Cmdlet | `runBy` | Controls | KSIs |
|---|---|---|---|---|---|
| `krb-new-gmsa` | `CreateGmsa` | `New-ADServiceAccount` | pipeline | AC-6, IA-5, CM-3 | KSI-IAM-ELP, KSI-CMT-LMC |
| `krb-set-retrievers` | `SetRetrievers` | `Set-ADServiceAccount` | pipeline | AC-6 | KSI-IAM-ELP |
| `krb-disable-superseded` | `DisableSuperseded` | `Disable-ADAccount` | pipeline | AC-2(3) | KSI-IAM-AAM |
| `krb-move-superseded` | `MoveSuperseded` | `Move-ADObject` | pipeline | AC-2(3) | KSI-IAM-AAM |
| `krb-new-dmsa` | `CreateDmsa` | `New-ADServiceAccount -CreateDelegatedServiceAccount` | person | IA-5, CM-3 | KSI-IAM-SNU, KSI-CMT-LMC |
| `krb-start-migration` | `StartDmsaMigration` | `Start-ADServiceAccountMigration` | person | IA-5, CM-3 | KSI-IAM-SNU, KSI-CMT-LMC |
| `krb-complete-migration` | `CompleteDmsaMigration` | `Complete-ADServiceAccountMigration` | person | AC-2(3), IA-5 | KSI-IAM-AAM, KSI-IAM-SNU |

`-RunAs Pipeline` sends the pipeline's writes; a person's write is `Refused` and the pipeline never sends it. `-RunAs Person` sends the person's writes, and a pipeline write only with `-TestDomain`, for a test domain before the pipeline exists. The controls and KSIs are the kit's mapping per call, carried into the plan and each run's `results.json` (*design guidance*); the standard's step-by-step mapping is the [guide's](../../../books/guides/service-account-migration.md#msa-standard-steps).

Before each write it re-reads the target and skips the write if the precheck no longer holds: the root key isn't ready, the account already exists, the retrievers changed since review, the migration state moved, the old account is already disabled, or it's already in the holding OU (and, with `-Apply`, a move waits until the account is disabled). Without `-Apply` it stops after the prechecks and reports `WouldSend`. After each write it reads the target again and records `Verified`: the outcome is `Sent` when the re-read shows the change and `Unverified` when it doesn't, which means check AD before anything else.

| Task | Cmdlets | Active Directory right |
|---|---|---|
| `kerberos-island` (read) | `Get-ADObject` (KDS root keys), `Get-ADServiceAccount`, `Get-ADUser`, `Get-ADDomainController`, `Get-ADComputer` | The default read of an authenticated domain user, plus a delegated read of `msKds-UseStartTime` and `msKds-CreateTime` in `CN=Master Root Keys`, whose class's default security descriptor grants Enterprise Admins, Domain Admins and SYSTEM only[^np06-kds-class] (research gaps, rows 52 and 53) |
| `kerberos-apply` (write; per call, the pipeline's gMSA or a person) | The reads, `New-ADServiceAccount`, `Set-ADServiceAccount`, `Start-` and `Complete-ADServiceAccountMigration`, `Disable-ADAccount`, `Move-ADObject` | The pipeline's gMSA: the right to create `msDS-GroupManagedServiceAccount` objects in the service-account OU, delegated there to `DL-gMSA-Creators`, of which it is the only member;[^np06-gmsa-manage] write of `msDS-GroupMSAMembership` on the accounts it creates; a delegated right to disable accounts in the account's OU and to move them into the holding OU. A person: Domain Admins or Enterprise Admins, or equivalent, to create or migrate to a dMSA[^np06-dmsa-setup] |

The read task holds no domain administration. The pipeline's identity, `gmsa-msapipe$`, is itself a gMSA in the service-account OU with only the delegated rights above ([WD-154](../../../about/decision-register.md#wd-154), [WD-159](../../../about/decision-register.md#wd-159), [WD-163](../../../about/decision-register.md#wd-163)): it is in no privileged group, never writes a group's membership, and never sends a dMSA step, an uninstall or a delete. The dMSA steps need Domain Admins under Learn's procedure, so they stay with a person, on a plan someone else approved. The guide's [Set it up once](../../../books/guides/service-account-migration.md#msa-standard-setup) delegates the create right and creates the pipeline's gMSA.

To complete, plan:

   ```powershell
   ./Invoke-NpiKerberosIsland.ps1 -Cloud gcc -RegisterRun out/inventory-test -MatrixRun out/kerberos-test-matrix -ProgramDatesPath <matrix-inputs>/program-dates.json -InputPath <inputs> -Server <test-dc> -OutputPath out/kerberos-test-complete
   ```

   The reviewer passes you `out/kerberos-test-complete/kerberos-plan.json`'s SHA-256 as `<sha3>`. Dry-run, apply, and read both accounts:

   ```powershell
   ./Invoke-NpiKerberosIslandAction.ps1 -PlanPath out/kerberos-test-complete/kerberos-plan.json -ApprovedSha256 <sha3> -RunAs Person -Server <test-dc> -OutputPath out/kerberos-test-complete-dry
   ./Invoke-NpiKerberosIslandAction.ps1 -PlanPath out/kerberos-test-complete/kerberos-plan.json -ApprovedSha256 <sha3> -RunAs Person -Server <test-dc> -OutputPath out/kerberos-test-complete-apply -Apply
   Get-ADUser -Identity <test-account> -Properties ServicePrincipalName -Server <test-dc> | Select-Object SamAccountName, Enabled, ServicePrincipalName
   Get-ADServiceAccount -Identity <new-dmsa> -Properties ServicePrincipalName -Server <test-dc> | Select-Object Name, ServicePrincipalName
   ```

   To back out instead, Learn's undo and the re-enable, by hand:

   ```powershell
   Undo-ADServiceAccountMigration -Identity <new-dmsa> -SupersededAccount "<test-account-dn>"
   Enable-ADAccount -Identity <test-account>
   ```

   Either way, after removing the test accounts in the test domain, delete the `out` folders:

   ```powershell
   Remove-Item -Recurse -Force out/kerberos-test*
   ```

## Dangers

| Danger | What happens | The guard |
|---|---|---|
| A gMSA left behind at program G5 | The workload loses its credential when the last domain controller is demoted | Every gMSA and dMSA reconciled with D11 and program G5 (NPI-KRB-07); the run repeated when D11 changes |
| A dMSA migration completed too early, or on a host that can't use it | The old account is disabled; the service fails on hosts the dMSA hasn't learned | Complete only 30 days after the start; Windows Server 2025 on every host and one domain controller; no unconstrained delegation (NPI-KRB-04) |
| The old account deleted | No way back; the service and the dMSA link to it | No delete, uninstall, undo or reset call exists; the writer refuses them by name |
| A dMSA started for an account with no AES keys | The service's tickets fail under the 2026 RC4 change, and the password mustn't be reset mid-migration | A person checks for events 202 to 209 and changes the password before `StartDmsaMigration` ([service account guide, B0](../../../books/guides/service-account-migration.md#migration-b)); NPI-KRB-04 doesn't check keys yet |
| A Windows Server 2025 domain controller without the August 2025 update | Anyone with create-child rights on an OU can create a dMSA that takes over another account | The update before promotion; dMSAs created by Domain Admins only through the write path ([Who may create a dMSA](../../../books/guides/service-account-migration.md#sam-dmsa-create-right)) |
| A root key used before it replicates | gMSA password retrieval fails on other domain controllers | Creations wait until a key has been usable for 10 hours (NPI-KRB-01); the code never creates a key |
| The root key read as a secret | Whoever runs the check holds the input to every gMSA password | Only `msKds-UseStartTime` and `msKds-CreateTime` are read, with a delegated read |
| Retrievers widened by hand | Another host can read the gMSA's password and act as the service | Retrievers are reviewed data, one domain local group per gMSA; drift is a finding and a reviewed `SetRetrievers`; adding a host is a reviewed group change |
| A restart of every service | Learn's step restarts unrelated services on the host | Host steps are the server owner's, scoped to the service, never run by this code |
| A plan changed after review | Different writes from the ones approved | The approved SHA-256; this tenant and domain; no older than seven days |
| A write identity with more than it needs | A standing credential that can create, migrate or take over any account | The pipeline's gMSA holds only the delegated rights on the service-account OUs (create gMSAs as the only member of `DL-gMSA-Creators`, write their retrievers, disable and move into the holding OU), is in no privileged group and is refused every person's step; Domain Admins stays with a person, for the dMSA steps only; the read path holds no administration |
| A write nobody approved | An account created or changed outside SailPoint's approval | Every write carries its request and change record or isn't planned (NPI-KRB-10); the writer refuses one without them |
| An island with no owner or end | SPNs nobody retires; P4.6 has no list to work from | NPI-KRB-05 and -06; the island list is ready for hand-off only when every row is |

## Checklist

- [ ] Every Kerberos account in the register has a reviewed disposition, or a finding with an owner of the fix.
- [ ] The KDS root key check ran with a delegated read of the start time only, not as a Domain Admin.
- [ ] Every gMSA's and dMSA's retrievers match `password-retrievers.json`, and every gMSA's is one domain local `DL-gMSA-<app>-Hosts` group, never a computer account.
- [ ] Every new gMSA and dMSA follows the [managed service account standard](../../../books/guides/service-account-migration.md#msa-standard): `gmsa-<app>` or `dmsa-<app>`, in the service-account OU from the reviewed `ad-standard.json`, with the 30-day interval and, with no SPN and no recorded reason, outbound-only.
- [ ] Every write in every applied plan carried its SailPoint request and ServiceNow change, and no write was `Blocked` (NPI-KRB-10) or `Unverified` when the plan was closed.
- [ ] The pipeline's gMSA, `gmsa-msapipe$`, holds only the delegated rights on the service-account OUs and is in no privileged group; its runs sent only pipeline steps, and a person sent the dMSA steps (`-TestDomain` only in a test domain).
- [ ] No dMSA was planned for an MSA, an account with unconstrained delegation, or a host without Windows Server 2025, and none was completed before 30 days.
- [ ] Every Windows Server 2025 domain controller had the August 2025 update before any dMSA was created, and every account migrated to a dMSA had AES keys before its migration started.
- [ ] Every plan's SHA-256 was approved by someone other than the person who applied it, and the write path's manifest is filed with the change record.
- [ ] No old account was deleted by this code; each one a gMSA replaced is disabled, in the holding OU, and deleted only by a person through the decommission ticket 90 days after the disable; each one a dMSA superseded is disabled and never deleted, as Learn warns.
- [ ] Every account on the island list has an end date within its bound (program G5, or the island's end of life where D11 keeps one, for every account that stays; WD-165) and, where Chapter 03 asks for one, an SPN owner; every `KeepKerberos` account carries the authorizing official's acceptance from Chapter 03, and the list went to the program's SPN retirement (P4.6) only when `islandHandoffReady` was true.
- [ ] Every gMSA and dMSA is `MovesToWorkloadIdentity`, `Retires`, `OnIslandList` or `HandedOff` against the current `program-dates.json`, and Chapter 03's run and this one were repeated after D11 was confirmed.
- [ ] The pinned Learn pages match their manifest, and every upstream commit since the pin has been reviewed.
